# การบ้านหลังประชุม pipeline 5 ส่วน (19 พ.ย. 2569) — ส่วนของมะขาม

เขียน 20 พ.ย. 2569 · ทุกตัวเลขวัดจากข้อมูลในโฟลเดอร์นี้ (GT = `json_แก้ไขแล้ว/` 40 หลัง · PDF = `image/` 175 หลัง) · สคริปต์วัดอยู่ใน `tools/` ถ้าไม่เห็นด้วยกับตัวเลข รันซ้ำได้

ที่ไม่ใช่ข้อเท็จจริง = ข้อเสนอ ระบุไว้ว่า "ข้อเสนอ" ทุกที่ · ข้อเสนอทั้งหมดรอทีมตัดสิน ยังไม่มีอะไรถูกเปลี่ยนใน GT หรือใน prompt

## 1. ส่วน 2 (จัดประเภทงานก่อสร้าง) — ควรมีเป็นขั้นแยกไหม

**ข้อเสนอ: ไม่ต้องมีเป็นขั้นที่เรียกโมเดล** เก็บเป็น "ข้อเท็จจริงของไฟล์" ที่ส่วน 1 คำนวณฟรีแทน (ขนาดกระดาษ จำนวนหน้า จำนวนชั้นจากสารบัญ) แล้วให้ส่วน 4 (ชนิดแผ่น GT/SP/SM/SS) เป็นตัวเลือก prompt จริง

เหตุผล
1. **ไม่มีข้อมูลสอบ "อื่นๆ"** คลังของเรา 175 หลังเป็นบ้านหรืออาคารล้วน ไม่มีถนน โรงงาน โรงไฟฟ้าสักไฟล์ ตัวจัดประเภทที่ตอบ "อื่นๆ" จึงพิสูจน์ไม่ได้ว่าถูกหรือผิด ซึ่งเป็นสภาพที่เกิดภาพหลอนได้มากที่สุด
2. **สัญญาณถูกที่ใช้ได้ฟรี แต่ไม่ขาด** (วัดจาก PDF ทั้ง 175 หลัง, "ขนาดที่เจอมากสุดของเล่ม"): บ้านเล็ก 118 หลัง = A3 106 หลัง (90%) · บ้านใหญ่ 56 หลัง = A3 24 (43%) A2 18 A0 11 A1 3 · จำนวนหน้ามัธยฐาน 21 vs 28 และช่วงทับกัน (2–137 vs 5–108) · ขนาดกระดาษอ่านฟรีจาก PDF ส่วนสเกลที่พิมพ์ในกรอบชื่อแบบยังไม่ได้ดึง (ต่อยอดในส่วน 1 ได้ ไม่ต้องเรียกโมเดล) สองอย่างนี้น่าจะพอสำหรับ "คาดสเกล" ที่ King ต้องการ แต่ยังไม่ได้วัดว่าพอจริงไหม
3. **สิ่งที่เปลี่ยน prompt จริงๆ คือชนิดแผ่น ไม่ใช่ชนิดงาน** (แปลนคาน ≠ ตารางเสา ≠ รูปตัดบันได) ส่วน 4 ต้องแยกชนิดแผ่นอยู่แล้ว
4. ทุกขั้นที่เพิ่ม = จุดพังเพิ่ม + เวลารันเพิ่ม + หน่วยความจำเสี่ยงหมด (ข้อกังวลของมะขามในประชุม) ขณะที่ส่วนอื่นๆ ที่เรียกโมเดลอยู่แล้ว (title block, grid, SM/GT/SS) คาดว่าใช้ 5–10 ครั้งต่อส่วนอยู่แล้ว

ความเสี่ยงที่รับ: ถ้างานจริงของ STECON เป็นอาคารใหญ่ที่ต้องการ prompt คนละแบบกับบ้าน เราจะไม่รู้จนกว่าจะเห็นผลพัง · เงื่อนไขกลับมาพิจารณา: เมื่อทดสอบ prompt เดียวกันกับอาคารใหญ่แล้วพังซ้ำและ prompt เฉพาะประเภทแก้ได้ (ต้องมีข้อมูลสอบก่อน) · ถ้าไม่เจอสารบัญหรือกรอบกริดเลย ให้ติดธง "นอกขอบเขต ให้คนตรวจ" ไม่เดาประเภท

## 2. นโยบาย dummy grid

**ข้อเสนอ: เก็บทุกตำแหน่งที่พิมพ์ไว้เป็น "ตำแหน่งรอ" ไม่มีชื่อ แล้วเลื่อนเป็น dummy grid (ตั้งชื่อ 3', 3'' ฯลฯ) เฉพาะเมื่อมีองค์ประกอบมาเกาะ** ผ่านโค้ดที่แน่นอน ไม่ใช่ให้โมเดลเลือก

หลักฐาน (GT 40 หลัง · "ใช้" = มีจุดปลายขององค์ประกอบในบ้านเดียวกันอ้างชื่อเส้นนั้น)
| รายการ | จำนวน |
|---|---|
| เส้นกริดทั้งหมดใน grid master | 970 (named 352 · dummy 618 = **64% เป็น dummy**) |
| dummy ที่มีองค์ประกอบมาเกาะ | 189 จาก 618 (**31%**) |
| dummy ที่เพิ่มตามกฎข้อ 4 (ทุกมิติที่พิมพ์ = เส้น) | 378 · **ใช้จริง 4 (1%)** |
| dummy ที่เหลือ (การอ่านแบบจริงต้องการเอง) | 240 · ใช้จริง 185 (**77%**) |
| จุดปลายองค์ประกอบที่อยู่บน dummy | 745 จาก 5,608 (13.3%) |

อ่านว่า: ข้อกังวลของมะขามจริง (ถ้าไม่เก็บมิติที่พิมพ์ ตัวเลือกจะขึ้นกับว่าอ่านคานเจออะไร) และของฝั่งที่กลัวภาพหลอนก็จริง (dummy 2 ใน 3 ไม่มีหน้าที่เลยจนถึงตอนนี้) ทางที่ไม่ต้องเลือกข้าง:
1. ผังกริดรอบแรก: เส้น named + "ตำแหน่งรอ" ทั้งหมด ตำแหน่งรอมาจากเวกเตอร์/ตัวเลขที่พิมพ์ (กริด lab) ไม่ต้องให้โมเดลคิดชื่อ → ครบตามที่มะขามต้องการ
2. หลังอ่านองค์ประกอบ: ตำแหน่งรอที่มีปลายองค์ประกอบเกาะ (ในระยะคลาดที่กำหนด) ถูกเลื่อนเป็น dummy ตั้งชื่อตามกฎ prime ที่มีอยู่ (`tools/gridfix.py`) → ได้ข้อกำหนดของ King (กล่องบันไดลิฟต์ที่ขึ้นหลายชั้นมี dummy ผนังล็อบบี้ชั้นเดียวไม่มี) โดยอัตโนมัติ
3. ผลข้างเคียงดี: ผังกริดรอบแรกสั้นลง 378 เส้นจาก 970 (39%) ในผังกริดที่ใช้สอนและที่ให้โมเดลพ่น ซึ่งเราเคยเจอว่าโมเดลวนจนชนเพดาน 9,000 token (งานจริง 11 พ.ย.)

ความเสี่ยงที่รับ: (ก) ต้องสร้างตัวเกาะองค์ประกอบเข้าตำแหน่งรอ ซึ่งยังไม่มี และพึ่งกริด lab ที่รู้ตำแหน่งพิกเซลจริง (ภาพสแกนต้อง OCR) (ข) ตัวนับ "ใช้" วัดด้วย regex รูปแบบอ้างอิง `D1` / `3'` อาจพลาดบางรูปแบบ ทิศทางชัด (1% เทียบ 77%) แต่เลขไม่เป๊ะ (ค) ตำแหน่งรอที่ไม่มีใครเกาะอาจเป็นมิติจริงที่องค์ประกอบยังไม่ถูกอ่านออกมา ไม่ใช่ขยะ — ต้องดูตอนใช้งานจริง ตรงกับที่ประชุมบอกว่าผลจะรู้ตอนใช้

## 3. JSON หนึ่งแบบต่อ detail หนึ่งชนิด — ร่าง v0.1

**ข้อเสนอ: แยกแม่แบบตามชนิดองค์ประกอบ (`element_type`) ไม่ใช่ตามแผ่น** ตอนนี้ `finetune_output_contract/templates/section.template.json` เป็นไฟล์เดียวที่ผสม คาน เสา ฐานราก ไว้ด้วยกัน และกติกาของแต่ละชนิดอยู่ในช่อง `note` เป็นข้อความ

หลักฐานว่าต้องแยกและต้องล็อกชื่อคีย์ (GT 40 หลัง, แถว `section` + `schedule`):
- **ความหนาฐานรากมี 4 ชื่อคีย์ปนกัน** จาก 188 แถว: ใช้ `height_mm` อย่างเดียวแค่ 61 แถว (32%) · 22 แถวไม่มีคีย์ความหนาเลย · ที่เหลือใช้ `height_mm`+`thickness_mm` (29) / `height_mm`+`depth_m` (23) / `height_mm`+`depth_mm` (17) ฯลฯ — ตัว import ของ Constistant ต้องเดาจากค่า (บันทึกใน Constistant CLAUDE.md 26 ก.ย.: ฐานรากใช้มิติสามธรรมเนียมขัดกัน) ก้อนนี้เป็นต้นเหตุเดียวกับที่ปริมาณคอนกรีตฐานรากเพี้ยนเงียบ ๆ มาก่อน · pile_cap 41 แถวก็เหมือนกัน
- **คีย์ที่ "มีเสมอ" น้อยกว่าที่ BOQ ต้องการ**: ฐานราก 188 แถวมีเสมอแค่ `element_id`/`element_type`/ความมั่นใจ (เหล็กหลัก ปลอก ขนาดล้วนเป็น "บางแถว") · เสาจากรูปตัด 64 แถว กว้าง/ลึกอยู่ 10–90% ของแถว ขณะที่เสาจากตาราง 181 แถวมีครบทุกแถว
- **คีย์หายากกระจาย**: คาน 371 แถวมีคีย์ที่เจอไม่ถึง 10% ของแถวอีก 29 ชื่อ (`depth_mm`, `height_m` เป็นชื่อสำรองของความสูง) · ฐานราก 73 ชื่อ · พื้น 43 ชื่อ · บันได 58 ชื่อ

หลักการร่าง
1. หนึ่งไฟล์แม่แบบต่อหนึ่ง `element_type` เฉพาะชนิดที่ Constistant ใช้คิดปริมาณ: `beam` `column` `footing` `pile_cap` `slab` `tie_beam` (ภายหลังเพิ่ม `pile` `pedestal` `stair` เมื่อมี consumer) ชนิดสถาปัตย์/ระบบ (ประตู หน้าต่าง สุขภัณฑ์ วงจรไฟ) อยู่นอกขอบเขตตามที่ King กำหนด (ข้าม MEP)
2. หนึ่งปริมาณ = หนึ่งชื่อคีย์ มีหน่วยในชื่อ: ความหนาฐานราก/ฐานแผ่น = `thickness_mm` ด้านแปลน = `width_mm` × `length_mm` (ห้าม `height_mm` `depth_mm` `depth_m` สำหรับสิ่งนี้) · คีย์เดิมที่ตรงกับสิ่งนี้ต้องมีตารางแปลง (alias) ให้ตัว import ใช้กับข้อมูลเก่าได้ ไม่ต้องแก้ GT ย้อนหลังทั้งหมด
3. คีย์ที่ BOQ ต้องการ = **จำเป็น** ค่าเป็น `null` ได้ แต่ต้องมีคีย์ และต้องมี `confidence_flags` บอกเหตุ ไม่ใช่เว้นว่างเงียบๆ (ฐานราก: ด้านแปลน ความหนา เหล็กหลักตาข่าย ปลอก/ตะแกรงขอบ) · คีย์อื่น = ไม่บังคับ
4. ค่าที่พิมพ์บนแบบเก็บแยกในคีย์ `*_printed_as` (มีอยู่แล้วในข้อมูล) เพื่อให้ตรวจย้อนหลังได้ว่าตีความอย่างไร
5. ชนิดที่โครงสร้างต่างกัน เช่น เสาใช้ `count` เดียวไม่แยกบน/ล่าง ตะแกรงฐานรากใช้ `count` เดียว ต้องอยู่ใน**แม่แบบ** ไม่ใช่ในช่อง `note`

ตัวต่อไปที่ต้องทำ ถ้าทีมเห็นด้วย: เขียนแม่แบบ `footing` กับ `column` ก่อน (เจ็บที่สุดตามตัวเลขข้างบน) แล้วดูว่าตัวอ่านแบบและตัวนำเข้าเปลี่ยนอะไรบ้าง · ข้อจำกัดที่ต้องรู้: เปลี่ยนเป้าหมายการสอนโมเดล = ต้องเทรนใหม่ ถ้าใช้ข้อมูลเดิมต้องผ่านสคริปต์แปลง ซึ่งเสี่ยงเลือกความหมายของ `depth_mm` ผิด (ฐานรากบางแถวใช้เป็นด้านแปลน บางแถวเป็นความหนา)

## 4. แขนระดับ (level arm) — ผลวัด

King: แบบโครงสร้างมักไม่พิมพ์ระดับ ต้องอ่านจากรูปตัดสถาปัตย์ · ที่วัดได้ = "ตัวเลขระดับที่พิมพ์อยู่บนหน้า อ่านออกไหม" ยังไม่ได้ทำ "ตัวเลขนี้คือระดับของอะไร" · เครื่องมือ `tools/levelarm_probe.py` · เทียบกับ `grid.z_levels` ของ GT (40 หลัง 343 ระดับ แต่ละระดับมีหน้าที่คนอ่านมา = 129 หน้า)

| วิธี | ผล | หมายเหตุ |
|---|---|---|
| อ่านจากข้อความฝังใน PDF | เจอ 7 จาก 343 ระดับ (**2%**) | หน้าที่คนอ่านระดับมา 56 หน้าไม่มีข้อความเลย 70 หน้ามีแค่เลขหน้า อีก 3 หน้าเท่านั้นที่มีข้อความจริง = ใช้เป็นทางหลักไม่ได้ |
| OCR ทั้งหน้า (ตัวอ่านละติน ≤3,300 px) | เจอ **75 จาก 106 (71%)** · ไม่นับระดับ 0.00: 64 จาก 94 (68%) | สุ่มทุกหน้าที่ 3 = 43 หน้า กระจายทุกบ้านที่มี · 7 หน้าอ่านไม่ได้สักป้าย · ~35 วินาทีต่อหน้า บน CPU |
| ป้ายที่ OCR อ่านได้เป็นระดับจริงไหม | 227 จาก 250 ป้าย (**91%**) ตรงกับระดับใดระดับหนึ่งของบ้านนั้นใน GT | เป็นขอบล่างของความแม่น: GT อาจตกระดับจริงบางตัว จึงไม่นับว่าผิดทั้งหมด |

ข้อจำกัดที่ต้องรู้
- นับเฉพาะป้ายที่มีเครื่องหมาย (+ − ±) ระดับที่พิมพ์เป็นเลขเปล่าไม่ถูกนับ
- "เจอ" = ตัวเลขเท่ากับระดับของ GT อยู่ในป้ายที่ OCR อ่านได้บนหน้านั้น ไม่ได้ตรวจว่าป้ายนั้นผูกกับชื่อระดับถูก ตัวเลขทั่วไปอย่าง +0.00 ที่เจอหลายที่จึงพองผลได้ ตัวเลขที่ไม่ใช่ศูนย์ (68%) ซื่อสัตย์กว่า
- ไม่ได้ทดสอบกับภาพสแกนคุณภาพต่ำหรือแบบ A0/A1 ที่ป้ายเล็กมากเมื่อย่อเหลือ 3,300 px (ใช้ตัวอ่านเดียวกับ title block)
- สุ่มทุกหน้าที่ 3 ตามลำดับบ้าน ไม่ใช่สุ่มจริง

อ่านว่า: **ตัวเลขระดับอ่านจากภาพได้ราว 2 ใน 3 โดยไม่ต้องเรียกโมเดลใหญ่ แต่ยังไม่ผูกกับชื่อ/ชั้น และยังพลาด 1 ใน 3** ข้อเสนอขั้นต่อไป (ยังไม่ได้ทดลอง): (ก) ตัดหน้าเป็นช่องซ้อนกัน เพื่อดึงป้ายเล็กที่หลุด (ข) ผูกเลขกับชั้นด้วยลำดับ: เรียงระดับจากต่ำไปสูงแล้วจับคู่กับชั้น F1 F2 ... แล้วเทียบความสูงชั้นกับ `tools/level_link.py` ที่มีอยู่ ถ้าไม่ลงรอยให้ติดธง ไม่เดา (ค) ให้โมเดลอ่านข้อความไทยข้างป้ายระดับ (ระดับพื้นชั้น 2, ระดับหลังคา) เฉพาะ crop เล็กรอบป้าย ไม่ใช่ทั้งหน้า
