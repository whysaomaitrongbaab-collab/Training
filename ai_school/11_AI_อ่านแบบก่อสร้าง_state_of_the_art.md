## 11.0 คำถามเปิด (ผูกกับงานจริงของเรา)

ย้อนไปดูตัวเลขของเรา: element recall สูงสุดที่โปรเจกต์ทำได้คือ 28.2% (รอบ t01, Qwen3.6-35B-A3B + LoRA) และในรอบ t02 บนผังคาน (beam plan) ได้เพียง 11% recall

คำถามที่มะขามถามตอนนั้นคือ "นี่เราทำอะไรผิด หรือว่างานนี้มันยากจริง ๆ"

คำตอบสั้น ๆ คือ ทั้งสองอย่าง เราทำผิดหลายจุด (บทที่ 5-8 อธิบายบั๊กทั้ง 7 ข้อไปแล้ว) แต่ถึงแม้จะแก้ทุกจุด งานนี้ก็ยังยากจริง ๆ ในระดับที่วงการวิจัยยังไม่ได้ปิดเกม หลักฐานคือ benchmark ที่เพิ่งออกในปี 2026: AECV-Bench [21] วัด VLM ชั้นนำบนผังพื้นสถาปัตย์ พบว่าการอ่านตัวหนังสือ (OCR) ทำได้ถึง 0.95 แต่การนับประตู-หน้าต่างได้เพียง 0.40-0.55 และ GDP.pdf [24] ที่ทดสอบเอกสารวิชาชีพ 10 สาขา พบว่าโมเดลที่ดีที่สุดผ่านเพียง 30.7% ของโจทย์ โดยหนึ่งใน failure pattern ที่ระบุไว้ชัดคือ "นับสัญลักษณ์ในผังพื้นผิด"

สังเกตว่านี่คือ pattern เดียวกับที่เราเจอ: VLM อ่านตัวเลข "B2 0.20×0.40" ได้ แต่นับว่ามี B2 กี่ตัวในผังไม่ได้ และเมื่อบังคับ greedy decoding ก็วนพิมพ์ B2 ไม่รู้จบ (บั๊กข้อ 4)

บทนี้จะพาไปดูว่าคนอื่นในโลกเจอปัญหาเดียวกันแล้วแก้อย่างไร แล้วค่อยกลับมาถามว่า ถ้าเริ่มออกแบบใหม่ด้วยความรู้ทั้งหมดในหลักสูตร เราจะเดินทางไหน

## 11.1 ทำไมแบบก่อสร้างไม่เหมือนภาพถ่ายธรรมชาติ

โมเดลภาพเกือบทุกตัว (CNN, ViT, vision tower ของ VLM) ถูก pre-train บนภาพถ่ายธรรมชาติ: หมา แมว รถ ถนน ภาพพวกนี้มีคุณสมบัติที่แบบก่อสร้างไม่มี และแบบก่อสร้างก็มีคุณสมบัติที่ภาพถ่ายไม่มี ลองไล่ทีละข้อ

**ขั้นที่ 1: ภาพถ่ายมี texture, แบบมีแต่เส้น**
ในภาพถ่าย พิกเซลข้างเคียงมักคล้ายกัน (ผิวหมา, ท้องฟ้า) โมเดลจึงเรียนรู้ "พื้นผิว" เป็นหลัก ส่วนแบบก่อสร้างคือกระดาษขาวกับเส้นดำหนา 1-3 พิกเซล ข้อมูลทั้งหมดอยู่ที่ เส้น ความหนาของเส้น และ ตำแหน่งสัมพัทธ์ ไม่มี texture ให้จับ นึกถึงการดูแบบขาวดำที่ถ่ายเอกสารมาเบลอ ๆ คนอ่านยังรู้ว่าเป็นคาน แต่โมเดลที่คุ้นกับ texture จะ "เห็นเป็นกระดาษเปล่า"

**ขั้นที่ 2: สัญลักษณ์มีความหมายตามข้อตกลง ไม่ใช่ตามรูปร่าง**
สี่เหลี่ยมทึบดำเล็ก ๆ คือเสา วงกลมมีเลขคือกริด เส้นประคือคานซ่อนอยู่ใต้พื้น ความหมายเหล่านี้ไม่ได้อยู่ในรูปทรง แต่อยู่ใน "ข้อตกลง" ของวิชาชีพ ภาพถ่าย 1 ล้านภาพจาก internet ไม่ได้สอนข้อตกลงนี้ นี่คือสิ่งที่ Huang et al. 2026 [23] ยืนยัน: โมเดลที่ train บนเอกสารทั่วไป (general document datasets) ตกลงชัดเจนเมื่อเจอแบบ AEC เพราะ domain mismatch

**ขั้นที่ 3: ข้อความเล็กมากและปะปนกับกราฟิก**
"2-DB12" บนแบบขนาด A1 ที่ rasterize มา 3309×2339 px อาจสูงแค่ 12-15 พิกเซล ข้อความเล็กแบบนี้ เมื่อ VLM ย่อภาพลงเหลือ 512 px (บั๊กข้อ 1 ของเรา) จะเหลือสูงประมาณ 2 พิกเซล อ่านไม่ออกแน่นอน

**ขั้นที่ 4: มาตราส่วนและกริด คือ "ระบบพิกัด" ที่ต้องอ่านก่อน**
ภาพถ่ายไม่มีระบบพิกัด แต่แบบมี: กริด A-B-C กับ 1-2-3 และมาตราส่วน 1:100 การรู้ว่าคาน B2 "อยู่ระหว่างกริด B กับ C" ต้องอ่านกริดก่อน แล้วค่อยหาคาน แล้วค่อยผูกความสัมพันธ์ นี่คือเหตุผลที่ t03 ของเราต้องแยก pass3 ออกมาวัดระยะจากผังกริดต่างหาก

**ขั้นที่ 5: ตารางเหล็กเสริม คือ table structure recognition ที่ซ่อนอยู่**
ตาราง beam schedule มีทั้งหัวคอลัมน์ที่ merge กัน (เหล็กบน/เหล็กล่าง, ปลาย/กลาง) และภาพหน้าตัดฝังในตาราง งานนี้ไม่ใช่ OCR ธรรมดา แต่เป็น "อ่านโครงสร้างตาราง" ซึ่งเป็นสายวิจัยของตัวเอง (หัวข้อ 11.4)

**ขั้นที่ 6: ความหนาแน่นสูงและภาพใหญ่มาก**
ผังคาน 1 หน้าอาจมีคาน 80 ตัว เสา 40 ต้น ข้อความ 300 ชิ้น ในภาพเดียว ต่างจาก COCO ที่เฉลี่ยมี object ราว 7 ชิ้นต่อภาพ และภาพเรามีขนาด 3309×2339 = 7.7 ล้านพิกเซล ในขณะที่ ViT มาตรฐานถูกออกแบบสำหรับ 224×224 หรือ 448×448

สรุปเป็นตาราง

| คุณสมบัติ | ภาพถ่ายธรรมชาติ | แบบก่อสร้าง | ผลต่อโมเดล |
|---|---|---|---|
| สัญญาณหลัก | texture, สี | เส้นบาง, ช่องว่าง | pre-train ไม่ตรง |
| ความหมาย | จากรูปร่าง | จากข้อตกลงวิชาชีพ | ต้องมี domain data |
| ขนาดข้อความ | ใหญ่ ไม่มีก็ได้ | 10-15 px สำคัญมาก | ย่อภาพไม่ได้ |
| ระบบพิกัด | ไม่มี | กริด + มาตราส่วน | ต้องอ่านสองชั้น |
| จำนวน object | ~7 | 100-400 | นับผิดง่าย |
| ขนาดภาพ | 0.3-1 MP | 7-8 MP | ต้อง tile |

🎨 **ภาพที่จะวาดใน HTML:** แบ่งจอเป็นซ้าย-ขวา ซ้ายคือภาพถ่ายแมว ขวาคือผังคานจริง มีสไลเดอร์ "ความละเอียดที่ป้อนโมเดล" ตั้งแต่ 224 ถึง 3309 px เมื่อลากลง ทั้งสองภาพจะถูกย่อจริง ๆ (nearest-neighbor) ผู้เรียนควรเห็นว่าแมวยังเป็นแมวที่ 224 px แต่ข้อความ "2-DB12" บนแบบหายไปตั้งแต่ประมาณ 1000 px ด้านล่างแสดงตัวเลข "ความสูงข้อความ (px)" คำนวณสด และแถบสีแดงเมื่อต่ำกว่า 8 px (เกณฑ์ที่ OCR ทั่วไปเริ่มพัง)

```python
# ทดลอง: ข้อความสูงกี่พิกเซลเมื่อย่อภาพ
import numpy as np
page_w, page_h = 3309, 2339          # หน้าที่ rasterize ของเรา
text_h_px = 14                        # ความสูงตัวอักษร "2-DB12" โดยประมาณ
for target in [3309, 2048, 1344, 1024, 768, 512, 448, 224]:
    scale = target / max(page_w, page_h)
    h = text_h_px * scale
    tokens_vit = (int(page_w*scale)//14) * (int(page_h*scale)//14)  # patch 14 px
    flag = "อ่านได้" if h >= 8 else "อ่านไม่ได้"
    print(f"ด้านยาว {target:>5} px | ตัวอักษรสูง {h:5.1f} px | patch ~{tokens_vit:>6} | {flag}")
```

ผลที่ควรได้: ที่ 512 px ตัวอักษรสูงราว 2.2 px นี่คือภาพที่ collator ของเราเห็นตอนเทรน (บั๊กข้อ 1) เท่ากับสอนโมเดลอ่านตัวเลขจากภาพที่ไม่มีตัวเลข

## 11.2 สาย (a): การรู้จำผังพื้น (floor plan recognition)

นี่คือสายที่เก่าแก่ที่สุดและใกล้เคียงกับเรามากในเชิงภาพ แต่ต่างกันที่ "สิ่งที่ต้องการออก"

**ขั้นที่ 1: Raster-to-Vector (Liu et al., ICCV 2017) [2]**
งานนี้วางกรอบคิดที่ยังใช้จนวันนี้: แทนที่จะให้โมเดลวาดผนังออกมาตรง ๆ ให้โมเดล (CNN) ทำนาย "จุดต่อ" (junction) ของผนัง ประตู หน้าต่าง เป็น heatmap ก่อน แล้วใช้ integer programming ประกอบจุดเหล่านั้นเป็นเส้นผนังที่ปิดสนิทตามกฎเรขาคณิต (ผนังต้องต่อกัน ห้องต้องปิด) ได้ precision/recall ประมาณ 90% บนผังพื้นญี่ปุ่น

บทเรียนสำหรับเรา: **แยก "การรับรู้" (perception, ให้ neural net) ออกจาก "การประกอบตามกฎ" (ให้ optimizer/กฎ)** โมเดลไม่ต้องรู้กฎว่าคานต้องพาดบนเสา ให้กฎทำ นี่คือ pattern เดียวกับที่ท่อของเราเริ่มทำใน t03 pass1 organize

**ขั้นที่ 2: CubiCasa5K (Kalervo et al., 2019) [1]**
ชุดข้อมูล 5,000 ผังพื้น annotate เป็น polygon กว่า 80 หมวด และโมเดล multi-task ที่ทำนายทั้ง segmentation ห้อง/ผนัง และ heatmap ของ icon พร้อมกัน สำคัญเพราะเป็นชุดข้อมูลสาธารณะชุดแรก ๆ ที่ใหญ่พอให้เทรนจริง

**ขั้นที่ 3: จาก raster ไป vector CAD โดยตรง (2021-2026)**
FloorPlanCAD (Fan et al., 2021) [3] ตั้งโจทย์ใหม่ชื่อ "panoptic symbol spotting" คืออ่านไฟล์ CAD ที่เป็น vector (เส้น, โค้ง) แล้วระบุทั้งหมวดและ instance ของสัญลักษณ์ทุกชิ้น จากนั้นมีงานต่อยอด: GAT-CADNet [4] มองแบบเป็นกราฟ (เส้นเป็น node), SymPoint มองเส้นเป็น point cloud, CADSpotting (2024-2026) [6] ใช้ sliding window + weighted voting + NMS เพื่อจัดการแบบขนาดใหญ่ราว 1,000 ตร.ม., ArchCAD-400K (2025) [5] สร้าง annotation engine อัตโนมัติจนได้ 413,062 chunk จากแบบ 5,538 แผ่น และ TextCAD (2026) [7] เพิ่มการอ่าน "ข้อความกำกับ" เข้าไปช่วยสัญลักษณ์

จุดที่ต้องระวังเมื่ออ่านงานสายนี้: ส่วนใหญ่รับ **vector CAD (DWG/DXF)** เป็น input ไม่ใช่ PDF สแกน ถ้าแบบของเรามาเป็น PDF vector ที่ยังมีเส้นอยู่ เราอาจ "ดึง vector" ออกได้โดยตรงโดยไม่ต้อง rasterize เลย ซึ่งเป็นทางเลือกที่โปรเจกต์เรายังไม่ได้ลอง

🎨 **ภาพที่จะวาดใน HTML:** ผังพื้นเล็ก ๆ 4 ห้อง มีปุ่มสลับ 3 มุมมอง: (1) raster (พิกเซล), (2) junction heatmap (จุดสีแดงที่มุมผนัง ความเข้มปรับได้ด้วยสไลเดอร์ threshold), (3) vector ที่ประกอบแล้ว (เส้นสีน้ำเงิน) เมื่อลด threshold ผู้เรียนจะเห็นจุดปลอมโผล่และผนังปลอมถูกประกอบขึ้น เมื่อเพิ่ม threshold ผนังจริงเริ่มขาด แสดงค่า precision/recall ของผนังสด

## 11.3 สาย (b): แบบวิศวกรรม, สัญลักษณ์ CAD และ P&ID

P&ID (piping and instrumentation diagram) คือแบบของวิศวกรเคมี/เครื่องกล: วาล์ว ปั๊ม ท่อ เชื่อมกันเป็นเครือข่าย โครงสร้างปัญหาเหมือนผังคานของเราอย่างน่าตกใจ: สัญลักษณ์เล็ก ๆ (วาล์ว = เสา) เชื่อมด้วยเส้น (ท่อ = คาน) มีป้ายกำกับ (tag = ชื่อคาน) และต้องออกมาเป็นกราฟ (topology = ความสัมพันธ์คาน-เสา-กริด)

**ขั้นที่ 1: pipeline แบบคลาสสิก (Digitize-PID, 2021) [8]**
Paliwal et al. เสนอท่อ 3 ส่วน: (1) ตรวจเส้นด้วย kernel-based line detection, (2) รู้จำสัญลักษณ์แบบสองขั้น (หาก่อน แล้วค่อยจำแนก), (3) OCR อ่าน tag แล้วประกอบเป็นกราฟ พร้อมปล่อยชุดข้อมูล synthetic 500 แผ่น สังเกตว่านี่คือ hybrid pipeline ตั้งแต่ปี 2021 ก่อนยุค VLM

**ขั้นที่ 2: YOLO และ detector สำหรับสัญลักษณ์**
สายนี้ใช้ object detector (YOLO, DETR) หาสัญลักษณ์เป็น bbox เป็นหลัก เพราะสัญลักษณ์มีรูปร่างคงที่ Gupta et al. 2024 [28] ใน Automation in Construction เสนอ semi-supervised symbol detection สำหรับ P&ID เพื่อลดภาระ annotate และในสาย AEC Huang et al. 2026 [23] เปรียบเทียบ detector 5 ตัวบนชุดข้อมูลแบบ AEC ที่สร้างเอง พบว่า RF-DETR ได้ mAP50 = 0.949 สำหรับตรวจ layout (title block, ตาราง, viewport) ในขณะที่ Qwen3-VL ได้ F1 = 0.911 ในการสกัดข้อมูลจากส่วนที่ตรวจเจอแล้ว นี่คือตัวเลขที่บอกว่า "detector หาที่, VLM อ่านความหมาย" ทำงานได้ดีจริง

**ขั้นที่ 3: MLLM ทำ P&ID (2026) [10]**
Zhu et al. 2026 ใช้ multimodal LLM แยกเป็น 2 ขั้น: สกัด tag ของอุปกรณ์ก่อน แล้วค่อยให้โมเดล "ให้เหตุผล" ประกอบ topology พบว่าการแยกขั้นให้ผลแม่นและสอดคล้องเชิงโครงสร้างมากกว่า end-to-end

**ขั้นที่ 4: แบบโครงสร้างโดยตรง**
งานที่ตรงกับเราที่สุดในสายนี้คือ Bayer et al. 2026 [27] ใน Automation in Construction: สกัด structural element จากแบบสะพาน 2D ด้วย deep learning แล้ว **ตรวจความถูกต้องด้วย knowledge graph** (กฎว่าอะไรต่อกับอะไรได้) ซึ่งเป็นแนวคิด "ให้กฎวิศวกรรมเป็นด่านตรวจ" แบบเดียวกับที่เราอยากทำ

🎨 **ภาพที่จะวาดใน HTML:** ผังคานย่อ 3×3 กริด แสดงเป็นกราฟ: เสาเป็น node วงกลม คานเป็น edge มีปุ่ม "สุ่มความผิดพลาดของ detector" ที่ลบเสาออก 1 ต้น ผู้เรียนจะเห็น edge ที่ลอยไม่มีปลาย ถูกขีดสีแดงโดยตัวตรวจกฎ ("คานต้องมีเสารองรับสองปลาย") พร้อมข้อความว่ากฎข้อไหนถูกละเมิด นี่คือ knowledge-graph validation ในรูปที่เล็กที่สุด

```python
# ตรวจกฎง่าย ๆ: คานทุกตัวต้องมีเสาที่ปลายทั้งสอง (รัศมี tol พิกเซล)
import numpy as np
cols = np.array([[100,100],[400,100],[100,400],[400,400]])      # เสา (x,y)
beams = [((100,100),(400,100)), ((100,400),(400,400)), ((400,100),(700,100))]
tol = 15
for i,(p,q) in enumerate(beams):
    ok = [np.min(np.linalg.norm(cols-np.array(e),axis=1)) <= tol for e in (p,q)]
    print(f"beam {i}: ปลาย A {'มีเสา' if ok[0] else 'ลอย'} | ปลาย B {'มีเสา' if ok[1] else 'ลอย'}")
```

## 11.4 สาย (c): Document AI และการอ่านตาราง

แบบก่อสร้างมี "ส่วนที่เป็นเอกสาร" เยอะกว่าที่คิด: title block, ตาราง beam/column schedule, หมายเหตุทั่วไป สายวิจัย Document AI จึงตรงกับส่วนนี้

**ขั้นที่ 1: LayoutLM (2019-2022) [11][12]: ให้โมเดลรู้ "ตำแหน่ง" ของคำ**
LayoutLM รับ input เป็นคำจาก OCR + พิกัด bbox ของแต่ละคำ + ภาพ แล้ว pre-train แบบ BERT ให้เข้าใจว่าคำที่อยู่ใกล้กันเชิงพื้นที่สัมพันธ์กัน LayoutLMv3 (2022) รวม masking ของข้อความและภาพเข้าด้วยกัน จุดสำคัญ: สายนี้ **ต้องมี OCR ก่อน** ถ้า OCR อ่าน "DB12" เป็น "D812" โมเดลก็รับความผิดนั้นไปเต็ม ๆ (error propagation)

**ขั้นที่ 2: Donut (2021) [13] และ Nougat (2023) [14]: ไม่ต้องมี OCR**
Donut คือ encoder-decoder ที่รับภาพเอกสารตรง ๆ แล้วพ่น JSON ออกมา ไม่ผ่าน OCR เลย พร้อมเครื่องมือสร้างเอกสาร synthetic เพื่อ pre-train (แนวคิดเดียวกับที่เราจะพูดใน 11.9) Nougat ของ Meta ทำสิ่งเดียวกันกับ PDF วิชาการ พ่นออกมาเป็น markdown พร้อมสมการ ทั้งสองคือบรรพบุรุษของ "VLM พ่น JSON" ที่เราใช้ และที่น่าสนใจคือ Khan et al. 2025 [19] ยังเลือก Donut (ไม่ใช่ VLM ตัวใหญ่) มาทูนอ่านแบบเครื่องกล ได้ F1 93.5% แต่ก็รายงาน hallucination rate 11.5% อย่างตรงไปตรงมา

**ขั้นที่ 3: Table structure recognition [15]**
PubTables-1M (Smock et al., 2021) ปล่อยตารางเกือบ 1 ล้านตารางจากบทความวิชาการ พร้อม annotation ของแถว คอลัมน์ เซลล์ที่ merge และโมเดล Table Transformer (DETR) ที่ตรวจโครงสร้างตาราง สำหรับตาราง beam schedule ของเรา แนวทางที่ตรงที่สุดคือ: ตรวจกรอบตาราง → ตรวจแถว/คอลัมน์ → ตัดเซลล์ → อ่านแต่ละเซลล์ ซึ่งแม่นกว่าให้ VLM อ่านทั้งตารางรวดเดียวมาก เพราะแต่ละเซลล์เป็นภาพเล็กที่ไม่ต้องย่อ

🎨 **ภาพที่จะวาดใน HTML:** ตาราง beam schedule จำลอง 6 แถว มีสองโหมด: "VLM อ่านทั้งตาราง" (ไฮไลต์ทั้งตารางแล้วโชว์ JSON ที่มีค่าเลื่อนแถว 1 ช่อง จำลอง error ทั่วไป) และ "ตรวจโครงสร้างก่อน" (ค่อย ๆ วาดเส้นแถวสีเขียว เส้นคอลัมน์สีน้ำเงิน แล้วเซลล์ทีละช่องกระพริบพร้อมค่าที่อ่านได้) ผู้เรียนควรเห็นว่าโหมดสองช้ากว่า แต่ไม่มี "เลื่อนแถว"

## 11.5 สาย (d): VLM อ่านแบบเทคนิค, แผนภูมิ และแบบวิศวกรรม

**ขั้นที่ 1: benchmark เชิงกราฟิกที่ VLM ถูกวัด**
ChartQA (2022) [16] มีคำถามกว่า 32,000 ข้อเกี่ยวกับกราฟที่ต้องทั้ง "ดู" และ "คิดเชิงตรรกะ" InfographicVQA (2021) [17] ต้องอ่าน layout + ข้อความ + กราฟิกพร้อมกัน สอง benchmark นี้เป็นเหตุผลที่ VLM ยุคใหม่ (Qwen2.5-VL [30], DocOwl [40]) ถูกฝึกให้อ่านเอกสารและกราฟดีขึ้นมาก แต่ก็ยังไม่ใช่ "แบบก่อสร้าง"

**ขั้นที่ 2: VLM อ่านแบบเครื่องกลและ GD&T (2024-2026) [18][19][20]**
กลุ่มของ Khan และ Moon (สิงคโปร์) ทำงานต่อเนื่อง 3 ชิ้นที่ควรอ่านทั้งหมด:
- 2024 [18]: ทูน Florence-2 (VLM ขนาดเล็ก) ด้วยแบบเพียง 400 แผ่นที่ผู้เชี่ยวชาญ annotate ให้อ่าน GD&T (geometric dimensioning and tolerancing) ได้ F1 ดีกว่า GPT-4o และ Claude 3.5 Sonnet ถึง 52.40 จุด นี่คือหลักฐานตรงที่สุดว่า **โมเดลเล็กที่ทูนตรง domain ชนะโมเดลปิดตัวใหญ่** ในงานแบบนี้ และตรงกับข้อสรุปของเราจาก t01 ว่าการทูนได้ผล
- 2025 [19]: hybrid = YOLOv11-OBB (oriented bbox สำหรับข้อความเอียง) หาตำแหน่งก่อน แล้ว Donut อ่านในกรอบ บนชุด 1,367 แบบ ได้ precision 88.5%, recall 99.2%, F1 93.5%
- 2025-2026 [20]: ขยายเป็น 3 ขั้น multi-view โดยแยก VLM "อ่านตัวเลข" (F1 0.963) กับ "อ่านตัวอักษร" (F1 0.672) ออกจากกัน แล้วรวมเป็น JSON ให้ CAD ใช้ต่อ

สังเกตตัวเลข F1 ตัวเลข 0.963 กับ ตัวอักษร 0.672 นี่บอกว่าแม้ระบบที่ดีที่สุด การอ่าน "รหัส/ข้อความอิสระ" ยังยากกว่าการอ่านตัวเลขมาก ในแบบของเรา "2-DB12@0.15" มีทั้งสองแบบผสมกัน

**ขั้นที่ 3: benchmark สำหรับแบบ AEC โดยเฉพาะ (2026)**
- AECV-Bench [21]: นับ object บนผังพื้น 120 แผ่น + QA 192 ข้อ ผล: OCR 0.95, นับประตู/หน้าต่าง 0.40-0.55 สรุปว่า VLM ปัจจุบันเป็น "document assistant" ที่ยังขาด "drawing literacy"
- DrawingVQA [22]: แบบ "Issued for Construction" จริง 33 แผ่น QA 92 ข้อ วัด 7 มิติทางวิศวกรรม พบช่องว่างใหญ่ระหว่างโมเดลกับผู้เชี่ยวชาญ
- GDP.pdf [24]: โมเดลที่ดีที่สุดผ่าน 30.7%

ชุดข้อมูลเหล่านี้เล็ก (33-120 แผ่น) เพราะ annotate โดยผู้เชี่ยวชาญแพงมาก ซึ่งเป็นเหตุผลเดียวกับที่ dataset ของเรามีราว 1,000 ตัวอย่างต่อ fold และเป็นเหตุผลที่ต้องคุยเรื่อง synthetic data ในหัวข้อ 11.9

🎨 **ภาพที่จะวาดใน HTML:** กราฟแท่งแนวนอนสองสี เปรียบเทียบ "ความสามารถของ VLM" ตามประเภทงานบนแบบ จากตัวเลขในบทนี้: OCR ข้อความ 0.95 [21], อ่านตัวเลข GD&T 0.963 [20], อ่านตัวอักษร 0.672 [20], นับสัญลักษณ์ 0.40-0.55 [21], โจทย์เอกสารวิชาชีพรวม 0.307 [24] และแท่งสุดท้ายคือ recall ของเรา 0.282 (t01) และ 0.11 (t02 beam plan) วางแท่งของเราไว้ท้ายเพื่อให้เห็นว่าเรา "อยู่ในย่านเดียวกับที่โลกทำได้บนงานนับ" ไม่ใช่ห่างเป็นสิบเท่า มี tooltip ชี้ไปที่เลขอ้างอิง

## 11.6 สาย (e): ถอดปริมาณอัตโนมัติ (automated quantity takeoff) และ BIM จากแบบ 2D

นี่คือ "งานปลายทาง" ของเรา Constistant ต้องการปริมาณ ไม่ใช่ bbox

**ขั้นที่ 1: QTO จาก BIM ทำได้ดีแล้ว, จาก 2D ยังยาก**
Valinejadshoubi et al. 2024 [29] ใน Automation in Construction แสดงระบบ QTO ความแม่นสูงจาก BIM เพราะข้อมูลอยู่ในรูปโครงสร้างอยู่แล้ว ปัญหาคือบ้านพักอาศัยส่วนใหญ่ในไทย (และโครงการของเรา) มีแค่แบบ 2D ไม่มี BIM งานสาย "2D → BIM" จึงเป็นสะพานที่ทุกคนพยายามสร้าง

**ขั้นที่ 2: Handoff-H1 (2026) [25]: ระบบ QTO ที่ชนะนักประมาณราคามนุษย์**
นี่คืองานที่ใกล้เป้าหมายเราที่สุดในเชิงระบบ สถาปัตยกรรม 3 ชั้น: (1) CV model เฉพาะทางสกัด primitive (เส้น สัญลักษณ์ ข้อความ), (2) agent ที่มีเครื่องมือ (tool-using agents) ทำงานภาพเฉพาะจุด เช่น วัด ซูม นับ, (3) "project foundation" ที่เก็บความรู้ก่อสร้างเป็นลำดับชั้นเพื่อ ground การตัดสินใจ ทดสอบบนชุดแบบบ้าน 10 ชุด 2,009 รายการที่ตรวจแล้ว ได้คะแนนรวม 81.6% (coverage 86.1%, precision@25% 78.8%) ชนะ frontier LLM ที่ได้ 35-61% และชนะนักประมาณราคาอิสระที่ได้ 77.6%

ตัวเลข 35-61% ของ frontier LLM แบบใช้ตรง ๆ คือหลักฐานว่าโยนแบบทั้งหน้าให้ VLM ตัวใหญ่ที่สุดในโลกก็ยังไม่พอ ต้องมีโครงสร้างรอบ ๆ

**ขั้นที่ 3: ปัญหาเฉพาะของ "เหล็กเสริม"**
เราไม่พบงานที่ทำ rebar takeoff จากแบบ 2D ครบวงจรและตีพิมพ์ในวารสารหลักช่วง 2024-2026 (พบ preprint บน SSRN ของ Ying et al. 2025 ชื่อ "Automated Detection and Recognition of Steel Rebar Annotations in Engineering Drawings Using Deep Learning" แต่เข้าถึงบทคัดย่อเต็มไม่ได้ในขณะเขียน) นี่คือช่องว่างจริงในวงการ และเป็นข่าวดีสำหรับเราในแง่ว่าสิ่งที่ทำอยู่ยังไม่มีใครตอบให้

🎨 **ภาพที่จะวาดใน HTML:** แผนผัง 3 ชั้นของ Handoff-H1 วาดเป็นบล็อกซ้อนกัน คลิกแต่ละชั้นแล้วมีตัวอย่างว่า "ถ้าเป็นโปรเจกต์เรา ชั้นนี้คืออะไร" (ชั้น 1 = cv_scan.py + template matching, ชั้น 2 = VLM ที่ถูกเรียกเฉพาะ region, ชั้น 3 = กฎ คสล. เช่น คานต้องมีเสารับ, เหล็กล่างต้องมี) ด้านข้างเป็นกราฟแท่ง 81.6 / 77.6 / 35-61 เพื่อเน้นว่าโครงสร้างสำคัญกว่าขนาดโมเดล

## 11.7 สาย (f): hybrid pipeline กับ end-to-end VLM

ถึงตรงนี้เห็นสองค่ายชัดเจน

**ค่าย 1: hybrid** = detector (YOLO/DETR หรือ template matching) หาตำแหน่ง → OCR หรือ VLM เล็กอ่านในกรอบ → LLM/กฎประกอบเป็น JSON
ตัวอย่าง: Digitize-PID [8], Khan 2025 [19][20], Huang 2026 [23], Handoff-H1 [25], Zhu 2026 [10]

**ค่าย 2: end-to-end VLM** = ภาพทั้งหน้าเข้า JSON ออก
ตัวอย่าง: Donut/Nougat [13][14], Florence-2 ทูน [18], และ t01/t02 ของเรา

ข้อแลกเปลี่ยน อธิบายด้วยทฤษฎีจากบทก่อน ๆ

| ประเด็น | Hybrid | End-to-end VLM | ทฤษฎีที่อธิบาย |
|---|---|---|---|
| ความละเอียด | แต่ละขั้นเห็นภาพเต็มความละเอียดในกรอบเล็ก | ต้องย่อหรือ tile ทั้งหน้า | บทที่ 4: จำนวน visual token จำกัด |
| การนับ | detector นับได้ deterministic | LLM นับผิด วนซ้ำ | บทที่ 3: autoregressive ไม่มี "ตัวนับ" |
| ความหมาย/บริบท | ต้องออกแบบ schema เอง | เข้าใจข้อความอิสระได้ดี | บทที่ 4: language prior |
| ข้อมูลที่ต้องใช้ | detector ต้องการ bbox label (แพง) | ต้องการแค่ภาพ+JSON | บทที่ 10 |
| จุดล้มเหลว | error propagate ผ่านขั้น | ล้มเหลวแบบไม่บอกเหตุ (hallucinate) | บทที่ 8 |
| ตรวจสอบได้ | ทุกขั้นวัดแยกได้ | วัดได้แค่ปลายทาง | บทที่ 8 |
| ค่าใช้จ่าย/ความเร็ว | CV <1 วิ/หน้า, VLM เฉพาะจุด | VLM ทั้งหน้า ช้าและแพง | บทที่ 7 |

ข้อสังเกตจากตัวเลขในบทนี้: งานที่รายงาน F1 > 0.9 บนแบบวิศวกรรม [19][20][23] เป็น hybrid ทั้งหมด ส่วน end-to-end ที่รายงานสูงคืองานที่ "กรอบภาพเล็กและ output สั้น" (GD&T ต่อ view เดียว [18]) ยังไม่มีงานที่ end-to-end ทั้งหน้าผังคานแล้วได้ recall สูงตีพิมพ์ในช่วงที่สำรวจ

🎨 **ภาพที่จะวาดใน HTML:** flow chart สองแถวคู่ขนาน บนคือ hybrid (5 กล่อง) ล่างคือ end-to-end (2 กล่อง) แต่ละกล่องมีสไลเดอร์ "ความแม่นของขั้นนี้" 0-1 แถวบนคำนวณความแม่นรวมเป็นผลคูณ (เช่น 0.95 × 0.97 × 0.93 = 0.857) ผู้เรียนควรเห็นว่า hybrid ที่แต่ละขั้นดีมากก็ยังถูก "คูณลง" ส่วนแถวล่างมีสไลเดอร์เดียวแต่มีปุ่มสุ่ม "hallucination" ที่ทำให้ค่ากระโดดขึ้นลงคาดเดาไม่ได้ ข้อความสรุป: hybrid แลกความแม่นสูงสุดกับความคาดเดาได้

```python
# ความแม่นรวมของท่อหลายขั้น = ผลคูณ (สมมติ error อิสระ)
stages = {"detector":0.95, "crop/ocr":0.97, "assemble":0.93}
total = 1.0
for k,v in stages.items():
    total *= v
    print(f"หลังขั้น {k:10s}: {total:.3f}")
# ถ้า detector ลดเหลือ 0.80 (ไม่มี domain data) จะเหลือ?
print("ถ้า detector=0.80:", round(0.80*0.97*0.93,3))
```

## 11.8 สาย (g): grounding และการตรวจสอบคำตอบ

ปัญหาใหญ่ของ VLM คือ "พูดได้ แต่พิสูจน์ไม่ได้" วิธีแก้ที่วงการใช้คือบังคับให้โมเดล **ชี้** ว่าเห็นสิ่งที่ตอบตรงไหน (grounding) แล้วใช้ CV ตรวจ

**ขั้นที่ 1: VLM ที่พ่นพิกัดได้**
Shikra (2023) [32] เป็นงานแรก ๆ ที่สอน VLM ให้อ่านและเขียนพิกัดเป็นข้อความธรรมดา Qwen2.5-VL [30] ทำ grounding ด้วย "พิกัดสัมบูรณ์" (absolute coordinate) ตามพิกเซลจริงของภาพที่ป้อน และ Qwen3-VL [31] รองรับทั้ง box และ point (README ระบุว่าใช้พิกัดสัมพัทธ์) ความหมายสำหรับเราคือ ถ้าให้โมเดลตอบ `{"name":"B2","bbox":[x1,y1,x2,y2]}` เราตรวจได้ทันทีว่ากรอบนั้นมีเส้นคานอยู่จริงหรือไม่ด้วย cv2

**ขั้นที่ 2: การตรวจด้วย IoU**
$$\text{IoU}(A,B) = \frac{|A \cap B|}{|A \cup B|}$$
$A$ = กรอบที่ VLM บอก, $B$ = กรอบที่ template matching เจอ ถ้า IoU > 0.5 ถือว่าตรงกัน

ตัวอย่างตัวเลข: $A=[100,100,200,150]$ (กว้าง 100 สูง 50 พื้นที่ 5,000), $B=[120,100,220,150]$ (พื้นที่ 5,000) ส่วนซ้อน = กว้าง 80 × สูง 50 = 4,000; ส่วนรวม = 5,000 + 5,000 − 4,000 = 6,000; IoU = 4,000/6,000 = 0.667 ผ่าน

**ขั้นที่ 3: VLM เป็นกรรมการ (VLM-as-judge)**
Ghosh 2025 [33] กลับด้าน: ให้ detector หา แล้วให้ VLM ตัดสินว่า detection ถูกไหม ใช้ได้กับ P&ID และเป็นแนวคิดที่เราใช้ได้ทันทีเพื่อลด false positive จาก template matching ที่ threshold 0.60-0.70

**ขั้นที่ 4: self-consistency [34]**
Wang et al. 2022: สุ่มคำตอบหลายชุด (temperature > 0) แล้วเลือกคำตอบที่ปรากฏบ่อยสุด สำหรับการนับ ให้ VLM นับ 5 ครั้ง ถ้าได้ 12, 12, 13, 12, 11 ตอบ 12 และถ้ากระจายมาก (5, 12, 20) แปลว่าโมเดลไม่มั่นใจ ควรส่งให้คนดู นี่คือวิธีเปลี่ยน "ความไม่นิ่ง" ของ VLM (ที่เราบ่นในบทที่ 7) ให้กลายเป็นสัญญาณความมั่นใจ

**ขั้นที่ 5: วัด hallucination อย่างเป็นระบบ**
POPE (2023) [35] วัด object hallucination ด้วยคำถาม yes/no ว่า "มี X ในภาพไหม" ที่สุ่มทั้ง X ที่มีจริงและไม่มี เราทำแบบเดียวกันได้: ถามว่า "มีคาน B7 ในหน้านี้ไหม" ทั้งที่ B7 ไม่มี แล้วนับว่าโมเดลตอบ "มี" กี่ครั้ง Lilian Weng [43] สรุปวิธีตรวจและลด hallucination ไว้ครบสำหรับผู้ต้องการอ่านต่อ

🎨 **ภาพที่จะวาดใน HTML:** ภาพผังคานย่อ มีกรอบสีน้ำเงิน (VLM ตอบ) ที่ลากย้ายได้ และกรอบสีเขียว (CV เจอ) อยู่กับที่ ตัวเลข IoU อัปเดตสด พื้นที่ซ้อนทับระบายสี เมื่อ IoU ต่ำกว่าสไลเดอร์ threshold กรอบน้ำเงินกลายเป็นแดงพร้อมป้าย "ต้องให้คนตรวจ" ด้านล่างมี mini-panel self-consistency: กดปุ่ม "ให้โมเดลนับ 5 ครั้ง" แล้วโชว์ histogram ของคำตอบ

```python
import numpy as np
def iou(a,b):
    ix1,iy1 = max(a[0],b[0]), max(a[1],b[1])
    ix2,iy2 = min(a[2],b[2]), min(a[3],b[3])
    inter = max(0,ix2-ix1)*max(0,iy2-iy1)
    area = lambda r:(r[2]-r[0])*(r[3]-r[1])
    return inter/(area(a)+area(b)-inter)
print("IoU =", round(iou([100,100,200,150],[120,100,220,150]),3))   # 0.667
# self-consistency: โหวตคำตอบการนับ
votes = [12,12,13,12,11]
vals,cnt = np.unique(votes, return_counts=True)
print("ตอบ", vals[cnt.argmax()], "| ความมั่นใจ", cnt.max()/len(votes))
```

## 11.9 สาย (h): synthetic data และ domain randomization

**ขั้นที่ 1: ทำไมต้องสร้างข้อมูลเอง**
dataset ของเรา ~1,000 ตัวอย่างต่อ fold ได้จากการที่คนแก้ JSON ทีละบ้าน แพงและช้า ในขณะที่ผังคาน-เสาเป็นสิ่งที่ "สร้างด้วยกฎได้": สุ่มกริด 3-6 ช่อง, สุ่มระยะ 3-5 ม., วางเสาที่จุดตัด, วางคานระหว่างเสา, สุ่มชื่อ B1-B9, ตั้งขนาด 0.20×0.40 แล้ว render เป็นภาพด้วย matplotlib หรือ cv2 พร้อม JSON ที่ถูกต้อง 100% เพราะเราเป็นคนสร้าง

**ขั้นที่ 2: domain randomization (Tobin et al., 2017) [36]**
แนวคิดจากหุ่นยนต์: ถ้า synthetic ไม่เหมือนของจริง ให้สุ่มทุกอย่างที่ไม่สำคัญ (สี, แสง, พื้นหลัง) ให้หลากหลายจนของจริงกลายเป็น "แค่อีกหนึ่ง variation" สำหรับแบบ: สุ่มความหนาเส้น, ฟอนต์, ขนาดตัวอักษร, เอียงเล็กน้อย, noise ของสแกน, สัญลักษณ์เสาแบบทึบ/กลวง, มีหรือไม่มี dimension line

**ขั้นที่ 3: หลักฐานว่าใช้ได้กับแบบ**
- Donut [13] pre-train ด้วยเอกสาร synthetic ก่อนทูนของจริง
- SynthPID (2026) [9] สร้าง P&ID synthetic 665 แผ่น โดย "ยืม topology จากแบบจริง" แทนการวางสัญลักษณ์สุ่ม ได้ edge mAP 63.8% โดยไม่เห็นภาพจริงเลย ห่างจาก oracle ที่เทรนบนของจริงเพียง 8 จุด และพบว่าผลอิ่มตัวหลัง ~400 ภาพเพราะ "ความหลากหลายของ seed" เป็นตัวจำกัด ไม่ใช่จำนวนภาพ
- ArchCAD-400K [5] ใช้ annotation engine อัตโนมัติสร้าง label 413,062 chunk
- OmniMech (2026) [37] จับคู่แบบ 2D มีมิติกว่า 251,000 แผ่นกับโมเดล CAD ต้นทาง เพื่อวัดว่า VLM สร้าง CAD กลับได้ไหม

บทเรียนจาก SynthPID ตรงกับเรามาก: อย่าสุ่มมั่ว ให้สุ่มจาก "ผังจริง" ที่มีอยู่ (เช่น ยืมกริดจากบ้าน 20 หลังที่ annotate แล้ว แล้วสุ่มชื่อ/ขนาด/สไตล์ทับ) ความหลากหลายของโครงสำคัญกว่าจำนวน

**ขั้นที่ 4: ข้อควรระวัง (distribution shift อีกแบบ)**
synthetic ที่สะอาดเกินไปทำให้โมเดลเก่งบน synthetic แต่ตกบนของจริง (sim-to-real gap) ต้องวัดบนของจริงเสมอ และ leave-one-out ต้องแยกบ้านจริงออกจาก train ทั้งหมด ห้ามให้ synthetic ที่ยืมกริดจากบ้าน X ไปอยู่ใน train แล้ววัดบนบ้าน X (data leakage, บทที่ 8)

🎨 **ภาพที่จะวาดใน HTML:** ปุ่ม "สุ่มผังใหม่" สร้างผังคาน-เสาแบบสุ่ม (กริด, ระยะ, ชื่อคาน) วาดสดบน canvas พร้อม JSON ทางขวาที่อัปเดตพร้อมกัน มีสไลเดอร์ domain randomization 3 ตัว: ความหนาเส้น, noise, ขนาดฟอนต์ เมื่อลากจะเห็นภาพเปลี่ยนแต่ JSON ไม่เปลี่ยน (นี่คือประเด็น: label ถูกเสมอ) และตัวนับ "สร้างแล้ว N ตัวอย่างใน T วินาที"

```python
# สร้างผังคานสังเคราะห์ + JSON คู่ (ย่อสุด)
import numpy as np, cv2, json, random
def synth(seed):
    random.seed(seed); img = np.full((600,800),255,np.uint8)
    xs = np.cumsum([80]+[random.randint(120,200) for _ in range(3)])
    ys = np.cumsum([80]+[random.randint(120,200) for _ in range(2)])
    beams=[]; t=random.randint(1,3)
    for y in ys:
        for i in range(len(xs)-1):
            n=f"B{random.randint(1,4)}"; cv2.line(img,(xs[i],y),(xs[i+1],y),0,t)
            cv2.putText(img,n,((xs[i]+xs[i+1])//2-10,y-6),cv2.FONT_HERSHEY_SIMPLEX,0.4,0,1)
            beams.append({"name":n,"from":[int(xs[i]),int(y)],"to":[int(xs[i+1]),int(y)]})
    for x in xs:
        for y in ys: cv2.rectangle(img,(x-6,y-6),(x+6,y+6),0,-1)
    return img, {"beams":beams,"columns":len(xs)*len(ys)}
img,gt = synth(7); cv2.imwrite("synth_7.png",img)
print(json.dumps(gt,ensure_ascii=False)[:120], "...", "columns:",gt["columns"])
```

## 11.10 สาย (i): ความละเอียดและการแบ่งภาพ (tiling) สำหรับภาพใหญ่

นี่คือหัวใจของบั๊กข้อ 1 และข้อ 6 ของเรา จึงต้องเข้าใจให้ลึก

**ขั้นที่ 1: ต้นทุนของความละเอียดใน ViT**
ViT ตัดภาพเป็น patch ขนาด $p \times p$ พิกเซล จำนวน token ≈ $(W/p)(H/p)$ สำหรับ Qwen-VL ที่ patch 14 px และรวม 2×2 patch เป็น 1 token (spatial merge):

$$N_{\text{token}} \approx \frac{W \cdot H}{(14 \times 2)^2} = \frac{W \cdot H}{784}$$

ภาพ 3309×2339 → 7,739,751 / 784 ≈ 9,872 token ก่อนที่จะเขียน JSON แม้แต่ตัวเดียว ในขณะที่ max_length ของ t02 คือ 10-13k token นี่คือเหตุผลเชิงตัวเลขว่าทำไมท่อของเราถึงย่อภาพ (แล้วย่อมากเกินไป)

**ขั้นที่ 2: สามแนวทางของวงการ**
1. **ตัดเป็นช่องคงที่ (UReader [38], Monkey [39])**: UReader เสนอ shape-adaptive cropping เลือกจำนวนช่องตามสัดส่วนภาพ แล้วป้อนแต่ละช่องผ่าน vision encoder ความละเอียดต่ำที่ freeze ไว้ ทูนเพียง 1.2% ของพารามิเตอร์ Monkey ตัดภาพถึง 1344×896 เป็นช่อง 448×448 ให้ตรงกับที่ encoder ถูกเทรนมา จุดร่วม: ทุกช่องต้องมี "ภาพรวมย่อ" (global view) แนบไปด้วย ไม่งั้นโมเดลไม่รู้ว่าช่องนี้อยู่ตรงไหนของหน้า
2. **บีบ token หลัง encoder (DocOwl 1.5 [40])**: H-Reducer รวม token แนวนอนเพื่อคงข้อมูล layout แต่ลดความยาว
3. **dynamic resolution ตั้งแต่ต้น (Qwen2.5-VL [30], Qwen3-VL [31])**: ViT ที่รับภาพขนาดใดก็ได้ พร้อม window attention ให้ผู้ใช้ตั้ง min_pixels/max_pixels เอง README ของ Qwen3-VL แนะนำ 256-1280 token ต่อภาพสำหรับงานทั่วไป ซึ่ง "ไม่พอ" สำหรับแบบ A1 ทั้งแผ่น แต่พอสำหรับ 1 ช่องที่ตัดมา

**ขั้นที่ 3: SAHI [41]: tiling สำหรับ detector**
สำหรับฝั่ง CV/detector มีสูตรสำเร็จชื่อ SAHI: ตัดภาพเป็นช่องซ้อนกัน (overlap 10-20%) รัน detector ทุกช่อง แปลงพิกัดกลับ แล้ว NMS รวม ได้ผลดีมากกับ object เล็กในภาพใหญ่ CADSpotting [6] ใช้หลักการเดียวกัน (sliding window + weighted voting + NMS) กับแบบ CAD 1,000 ตร.ม.

**ขั้นที่ 4: ปัญหาเฉพาะของแบบเมื่อ tile**
คานยาวถูกตัดครึ่งอยู่สองช่อง ชื่อคานอยู่ช่องหนึ่ง เส้นอยู่อีกช่อง วิธีแก้ที่วงการใช้: (ก) overlap พอที่ข้อความไม่ถูกตัด (≥ ความกว้างข้อความที่ยาวสุด), (ข) ให้ global view ไปด้วย, (ค) ประกอบผลหลัง tile ด้วยกฎ (คานสองชิ้นที่ collinear และชื่อเดียวกัน = คานเดียว) ซึ่งเป็นสิ่งที่ MORPH_CLOSE + findContours ใน cv_scan.py ของเราทำอยู่แล้วในระดับพิกเซล

**ขั้นที่ 5: ทางเลือกใหม่ (2026): อย่าเพิ่ง "อ่าน" ให้ "ค้น" ก่อน**
Xu 2026 [42] เสนอ Deferred Visual Ingestion: อย่าให้ VLM อ่านทุกหน้าตอน index ให้ใช้โครงสร้างเอกสารทำ index แล้วค่อยเรียก VLM เฉพาะส่วนที่คำถามชี้ไป ได้ 65.6% บนแบบสะพาน เทียบ 24.3% ของวิธีอ่านทุกอย่างล่วงหน้า สำหรับเราคือ pass0 classify หน้าของ t03 นั่นเอง แต่ทำให้ละเอียดลงถึงระดับ region

🎨 **ภาพที่จะวาดใน HTML:** ผังคานเต็มหน้า มีสไลเดอร์ "ขนาดช่อง (px)" และ "overlap (%)" วาดกริดของช่องทับภาพ นับจำนวนช่องและ token รวม (ช่อง × token/ช่อง + global view) แสดงสด ไฮไลต์คานที่ถูกตัดข้ามช่องเป็นสีส้ม เมื่อเพิ่ม overlap คานส้มลดลงแต่ token เพิ่ม ผู้เรียนควรหา "จุดที่ token ≤ งบ (เช่น 8,000) แต่ไม่มีคานส้ม"

```python
# งบ token กับการ tile: กี่ช่อง, overlap เท่าไร
W,H = 3309,2339
def plan(tile, overlap):
    step = int(tile*(1-overlap))
    nx = -(-(W-tile)//step)+1; ny = -(-(H-tile)//step)+1
    tok_tile = (tile*tile)//784
    tok_global = (1024*724)//784           # ภาพรวมย่อด้านยาว 1024
    return nx*ny, nx*ny*tok_tile + tok_global
for tile in [1344, 1024, 896]:
    for ov in [0.0, 0.15, 0.30]:
        n,t = plan(tile,ov); print(f"tile {tile} overlap {ov:.2f}: {n:2d} ช่อง, ~{t:,} token")
```

## 11.11 สาย (j): benchmark ที่เราควรสร้างเอง

benchmark สาธารณะ [21][22][24] มีแบบ 33-120 แผ่น เป็นแบบต่างประเทศ ไม่มีเหล็กเสริมแบบไทย และวัดคนละอย่างกับที่ Constistant ต้องการ เราต้องมีของตัวเอง หลักการออกแบบจากบทที่ 8 และจากงานที่อ่านมา:

1. **แยกระดับความยาก (multi-depth)** ตาม DrawingVQA [22]: ระดับ 1 อ่านข้อความ (ชื่อคาน, ขนาด), ระดับ 2 นับ (มี B2 กี่ตัว), ระดับ 3 สัมพันธ์ (B2 อยู่ระหว่างกริดใด), ระดับ 4 คำนวณ (ปริมาณเหล็กรวม) รายงานแยกทุกระดับ เพราะโมเดลอาจได้ 0.95 ระดับ 1 แต่ 0.3 ระดับ 3 แบบเดียวกับ AECV-Bench [21]
2. **มี negative case** ตาม POPE [35]: ถามถึงคานที่ไม่มี เพื่อวัด hallucination แยกจาก recall
3. **แยกตามแหล่งที่มา**: PDF vector กับ PDF สแกน, บ้าน 1 ชั้นกับ 3 ชั้น, สำนักงานออกแบบต่างกัน เพราะ distribution shift ระหว่างสำนักงานออกแบบอาจใหญ่กว่าระหว่างบ้าน
4. **freeze test set** และห้ามดูตอนพัฒนา ใช้ leave-one-out หรือ k-fold ตามที่ t05 ทำ แต่ต้องมี "held-out บ้าน" ที่ไม่เคยแตะเลยสัก 3-5 หลังไว้วัดครั้งสุดท้าย
5. **วัดสิ่งที่ Constistant ใช้จริง**: ปริมาณคอนกรีต (ลบ.ม.) และเหล็ก (กก.) ต่อบ้าน คลาดเคลื่อนกี่ % เทียบกับที่วิศวกรถอด นี่คือตัวเลขที่ผู้ใช้เข้าใจ และเป็นตัวเลขที่ Handoff-H1 [25] เลือกใช้ (precision@25%)
6. **บันทึก seed, เวอร์ชันโมเดล, quantization, sampling params ทุกครั้ง** (บั๊กข้อ 2, 3, 5 ของเราเกิดเพราะไม่บันทึก)

🎨 **ภาพที่จะวาดใน HTML:** ตาราง scorecard 4 ระดับ × 3 แหล่งที่มา (vector/scan/สำนักงาน B) ช่องละหนึ่งค่า สีเขียว-เหลือง-แดง ผู้เรียนกรอกผลจากรอบทูนสมมติ 2 รอบแล้วกด "เปรียบเทียบ" ตารางแสดงลูกศรขึ้น/ลงต่อช่อง เพื่อฝึกนิสัย "อย่าดูตัวเลขเดียว"

## 11.12 เชื่อมกับงานของเรา

ไล่ตามบั๊กและรอบทูน ว่าทฤษฎีในบทนี้อธิบายอย่างไร

- **บั๊กข้อ 1 (train 512 px, infer 3,796 token)**: หัวข้อ 11.1 และ 11.10 แสดงว่าตัวอักษรที่ 512 px สูง ~2 px โมเดลจึงเรียนรู้ที่จะ "เดาจากภาษา" ไม่ใช่อ่านจากภาพ พอ inference ให้ภาพชัด โมเดลก็ไม่เคยฝึกใช้ข้อมูลนั้น การแก้ที่ถูกคือทำให้ train และ infer เห็นความละเอียดเดียวกัน หรือดีกว่านั้นคือ tile ทั้งสองฝั่งด้วยวิธีเดียวกัน (UReader/Monkey [38][39])
- **บั๊กข้อ 4 (greedy วน B2)**: หัวข้อ 11.7 อธิบายว่า autoregressive decoder ไม่มี "ตัวนับ" การนับ 80 คานด้วยการพิมพ์ทีละตัวคือการเดินบนเชือกยาว 80 ก้าว วิธีของวงการคือให้ detector นับ (deterministic) แล้วให้ VLM อ่านทีละกรอบ [19][23] ซึ่ง xgrammar ที่เราใช้แก้ได้แค่ "รูปแบบ" ไม่ได้แก้ "จำนวน"
- **t02 beam plan recall 11%**: ตรงกับ AECV-Bench [21] ที่นับสัญลักษณ์ได้ 0.40-0.55 บนผังพื้นซึ่งง่ายกว่าผังคานมาก และตรงกับ frontier LLM ที่ได้ 35-61% ใน Handoff-H1 [25] เราไม่ได้แย่ผิดปกติ เราเจอกำแพงเดียวกับทุกคน
- **t03 แยก 4 pass**: คือการเดินไปทาง hybrid โดยไม่รู้ตัว pass0 classify = Deferred Visual Ingestion [42], pass3 วัดจากกริด = การอ่าน "ระบบพิกัด" ก่อน (11.1 ขั้นที่ 4)
- **tools/cv_scan.py, pattern_recognition.py**: template matching ที่ threshold 0.60-0.70 + multi-scale + greedy NMS คือ detector ยุคก่อน deep learning มันคือ "ชั้น 1" ของ Handoff-H1 [25] ที่เรามีอยู่แล้ว สิ่งที่ยังไม่มีคือชั้น 3 (กฎ) และการเอา VLM มาเป็น judge [33] ของผล CV
- **บั๊กข้อ 2, 3 (adapter ไม่ merge, Q4_K_M ไม่วัดซ้ำ)**: หัวข้อ 11.11 ข้อ 6 คือคำตอบ benchmark ที่ดีต้องบันทึก artifact ทุกชิ้นที่ถูกวัด
- **t04 InternVL3 พังจาก crop_to_patches**: นี่คือ tiling (11.10) ที่ config ผิด InternVL ใช้ dynamic tiling 448×448 หลายช่อง + thumbnail ถ้าปิดหรือตั้งผิด โมเดลจะเห็นภาพย่อเดียว เท่ากับบั๊กข้อ 1 ในร่างใหม่

## 11.13 ระดับนักวิจัย: คำถามที่ยังเปิดอยู่

1. **detector-first หรือ VLM-first?** ผลปี 2025-2026 เอียงไป hybrid [19][20][23][25] แต่ Liu & Liu 2026 ("Learning to Ground Before Reading", arXiv 2608.29268 พบจากการค้น arXiv ยังไม่ได้ตรวจเนื้อหาเต็ม) อ้างว่า VLM ขนาดกะทัดรัดตัวเดียว parse แบบ PCB ทั้งหน้าได้โดยไม่ต้องมี detector หากทำได้จริงกับแบบโครงสร้าง ข้อแลกเปลี่ยนในตาราง 11.7 จะเปลี่ยน คำถามวิจัยคือ: "ground before read" ต้องการข้อมูล bbox มากแค่ไหน และ scale ไปภาพ 8 MP ได้ไหม
2. **การนับใน autoregressive model**: ยังไม่มีคำตอบว่าทำไม VLM นับได้แย่ทั้งที่อ่านได้ดี [21][24] สมมติฐานที่เถียงกัน: (ก) visual token ถูกบีบจนสัญลักษณ์ซ้ำ ๆ รวมเป็นก้อนเดียว, (ข) language prior ทำให้เลือกตัวเลข "ที่พบบ่อย", (ค) ขาด training signal ที่บังคับให้แจงรายการทีละชิ้นพร้อมพิกัด งาน grounding [30][32] เป็นความพยายามแก้ข้อ (ค)
3. **synthetic data อิ่มตัวเมื่อไร**: SynthPID [9] เห็น plateau ที่ ~400 ภาพเพราะ seed ไม่หลากหลาย ยังไม่มีทฤษฎีบอกว่าต้องมี "โครงจริง" กี่แบบถึงจะพอ และ sim-to-real gap ของแบบ (ที่ไม่มีแสง/เงา) เล็กกว่าของภาพถ่ายจริงหรือไม่
4. **vector หรือ raster**: สาย panoptic symbol spotting [3][5][6][7] อ่าน vector โดยตรงและได้ผลดี แต่แบบในโลกจริงมาเป็น PDF ที่บางส่วนยัง vector บางส่วนสแกน ยังไม่มีงานที่รวมสองโลก (ดึง vector เมื่อมี, rasterize เมื่อไม่มี) แล้วรายงานผลบนชุดเดียวกัน
5. **benchmark ที่วัด "ปริมาณ" ไม่ใช่ "bbox"**: Handoff-H1 [25] เป็นงานแรก ๆ ที่วัดผลด้วยตัวเลขที่นักประมาณราคาใช้ วงการยังไม่มีมาตรฐานร่วมว่าจะ credit "นับถูกแต่ขนาดผิด" อย่างไร ซึ่งกระทบ element recall ของเราโดยตรง

## 11.14 ถ้าออกแบบระบบใหม่ด้วยความรู้ทั้งหมดในหลักสูตรนี้

สามทางเลือก ไม่ฟันธง มะขามเลือกเอง

**ทางเลือก A: Hybrid เต็มรูป (CV/detector นำ, VLM อ่านเฉพาะกรอบ)**
- ท่อ: pass0 classify หน้า → ตรวจกริดและมาตราส่วนด้วย CV (เส้นตรงยาว + วงกลมมีตัวอักษร) → template matching / YOLO เล็กหาเสาและปลายคาน → tile รอบแต่ละ object แล้วให้ VLM (Qwen3-VL 8B ทูน LoRA) อ่านชื่อ/ขนาด/เหล็กในกรอบเดียว → กฎประกอบ (คานต้องมีเสาสองปลาย, ชื่อซ้ำต้องขนาดเดียวกัน) → JSON
- ข้อดี: การนับ deterministic, ทุกขั้นวัดแยกได้, VLM เห็นภาพความละเอียดเต็มเสมอ (ไม่มีบั๊กข้อ 1 อีก), ต้นทุน VLM ต่ำเพราะเรียกเฉพาะกรอบ, สอดคล้องกับผลที่รายงาน F1 > 0.9 [19][20][23]
- ข้อเสีย: ต้อง annotate bbox สำหรับ detector (แพงกว่า JSON), error คูณกันหลายขั้น, ต้องดูแล code หลายส่วน, สัญลักษณ์ที่ไม่เคยเห็น (สำนักงานออกแบบใหม่) ทำ detector พังก่อน VLM
- เหมาะเมื่อ: แบบมาจากสำนักงานไม่กี่แห่งที่สัญลักษณ์คงที่ และเราต้องการอธิบายได้ว่าผิดตรงไหน

**ทางเลือก B: End-to-end VLM ที่ทำ tiling และ grounding ถูกต้อง**
- ท่อ: ภาพเต็ม tile ตามสูตร 11.10 (ช่อง ~1024 px, overlap 20%, global view) ทั้งตอนเทรนและ infer ด้วย collator เดียวกัน → VLM ทูนให้ตอบ JSON พร้อม bbox ทุกรายการ (grounded output) → CV ตรวจ IoU กับเส้น/สัญลักษณ์ที่ template matching เจอ → self-consistency 3-5 ครั้งสำหรับการนับ → รวมข้ามช่องด้วยกฎ collinear
- ข้อดี: dataset ที่มีอยู่ (ภาพ + JSON) ใช้ได้ทันทีถ้าเพิ่ม bbox, ระบบชิ้นเดียว, รับสัญลักษณ์แปลกได้ดีกว่าเพราะพึ่ง language prior, ขยายไปอ่านหมายเหตุ/ข้อความอิสระได้
- ข้อเสีย: ต้องการ bbox ใน ground truth เหมือนกัน (ไม่ได้ประหยัดเท่าที่คิด), การนับยังพึ่ง VLM (แม้มี self-consistency ช่วย), token แพงมาก (10-20 ช่อง × ~1,300 token), ทูนยากกว่า (t01-t05 คือหลักฐาน), ยังไม่มี paper ที่ทำแบบนี้บนผังคานทั้งหน้าแล้วได้ recall สูง
- เหมาะเมื่อ: แบบหลากหลายมาก และเรายอมจ่าย GPU มากกว่าเพื่อลด code ที่ต้องดูแล

**ทางเลือก C: ผสมแบบ "CV เป็นกรรมการ, VLM เป็นผู้เล่น" + synthetic data หนัก**
- ท่อ: สร้าง synthetic ผังคาน-เสาแบบ SynthPID [9] (ยืมกริดจากบ้านจริง 20-30 หลัง, สุ่มสไตล์) 5,000-10,000 ตัวอย่าง pre-tune VLM บน synthetic ก่อน แล้ว fine-tune ต่อบนของจริง ~1,000 → infer แบบ B (tile + grounded) → CV template matching รันขนานเป็น "second opinion" → ที่ไหน VLM กับ CV ไม่ตรง (IoU < 0.5 หรือจำนวนต่างเกิน 10%) ส่งให้คนดูใน review.html เฉพาะจุดนั้น
- ข้อดี: แก้ปัญหา data น้อยที่รากด้วย synthetic, ใช้ทรัพยากรที่มีอยู่แล้วทั้งหมด (cv_scan.py, review.html, Label Studio), คนตรวจเฉพาะจุดที่ระบบไม่มั่นใจ (active learning โดยธรรมชาติ), ทุกครั้งที่คนแก้ ได้ข้อมูลจริงเพิ่ม
- ข้อเสีย: sim-to-real gap ของ synthetic ต้องวัดจริง ๆ ก่อนเชื่อ, ระบบสองทางที่ต้องเปรียบเทียบผลกันเพิ่มความซับซ้อนตอน debug, ยังไม่แก้ปัญหาการนับที่ต้นเหตุ แค่จับได้เมื่อผิด
- เหมาะเมื่อ: เราต้องการเดินหน้าเร็วด้วยของที่มี และยอมรับว่ามีคนอยู่ในลูปอีกระยะ

ทั้งสามทางมีสิ่งร่วมกันที่ไม่ควรเถียง: (1) train และ infer ต้องเห็นภาพแบบเดียวกัน, (2) ต้องมี bbox ในคำตอบเพื่อให้ตรวจได้, (3) ต้องมีกฎวิศวกรรมเป็นด่านสุดท้าย, (4) benchmark ของตัวเองแบบ 11.11 ต้องมีก่อนเริ่มทูนรอบใหม่

## สรุปบทนี้ใน 5 บรรทัด

1. แบบก่อสร้างคือเส้น + สัญลักษณ์ตามข้อตกลง + ข้อความเล็ก + ระบบพิกัดสองชั้น บนภาพ 8 MP ที่หนาแน่น ต่างจากภาพถ่ายทุกมิติ โมเดลทั่วไปจึงอ่านได้แต่นับไม่ได้ [21][24]
2. งานที่รายงาน F1 > 0.9 บนแบบวิศวกรรมในปี 2025-2026 เป็น hybrid (detector หาที่, VLM/Donut อ่านในกรอบ, กฎประกอบ) ทั้งหมด [19][20][23][25]
3. ความละเอียดต้องเท่ากันระหว่าง train กับ infer และภาพใหญ่ต้อง tile พร้อม global view [38][39][30] บั๊กข้อ 1 และ t04 ของเราคือการละเมิดข้อนี้
4. ให้ VLM ตอบพร้อม bbox แล้วใช้ CV ตรวจ IoU, ใช้ self-consistency กับการนับ, วัด hallucination ด้วย negative case [30][32][34][35]
5. ข้อมูลน้อยแก้ด้วย synthetic ที่ยืมโครงจากของจริง [9][36] และต้องมี benchmark 4 ระดับของตัวเองก่อนทูนรอบใหม่ ไม่ว่าจะเลือกทาง A, B หรือ C
