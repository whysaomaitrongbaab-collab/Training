## 5.0 คำถามเปิด (ผูกกับงานจริงของเรา)

ตอนรอบทูน t02 เราตั้ง `max_length` ไว้ประมาณ 10k-13k token ต่อตัวอย่าง แล้วพบว่าหน้าแบบคานบางหน้าถูก "ตัดท้าย" ทั้งที่ JSON ของหน้านั้นดูไม่ยาวนัก ในสายตาคน JSON หน้าหนึ่งอาจมีแค่ 3,000 ตัวอักษร แต่ตัวนับ token บอกว่า 1,800 token และภาพหนึ่งภาพกิน 3,796 token อีกต่างหาก

คำถามที่มะขามถามตอนนั้นคือ "token คืออะไร ทำไมภาษาไทยถึงแพงกว่าอังกฤษ และทำไมโมเดลพ่น JSON ยาว ๆ แล้วช้าลงเรื่อย ๆ ทั้งที่ GPU ยังว่าง"

คำตอบทั้งหมดอยู่ในโครงสร้างของ Transformer เอง บทนี้จะไล่จากตัวอักษร → token → เวกเตอร์ → attention → โมเดลทั้งก้อน → เหตุผลที่โมเดลใหญ่ขึ้นแล้วเก่งขึ้น → เหตุผลที่ MoE ทำให้ OOM ทั้งที่ "active แค่ 3B"

## 5.1 Tokenization: หั่นข้อความให้เป็นชิ้นที่นับได้

### 5.1.1 ทำไมไม่ใช้ตัวอักษร หรือคำ

โมเดลรับได้เฉพาะตัวเลข ดังนั้นต้องมี "พจนานุกรม" ที่แปลงข้อความเป็นลำดับของเลขจำนวนเต็ม ทางเลือกสุดขั้วมีสองทาง

- ใช้ตัวอักษร (character) เป็นหน่วย: พจนานุกรมเล็กมาก แต่ประโยคหนึ่งยาวหลายร้อยหน่วย โมเดลต้องเรียนรู้เองว่า "ค-า-น" ประกอบเป็นคำว่าคาน
- ใช้คำ (word) เป็นหน่วย: สั้นดี แต่พจนานุกรมระเบิด และเจอคำใหม่ (เช่น "DB16@0.15") ก็ไม่รู้จัก

ทางสายกลางคือ **subword**: หั่นคำที่พบบ่อยเป็นชิ้นเดียว หั่นคำหายากเป็นหลายชิ้น เทียบกับงานถอดปริมาณ: เหล็กเสริมมาตรฐาน DB12, DB16 เราจำเป็นหน่วยเดียว แต่เหล็กขนาดแปลก ๆ เราต้องแยกอ่านทีละหลัก

### 5.1.2 Byte Pair Encoding (BPE)

BPE ที่ใช้ใน LLM มาจากงานแปลภาษาของ Sennrich และคณะ ปี 2015 [1] แนวคิดคือ

1. เริ่มจากพจนานุกรมที่มีแค่ byte 256 ตัว
2. นับคู่ token ที่ปรากฏติดกันบ่อยที่สุดในคลังข้อความ
3. รวมคู่นั้นเป็น token ใหม่ เพิ่มลงพจนานุกรม
4. ทำซ้ำจนพจนานุกรมมีขนาดตามที่ต้องการ (Qwen ใช้ 151,646 token [16])

ผลคือ "ภาษาที่พบบ่อยในคลัง" จะได้ token ยาว ๆ ส่วน "ภาษาที่พบน้อย" จะถูกหั่นละเอียด **นี่คือเหตุผลที่ภาษาไทยแพง** ไม่ใช่เพราะภาษาไทยยากกว่า แต่เพราะตอนสร้างพจนานุกรม ข้อความไทยมีสัดส่วนน้อย คู่ตัวอักษรไทยจึงไม่ค่อยได้ถูกรวม

SentencePiece [2] เป็นเครื่องมืออีกตัวที่ทำงานคล้ายกันแต่ไม่ต้องการช่องว่างคั่นคำ (ภาษาไทยและญี่ปุ่นไม่มีช่องว่าง) โดยมองช่องว่างเป็นตัวอักษรธรรมดา

### 5.1.3 ตัวอย่างจริงจาก tokenizer ของ Qwen3

ผลด้านล่างรันจริงด้วย tokenizer ของ `Qwen/Qwen3-8B` (พจนานุกรม 151,669 รายการรวม special token)

| ข้อความ | ตัวอักษร | token | ตัวอักษร/token |
|---|---|---|---|
| `Beam B2 size 0.20x0.40 m, main bars 4-DB16, stirrups RB6@0.15` | 61 | 35 | 1.74 |
| `คาน B2 ขนาด 0.20x0.40 ม. เหล็กเสริมหลัก 4-DB16 เหล็กปลอก RB6@0.15` | 65 | 44 | 1.48 |
| `ฐานรากเสาเข็ม` | 13 | 7 | 1.86 |
| `{"beam_id": "B2", "width_m": 0.20, ...}` (JSON 98 ตัวอักษร) | 98 | 55 | 1.78 |

ดูการหั่นคำว่า "เหล็กเสริมหลัก": `' เ', 'หล', '็ก', 'เสร', 'ิ', 'ม', 'หล', 'ัก'` คือ 8 token สำหรับ 14 ตัวอักษร และสระ "ิ" ถูกแยกเป็น token เดี่ยว ๆ เพราะพจนานุกรมไม่เคยรวม "เสริ" เข้าด้วยกัน ส่วน "stirrups" ภาษาอังกฤษถูกหั่นเป็น `' stir', 'r', 'ups'` 3 token เพราะเป็นคำเฉพาะทางที่พบน้อยเหมือนกัน

สังเกตอีกอย่าง: ตัวเลข `0.20` ถูกหั่นเป็น `'0', '.', '2', '0'` คือ 4 token ต่อเลขทศนิยมหนึ่งตัว ใน JSON ของเราที่มีขนาดคาน ระยะกริด เลขเหล็ก นับร้อยตัว นี่คือส่วนที่กิน token มากที่สุด ไม่ใช่ตัวหนังสือไทย

งานวิจัยภาษาไทยยืนยันภาพนี้: paper Typhoon [3] รายงานว่า tokenizer ที่เทรนด้วยข้อความไทยประหยัด token ได้ 2.62 เท่าเมื่อเทียบกับ tokenizer ทั่วไป และ paper SeaLLMs [4] วัดว่าประโยคเดียวกันในภาษาไทยใช้ token มากกว่าภาษาอังกฤษราว 4.3 เท่าเมื่อใช้ tokenizer ที่เน้นอังกฤษ (Qwen ทำได้ดีกว่าตัวเลขนั้นมาก ตามตารางด้านบน แต่ก็ยังแพงกว่าอังกฤษ)

### 5.1.4 max_length 10240 หมายถึงอะไรจริง ๆ

`max_length` คือจำนวน token รวมทั้งลำดับ: system prompt + ภาพ (แปลงเป็น visual token) + คำสั่ง + JSON คำตอบ ถ้าภาพหนึ่งภาพกิน 3,796 token (ตอนใช้จริง) และ JSON คำตอบ 1,800 token บวก prompt อีก 500 token รวม 6,100 token ยังพอ แต่ถ้าหน้าไหนมีคาน 60 ตัว JSON อาจแตะ 5,000 token แล้วรวมกันเกิน 10,240 ส่วนที่เกินจะถูกตัดทิ้ง (truncate) เงียบ ๆ ตอนเทรน โมเดลจึงเรียนรู้ว่า "JSON จบกลางคัน" เป็นเรื่องปกติ

🎨 **ภาพที่จะวาดใน HTML:** กล่องข้อความให้พิมพ์ประโยคไทย/อังกฤษ/JSON ได้เอง ด้านล่างแสดงการหั่น token เป็นแถบสีสลับกัน (แต่ละ token คนละสี) พร้อมตัวนับ "ตัวอักษร / token / อัตราส่วน" แบบเรียลไทม์ มีปุ่ม preset สามปุ่ม: "ประโยคไทย" "ประโยคอังกฤษ" "JSON คาน 1 ตัว" และแถบด้านขวาเป็น "งบ token 10,240" ที่ถูกเติมด้วยสามส่วน (ภาพ 3,796 / prompt / JSON) ให้ผู้เรียนลากสไลเดอร์ "จำนวนคานในหน้า" แล้วเห็นว่า JSON กินงบเพิ่มจนล้นตอนไหน (ใช้ tokenizer ฝั่ง JS แบบประมาณ หรือตารางค่าที่คำนวณไว้ล่วงหน้าจาก Qwen tokenizer)

```python
# รันได้จริง ต้องมี transformers และเน็ตครั้งแรกเพื่อโหลด tokenizer (~10 MB)
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-8B")
for s in ["เหล็กเสริมหลัก 4-DB16", "main bars 4-DB16",
          '{"beam_id": "B2", "width_m": 0.20}']:
    ids = tok.encode(s, add_special_tokens=False)
    print(len(s), "chars ->", len(ids), "tokens:", [tok.decode([i]) for i in ids])
```

## 5.2 Embedding: ให้ token มีพิกัดในปริภูมิความหมาย

### 5.2.1 จากเลขจำนวนเต็มเป็นเวกเตอร์

token id เป็นแค่เลขลำดับในพจนานุกรม เลข 5000 ไม่ได้ "ใกล้" เลข 5001 ในความหมายใด ๆ โมเดลจึงมีตาราง **embedding** ขนาด (จำนวน token × มิติ d) แต่ละแถวเป็นเวกเตอร์ที่เรียนรู้ได้ ตัวอย่าง Qwen3-8B มี d = 4096 ดังนั้นตาราง embedding อย่างเดียวคือ 151,669 × 4096 ≈ 621 ล้านพารามิเตอร์

เทียบกับงานโยธา: ตารางเหล็กเสริมบอกว่า DB16 มีพื้นที่หน้าตัด 201 mm², น้ำหนัก 1.58 kg/m, กำลังคราก 390 MPa ค่าเหล่านี้คือ "พิกัด" ของ DB16 ในปริภูมิคุณสมบัติ เหล็ก DB12 กับ DB16 อยู่ใกล้กัน ส่วน RB6 อยู่ไกลออกไปเพราะเป็นเหล็กกลมผิวเรียบ embedding ก็คือตารางแบบนี้ แต่โมเดลหาค่าในตารางเองจากข้อมูล ไม่มีใครกำหนด

### 5.2.2 word2vec (2013) และ king - man + woman ≈ queen

Mikolov และคณะ [5] แสดงให้เห็นในปี 2013 ว่าถ้าเทรนเวกเตอร์คำด้วยเป้าหมายง่าย ๆ (ทำนายคำข้างเคียง) เวกเตอร์ที่ได้จะมีโครงสร้างเชิงเส้น: vec(king) - vec(man) + vec(woman) ใกล้ vec(queen) มากที่สุด แปลว่า "ทิศทาง" ในปริภูมินี้มีความหมาย เช่น ทิศทางเพศ ทิศทางพหูพจน์

ในบริบทของเรา ถ้า embedding ดี เราคาดว่า vec("คาน") - vec("B") + vec("C") ควรใกล้ vec("เสา") เพราะ B คือ prefix ของคาน C คือ prefix ของเสาในแบบมาตรฐานไทย โมเดลที่ทูนแล้วมีโอกาสเรียนรู้ความสัมพันธ์นี้จาก dataset ของเรา

### 5.2.3 ระยะและมุมระหว่างเวกเตอร์

ความคล้ายวัดด้วย cosine similarity:

$$\cos(\theta) = \frac{\mathbf{a}\cdot\mathbf{b}}{\|\mathbf{a}\|\,\|\mathbf{b}\|}$$

โดย $\mathbf{a}\cdot\mathbf{b}$ คือผลคูณจุด (dot product) และ $\|\mathbf{a}\|$ คือความยาวเวกเตอร์ ค่า 1 คือทิศเดียวกัน 0 คือตั้งฉาก ตัวอย่างมิติ 2: a = (1, 0), b = (1, 1) ได้ cos = 1/(1 × √2) = 0.707

🎨 **ภาพที่จะวาดใน HTML:** ระนาบ 2 มิติที่มีจุดคำ 8-10 คำ (คาน, เสา, ฐานราก, DB16, RB6, กริด, ระยะ, JSON) ที่ผู้เรียนลากได้ มีลูกศรจากจุดกำเนิดไปแต่ละคำ เมื่อคลิกเลือกสองคำจะแสดงมุมและค่า cosine แบบเรียลไทม์ มีปุ่ม "ลอง king - man + woman" ที่วาดลูกศรผลลัพธ์ให้เห็นว่าไปตกใกล้ queen อีกส่วนหนึ่งเป็นสไลเดอร์ "มิติ d" (2 → 4096) ที่แสดงข้อความว่าโมเดลจริงใช้ d เท่าไร และตาราง embedding ใหญ่กี่พารามิเตอร์ (vocab × d)

```python
import numpy as np
E = {"คาน":[1.0,0.2],"เสา":[0.3,1.0],"B":[0.9,0.0],"C":[0.1,0.9]}
v = np.array(E["คาน"]) - np.array(E["B"]) + np.array(E["C"])
def cos(a,b): return a@b/np.linalg.norm(a)/np.linalg.norm(b)
for w in E: print(w, round(cos(v, np.array(E[w])),3))
# "เสา" ควรได้ค่าสูงสุด: คาน - B + C ≈ เสา
```

## 5.3 ก่อน Transformer: RNN/LSTM และปัญหาสองข้อ

### 5.3.1 อ่านทีละคำ จำไว้ในสถานะเดียว

Recurrent Neural Network (RNN) อ่านลำดับทีละ token และเก็บ "ความจำ" ไว้ในเวกเตอร์สถานะ $h_t$ เดียว:

$$h_t = \tanh(W_h h_{t-1} + W_x x_t)$$

$x_t$ คือ embedding ของ token ที่ t, $W_h, W_x$ คือน้ำหนักที่เรียนรู้ได้ LSTM (Hochreiter และ Schmidhuber 1997 [6]) เพิ่มประตู (gate) เพื่อเลือกว่าจะจำหรือลืมอะไร ช่วยให้จำได้ไกลขึ้น และ seq2seq ของ Sutskever และคณะ 2014 [7] ใช้ LSTM สองตัว (encoder อ่านต้นทาง decoder เขียนปลายทาง) แปลภาษาได้ดีพอ ๆ กับระบบที่ใช้กันมาสิบปี

### 5.3.2 ปัญหาข้อ 1: ลืมของไกล

ข้อมูลทั้งประโยคต้องถูกบีบลงใน $h_t$ ตัวเดียว เหมือนวิศวกรที่อ่านแบบ 40 หน้าแล้วต้องจำทุกอย่างในหัวโดยห้ามเปิดย้อนกลับ พออ่านถึงหน้า 40 รายละเอียดหน้า 3 ก็เลือนไปแล้ว ในเชิงคณิตศาสตร์ gradient ที่ไหลย้อนกลับผ่าน $W_h$ หลายสิบขั้นจะหดหรือระเบิด (vanishing/exploding gradient)

### 5.3.3 ปัญหาข้อ 2: ขนานไม่ได้

$h_t$ ต้องรอ $h_{t-1}$ เสร็จก่อน จึงคำนวณ 1,000 token ได้ทีละขั้นเท่านั้น GPU ที่มีคอร์เป็นหมื่นก็นั่งว่าง นี่คือคอขวดที่ทำให้เทรนโมเดลใหญ่ ๆ ด้วย RNN ไม่คุ้ม

🎨 **ภาพที่จะวาดใน HTML:** แถวของกล่อง token 20 กล่องเรียงซ้าย-ขวา มีลูกศรจากกล่องหนึ่งไปกล่องถัดไป (RNN) เมื่อกด "เล่น" จะเห็นแถบสีเข้มแทน "ความจำ" ค่อย ๆ จางลงเมื่อไกลจากต้นทาง (สไลเดอร์ปรับ "อัตราลืม" 0.5-0.99 เพื่อดูว่า LSTM ช่วยแค่ไหน) และมีนาฬิกาจับเวลาแสดงว่า RNN ใช้ 20 ขั้น ส่วนแถวล่าง (Transformer) ทุก token เชื่อมถึงกันหมดและใช้ 1 ขั้น

## 5.4 Attention: ให้ token "มองกลับไปดู" ได้เอง

### 5.4.1 Bahdanau 2014: ค้นหาแทนการจำ

Bahdanau, Cho และ Bengio [8] แก้ปัญหา "ลืมของไกล" ในงานแปลด้วยการให้ decoder ไม่ต้องพึ่ง $h_t$ ตัวเดียว แต่ "ค้น" กลับไปดูสถานะของทุกคำในประโยคต้นทาง แล้วให้น้ำหนักว่าคำไหนสำคัญตอนนี้ น้ำหนักนี้เรียกว่า attention weight

เทียบกับงานเรา: ตอนถอดคาน B2 ที่แนวกริด 3 เราไม่ได้จำทั้งแบบ แต่เปิดกลับไปดูตารางกริด (weight สูง) และมองข้ามหมายเหตุงานสถาปัตย์ (weight ต่ำ) attention คือการทำสิ่งนี้แบบอัตโนมัติ

### 5.4.2 Self-attention: Query, Key, Value

Vaswani และคณะ 2017 [9] ใน "Attention Is All You Need" ตัด RNN ทิ้งทั้งหมด ให้ token ในลำดับเดียวกันมองกันเอง (self-attention) แต่ละ token สร้างเวกเตอร์สามตัวจาก embedding $x$ ของตัวเอง:

$$q = x W_Q,\quad k = x W_K,\quad v = x W_V$$

- **Query (q)**: "ฉันกำลังหาอะไร" เหมือนคำค้นในตาราง
- **Key (k)**: "ฉันมีอะไรให้ค้น" เหมือนหัวคอลัมน์ในตาราง
- **Value (v)**: "ถ้าเลือกฉัน จะได้ข้อมูลนี้ไป" เหมือนค่าในช่อง

สูตรเต็ม:

$$\text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V$$

$Q, K, V$ คือเมทริกซ์ที่ซ้อน q, k, v ของทุก token เป็นแถว, $d_k$ คือมิติของ k, softmax แปลงคะแนนเป็นน้ำหนักที่รวมกันได้ 1

### 5.4.3 คำนวณจริง: 3 token, มิติ 2

ให้ embedding ของ 3 token (สมมติว่า "คาน", "B2", "0.20") เป็น

$$X = \begin{bmatrix}1&0\\0&1\\1&1\end{bmatrix}$$

เพื่อให้เห็นตัวเลขชัด ใช้ $W_Q = W_K = I$ (เมทริกซ์เอกลักษณ์) และ $W_V = \begin{bmatrix}1&2\\0&1\end{bmatrix}$ จะได้ $Q = K = X$ และ

$$V = XW_V = \begin{bmatrix}1&2\\0&1\\1&3\end{bmatrix}$$

**ขั้น 1 คะแนนดิบ** $S = QK^\top$ (แถว i คือ query ของ token i, คอลัมน์ j คือ key ของ token j):

$$S = \begin{bmatrix}1&0&1\\0&1&1\\1&1&2\end{bmatrix}$$

อ่านว่า: token 3 (1,1) คล้ายตัวเองมากสุด (2) และคล้าย token 1, 2 เท่ากัน (1)

**ขั้น 2 หารด้วย √d_k** = √2 ≈ 1.414:

$$S' = \begin{bmatrix}0.707&0&0.707\\0&0.707&0.707\\0.707&0.707&1.414\end{bmatrix}$$

**ขั้น 3 softmax ทีละแถว** $\text{softmax}(s)_j = e^{s_j}/\sum_m e^{s_m}$ แถวแรก: $e^{0.707}=2.03,\ e^0=1,\ e^{0.707}=2.03$ รวม 5.06 ได้ (0.401, 0.198, 0.401)

$$A = \begin{bmatrix}0.401&0.198&0.401\\0.198&0.401&0.401\\0.248&0.248&0.503\end{bmatrix}$$

ทุกแถวรวมได้ 1 นี่คือ "น้ำหนักความสนใจ"

**ขั้น 4 ผลลัพธ์** $Z = AV$ แถวแรก: 0.401×(1,2) + 0.198×(0,1) + 0.401×(1,3) = (0.802, 2.203)

$$Z = \begin{bmatrix}0.802&2.203\\0.599&2.000\\0.752&2.255\end{bmatrix}$$

token แต่ละตัวได้เวกเตอร์ใหม่ที่ "ผสม" ข้อมูลจาก token อื่นตามน้ำหนัก นี่คือกลไกที่ทำให้ "B2" รู้ว่าตัวเองอยู่ใกล้คำว่า "คาน" ไม่ใช่ "เสา"

### 5.4.4 ทำไมต้องหาร √d_k

ถ้า q และ k มีองค์ประกอบสุ่มขนาดประมาณ 1 ผลคูณจุดของเวกเตอร์มิติ d จะมีค่าเบี่ยงเบนประมาณ √d ทดลองจริงด้วย numpy (5 key, seed 0):

| d | std ของคะแนนดิบ | softmax ไม่หาร | softmax หาร √d |
|---|---|---|---|
| 2 | 0.08 | (0.21, 0.18, 0.21, 0.22, 0.18) | (0.21, 0.18, 0.21, 0.21, 0.19) |
| 64 | 7.1 | (0.00, 0.00, 0.00, 0.00, 1.00) | (0.03, 0.11, 0.17, 0.22, 0.47) |
| 512 | 23.1 | (0, 0, 0, 1, 0) | (0.13, 0.02, 0.21, 0.52, 0.11) |

ไม่หาร softmax จะกลายเป็น one-hot คือ "มองแค่ token เดียว" gradient ไหลไม่ได้ (softmax อิ่มตัว) หารแล้วน้ำหนักกระจาย โมเดลเรียนต่อได้ เทียบง่าย ๆ คือการ normalize หน่วยก่อนเทียบขนาด เหมือนเทียบโมเมนต์เป็น kN·m ไม่ใช่ N·mm

🎨 **ภาพที่จะวาดใน HTML:** ตาราง 3×3 ของ attention weight ที่ระบายสีตามค่า (heatmap) มี 3 token ให้แก้ค่า embedding ได้ทีละช่อง (มิติ 2) และเมทริกซ์ $W_Q, W_K, W_V$ ให้แก้ได้ ทุกครั้งที่แก้ให้แสดง S, S/√d, softmax, Z ทีละขั้นพร้อมตัวเลข มีสวิตช์ "หาร √d" เปิด/ปิด และสไลเดอร์ d (2 → 512) ที่สุ่มเวกเตอร์ใหม่ให้เห็น heatmap กลายเป็นช่องเดียวเข้มเมื่อปิดการหาร

```python
import numpy as np
np.set_printoptions(precision=3, suppress=True)
X = np.array([[1.,0.],[0.,1.],[1.,1.]])          # 3 token, d=2
Wq = Wk = np.eye(2); Wv = np.array([[1.,2.],[0.,1.]])
Q, K, V = X@Wq, X@Wk, X@Wv
S = Q@K.T / np.sqrt(2)
A = np.exp(S) / np.exp(S).sum(1, keepdims=True)     # softmax ทีละแถว
print("weights\n", A); print("output\n", A@V)
mask = np.triu(np.ones((3,3), bool), 1)              # causal: ห้ามมองอนาคต
Sm = np.where(mask, -np.inf, S)
Am = np.exp(Sm) / np.exp(Sm).sum(1, keepdims=True)
print("causal weights\n", Am)
```

### 5.4.5 Multi-head: มองหลายมุมพร้อมกัน

หนึ่งชุด $W_Q, W_K, W_V$ เรียนรู้ความสัมพันธ์ได้แบบเดียว (เช่น "คำนี้ขยายคำไหน") Transformer จึงใช้หลายหัว (head) พร้อมกัน แต่ละหัวมี d เล็กลง (เช่น d = 4096 แบ่งเป็น 32 หัว หัวละ 128) แล้วต่อผลลัพธ์กลับ [9] หัวหนึ่งอาจเรียนรู้ "ตัวเลขนี้เป็นความกว้างของคานไหน" อีกหัวเรียนรู้ "ชื่อคานนี้อยู่แนวกริดไหน" เหมือนทีมตรวจแบบที่แบ่งกันดูคนละเรื่องแล้วมารวมกัน

Qwen3.6-35B-A3B ใช้ 16 หัวสำหรับ query แต่แค่ 2 หัวสำหรับ key/value [15] เทคนิคนี้เรียก Grouped-Query Attention (GQA, Ainslie 2023 [10]) ต่อยอดจาก Multi-Query Attention ของ Shazeer 2019 [11] เหตุผลจะชัดในหัวข้อ KV cache

## 5.5 ส่วนประกอบที่เหลือของ Transformer block

### 5.5.1 Positional encoding: attention ไม่รู้ลำดับ

สังเกตว่าสูตร attention ไม่มี "ตำแหน่ง" อยู่เลย สลับลำดับ token แล้วผลลัพธ์แต่ละ token ยังเหมือนเดิม (แค่สลับแถว) แต่ "B2 0.20 0.40" กับ "0.40 B2 0.20" ต่างกันมาก จึงต้องเติมข้อมูลตำแหน่งเข้าไป

- **Sinusoidal** (Vaswani 2017 [9]): บวกเวกเตอร์ sin/cos ที่ความถี่ต่างกันเข้ากับ embedding ตำแหน่ง p มิติที่ 2i ได้ $\sin(p/10000^{2i/d})$ มิติที่ 2i+1 ได้ $\cos(\cdot)$ เหมือนเข็มนาฬิกาหลายเข็มที่หมุนคนละความเร็ว อ่านตำแหน่งได้จากมุมของทุกเข็มรวมกัน
- **RoPE** (Su และคณะ 2021 [12]): แทนที่จะบวก ให้ "หมุน" เวกเตอร์ q และ k ด้วยมุมที่ขึ้นกับตำแหน่ง ผลคือผลคูณจุด $q_m \cdot k_n$ ขึ้นกับ m - n (ระยะห่างสัมพัทธ์) โดยอัตโนมัติ Qwen ทุกรุ่นใช้ RoPE [15] และ Qwen3-VL ขยายเป็น Interleaved-MRoPE ที่หมุนตามแกนเวลา ความกว้าง ความสูง ของภาพ/วิดีโอ [13]

ตัวอย่างมิติ 2: หมุนเวกเตอร์ (1, 0) ด้วยมุม $m\theta$ ได้ $(\cos m\theta, \sin m\theta)$ ถ้า θ = 10° token ตำแหน่ง 3 หมุน 30° ตำแหน่ง 5 หมุน 50° ผลคูณจุดของสองตัวนี้คือ cos(20°) = 0.94 ขึ้นกับผลต่าง 2 ตำแหน่งเท่านั้น ไม่ว่าจะเลื่อนทั้งคู่ไปที่ไหน

🎨 **ภาพที่จะวาดใน HTML:** วงกลมหน่วยสองวง ซ้ายแสดงเวกเตอร์ q ที่ตำแหน่ง m (สไลเดอร์) ขวาแสดง k ที่ตำแหน่ง n (สไลเดอร์) ทั้งคู่หมุนตาม RoPE พร้อมแสดงมุมและผลคูณจุด ด้านล่างกราฟ "ผลคูณจุด vs ผลต่างตำแหน่ง" ที่ยังคงเดิมเมื่อเลื่อน m, n พร้อมกัน (แสดงว่า RoPE เข้ารหัสระยะสัมพัทธ์) มีแท็บ "sinusoidal" แสดง heatmap ของ sin/cos 64 มิติ × 100 ตำแหน่ง

### 5.5.2 Feed-forward: คิดต่อทีละ token

หลัง attention แต่ละ token ผ่านเครือข่ายเล็ก ๆ สองชั้นแบบเดียวกับบทที่ 2:

$$\text{FFN}(x) = W_2\,\sigma(W_1 x)$$

โดย $W_1$ ขยายมิติ (เช่น 4096 → 12288) $\sigma$ คือ activation (Qwen ใช้ SwiGLU) และ $W_2$ หดกลับ ชั้นนี้ไม่มีการมองข้าม token คิดเฉพาะตัว จึงมองว่า attention คือ "รวบรวมข้อมูล" ส่วน FFN คือ "ประมวลผล" และ FFN กินพารามิเตอร์ราวสองในสามของแต่ละ block ซึ่งเป็นส่วนที่ MoE จะเข้ามาแทนที่ในหัวข้อ 5.9

### 5.5.3 Residual และ LayerNorm: ทำให้ซ้อนได้หลายสิบชั้น

Transformer ซ้อน block เหล่านี้หลายสิบชั้น (Qwen3-8B มี 36 ชั้น) ปัญหาคือ gradient เดินทางผ่านหลายสิบชั้นแล้วหาย วิธีแก้สองอย่างที่ยืมมาจากงาน CNN

- **Residual connection** (He 2015 [14]): แทนที่จะให้ชั้นเรียนรู้ $y = f(x)$ ให้เรียนรู้ $y = x + f(x)$ คือเรียนรู้ "ส่วนต่าง" เท่านั้น เหมือนเสริมแผ่นเหล็กบางบนคานเดิม คานเดิมยังรับแรงได้ แผ่นเสริมแค่เพิ่มส่วนที่ขาด gradient จึงไหลผ่านทางลัด $x$ ได้ตรง ๆ
- **LayerNorm** (Ba 2016 [17]): ปรับเวกเตอร์ของแต่ละ token ให้ค่าเฉลี่ย 0 ส่วนเบี่ยงเบน 1 ก่อนเข้าแต่ละชั้นย่อย เหมือน normalize หน่วยไม่ให้ค่าใดค่าหนึ่งใหญ่จนกลบเพื่อน (LLM สมัยใหม่ใช้ RMSNorm ที่ตัดขั้นลบค่าเฉลี่ยออกเพื่อประหยัด)

หนึ่ง block จึงเป็น: `x = x + Attn(Norm(x)); x = x + FFN(Norm(x))`

🎨 **ภาพที่จะวาดใน HTML:** ผังบล็อกแนวตั้งของ Transformer block หนึ่งชั้น (Norm → Multi-head Attn → + → Norm → FFN → +) ที่คลิกแต่ละกล่องแล้วไฮไลต์สมการและจำนวนพารามิเตอร์ของกล่องนั้นสำหรับ d, จำนวนหัว, และ FFN ratio ที่ผู้เรียนตั้งได้ ด้านข้างมีตัวเลข "พารามิเตอร์ต่อชั้น × จำนวนชั้น + embedding = รวม" ที่อัปเดตทันที ให้ลองตั้งค่าให้ได้ใกล้ 8B

## 5.6 สามสถาปัตยกรรม: Encoder, Decoder, และ Encoder-Decoder

Transformer ต้นฉบับ [9] มีสองฝั่ง: encoder อ่านต้นทาง (ทุก token มองกันได้ทั้งสองทิศ) และ decoder เขียนปลายทาง (มองได้เฉพาะสิ่งที่เขียนไปแล้ว บวกมอง encoder) ต่อมาแยกเป็นสามสาย

| แบบ | ตัวอย่าง | มองได้ | เหมาะกับ |
|---|---|---|---|
| Encoder-only | BERT 2018 [18] | ทั้งสองทิศ | จัดหมวด, ค้นหา, เข้าใจข้อความ |
| Decoder-only | GPT-1/2/3 [19][20][21], Qwen, Llama | เฉพาะซ้าย (อดีต) | สร้างข้อความ |
| Encoder-decoder | T5 2019 [22] | encoder สองทิศ, decoder ซ้าย | แปล, สรุป |

**Causal mask** คือกลไกที่ทำให้ decoder มองอนาคตไม่ได้: ใส่ $-\infty$ ในคะแนน $S$ ทุกช่องที่ j > i ก่อน softmax ทำให้น้ำหนักของอนาคตเป็น 0 พอดี จากตัวอย่าง 5.4.3 เมื่อใส่ mask จะได้

$$A_{\text{causal}} = \begin{bmatrix}1&0&0\\0.33&0.67&0\\0.248&0.248&0.503\end{bmatrix}$$

แถวสุดท้ายเหมือนเดิม (มองได้ครบ) แถวแรกมองได้แค่ตัวเอง

ทำไม LLM สมัยใหม่เกือบทั้งหมดเป็น decoder-only? เพราะการเทรนง่ายที่สุด (ข้อ 5.7) และงานทุกอย่างแปลงเป็น "เขียนต่อ" ได้ รวมถึงงานของเรา: ป้อนภาพ + คำสั่ง แล้ว "เขียนต่อ" เป็น JSON

🎨 **ภาพที่จะวาดใน HTML:** ตาราง attention 6×6 สามแบบเรียงกัน (encoder เต็ม, decoder สามเหลี่ยมล่าง, encoder-decoder แบ่งสองส่วน) เมื่อวางเมาส์บนแถว i จะไฮไลต์คอลัมน์ที่ token i มองได้ มีตัวเลือกโมเดลจริง (BERT / GPT / T5 / Qwen3-VL) ที่เปลี่ยนตารางและข้อความอธิบายว่าภาพ (visual token) ถูกวางไว้ตรงไหนของลำดับใน Qwen3-VL

## 5.7 Next-token prediction: ทำไม "ทำนายคำถัดไป" สร้างความรู้ได้

### 5.7.1 Self-supervised: ข้อมูลเป็นครูของตัวเอง

Decoder-only ถูกเทรนด้วยเป้าหมายเดียว: ให้ token ที่ 1..t ทำนายการแจกแจงของ token ที่ t+1 ให้ตรงกับของจริง

$$\mathcal{L} = -\sum_{t} \log p_\theta(x_{t+1} \mid x_1,\ldots,x_t)$$

$p_\theta$ คือความน่าจะเป็นที่โมเดล (พารามิเตอร์ θ) ให้กับ token จริง loss คือค่าลบของ log ความน่าจะเป็นนั้น รวมทุกตำแหน่ง ถ้าโมเดลให้ 0.5 กับ token จริง loss = -log 0.5 = 0.69 ถ้าให้ 0.01 loss = 4.6

ข้อดีมหาศาลคือ **ไม่ต้องมีคนติดป้าย** ข้อความทุกประโยคบนอินเทอร์เน็ตเป็นตัวอย่างสอนได้ทันที (เทียบกับงานเราที่ต้องนั่งแก้ JSON ใน review.html ทีละหน้า) และเพราะ causal mask ประโยคยาว T token ให้ตัวอย่างสอน T ข้อในการคำนวณครั้งเดียว

### 5.7.2 ทำไมมันสร้าง "ความรู้"

ลองคิดว่าจะทำนาย token ถัดไปของ "คานขนาด 0.20×0.40 ม. ใช้เหล็กปลอก RB6@" ให้ดีต้องรู้อะไรบ้าง: รู้ว่าเหล็กปลอกระบุระยะห่าง รู้ว่าหน่วยเป็นเมตร รู้ว่าค่าทั่วไปคือ 0.10-0.20 รู้ไวยากรณ์ของแบบก่อสร้าง การบีบให้ loss ต่ำบนข้อความหลายล้านล้าน token จึงบังคับให้โมเดลสร้างแบบจำลองภายในของโลกที่เขียนข้อความเหล่านั้น Radford และคณะ 2019 [20] แสดงว่า GPT-2 ที่เทรนแค่ทำนายคำถัดไปทำงานแปล สรุป ตอบคำถามได้โดยไม่เคยถูกสอนงานเหล่านั้นตรง ๆ

แต่ต้องจำไว้ (จะสำคัญมากในบทที่ 6): โมเดลเรียนรู้ **การแจกแจง** ของข้อความ ไม่ใช่ความจริง ถ้าในคลังมีคนเขียนผิดบ่อย โมเดลก็จะทำนายผิดอย่างมั่นใจ

🎨 **ภาพที่จะวาดใน HTML:** กล่องข้อความให้พิมพ์ต้นประโยคภาษาไทยหรือ JSON ครึ่งเดียว ด้านล่างแสดงแท่งกราฟ top-10 token ถัดไปพร้อมความน่าจะเป็น (ใช้ตารางที่คำนวณไว้ล่วงหน้าจากโมเดลเล็ก หรือ bigram จาก dataset ตัวอย่าง) สไลเดอร์ temperature ปรับความแหลมของการแจกแจงและปุ่ม "สุ่ม 1 token" ที่ต่อประโยคไปเรื่อย ๆ ให้เห็นว่าคำตอบเปลี่ยนไปทุกครั้งที่กด และแสดงค่า loss = -log p ของ token ที่ถูกเลือก

```python
import numpy as np
logits = np.array([3.0, 2.0, 0.5, -1.0])          # คะแนนดิบของ 4 token ถัดไป
for T in [0.1, 0.7, 1.0, 2.0]:
    p = np.exp(logits/T) / np.exp(logits/T).sum()
    print(f"T={T}: p={np.round(p,3)}  loss ถ้าคำตอบจริงคือ token0 = {-np.log(p[0]):.2f}")
# T ต่ำ -> แหลม (เกือบ greedy) ; T สูง -> แบน (สุ่มมาก)
```

## 5.8 ใหญ่ขึ้นแล้วเก่งขึ้น: GPT-1/2/3, Scaling laws และ emergent abilities

### 5.8.1 ลำดับเหตุการณ์ (หลักการพื้นฐาน ไม่เปลี่ยน)

- GPT-1 (Radford 2018 [19]): 117M พารามิเตอร์ แสดงว่า pretrain แล้ว fine-tune ชนะการเทรนจากศูนย์
- GPT-2 (Radford 2019 [20]): 1.5B แสดงว่าโมเดลใหญ่ทำหลายงานได้โดยไม่ต้อง fine-tune
- GPT-3 (Brown 2020 [21]): 175B แสดง in-context learning คือให้ตัวอย่างใน prompt แล้วทำตามได้ (บทที่ 6 จะขยาย)

### 5.8.2 Scaling laws: Kaplan 2020 และ Chinchilla 2022

Kaplan และคณะ [23] วัดว่า loss ลดลงเป็น power law ตามสามตัวแปร: จำนวนพารามิเตอร์ N, จำนวน token ที่เทรน D, และ compute C

$$L(N) \approx \left(\frac{N_c}{N}\right)^{\alpha_N},\quad \alpha_N \approx 0.076$$

คือเพิ่มพารามิเตอร์ 10 เท่า loss ลดลงเป็นสัดส่วนคงที่ เหมือนกราฟ log-log ที่วิศวกรคุ้นเคย (เช่น S-N curve ของความล้า) และ Kaplan สรุปว่าควรเอา compute ไปเพิ่มขนาดโมเดลมากกว่าเพิ่มข้อมูล

Hoffmann และคณะ 2022 (Chinchilla) [24] วัดใหม่ละเอียดกว่าและพบว่า Kaplan ประเมินความสำคัญของข้อมูลต่ำไป: ที่ compute คงที่ ควรเพิ่ม N และ D **ในสัดส่วนเท่ากัน** ราว 20 token ต่อพารามิเตอร์ Chinchilla 70B ที่เทรน 1.4T token ชนะ Gopher 280B ที่เทรนแค่ 300B token นี่คือเหตุผลที่โมเดล 8B ยุคปัจจุบันเทรนด้วยข้อมูลหลายสิบ T token (มากกว่า Chinchilla-optimal หลายเท่า) เพราะคนใช้ต้องการโมเดลเล็กที่ inference ถูก ยอมจ่าย compute ตอนเทรนเพิ่ม

### 5.8.3 Emergent abilities: ถกเถียงกันอยู่

Wei และคณะ 2022 [25] รายงานว่าความสามารถบางอย่าง (เช่น คณิตหลายขั้น) "โผล่" ขึ้นทันทีเมื่อโมเดลใหญ่ถึงระดับหนึ่ง ทำนายจากโมเดลเล็กไม่ได้ แต่ Schaeffer และคณะ 2023 [26] แย้งว่าความกะทันหันเกิดจาก **ตัววัด** ที่ไม่เป็นเชิงเส้น (เช่น exact match ที่ต้องถูกทุกหลัก) ถ้าวัดด้วยตัววัดต่อเนื่อง (เช่น log-likelihood ต่อ token) จะเห็นการดีขึ้นแบบราบเรียบ

บทเรียนสำหรับเรา: element recall ของเราเป็นตัววัดแบบ "ถูก/ผิดต่อองค์ประกอบ" ซึ่งไม่เชิงเส้น recall กระโดดจาก 11% เป็น 28% ระหว่างรอบทูน อาจไม่ได้แปลว่าโมเดล "เข้าใจ" ขึ้นแบบก้าวกระโดด แต่อาจแปลว่าความน่าจะเป็นต่อ token ค่อย ๆ ข้ามเส้นที่ทำให้ JSON ทั้งก้อน parse ผ่าน

🎨 **ภาพที่จะวาดใน HTML:** กราฟ log-log แกน x = พารามิเตอร์ (10M → 1T) แกน y = loss วาดเส้น power law ของ Kaplan และมีสไลเดอร์ "งบ compute" ที่แสดงจุด (N, D) ที่ Kaplan แนะนำเทียบกับ Chinchilla (จุด Chinchilla เลื่อนไปทาง D มากกว่า) แท็บที่สองแสดง "emergence": กราฟเดียวกันแต่แกน y สลับได้ระหว่าง "exact match" (โค้งกระโดด) กับ "log-likelihood" (โค้งราบ) ให้ผู้เรียนเห็นว่าข้อมูลเดียวกันดูต่างกันตามตัววัด

## 5.9 เมื่อใช้งานจริง: Context window, KV cache และเหตุผลที่ JSON ยาวช้า

### 5.9.1 Context window

context window คือจำนวน token สูงสุดที่โมเดลเห็นพร้อมกัน (Qwen3.6-35B-A3B ระบุ 262,144 token ขยายได้ถึงราว 1M ด้วย YaRN [15]) ขีดจำกัดมาจากสองอย่าง: positional encoding ที่เทรนมาถึงตำแหน่งไหน และหน่วยความจำ แต่หน้าต่างใหญ่ไม่ได้แปลว่าใช้ได้ดีเท่ากันทุกตำแหน่ง Liu และคณะ 2023 [27] พบว่าโมเดลตอบดีที่สุดเมื่อข้อมูลสำคัญอยู่ต้นหรือท้าย และแย่ลงมากเมื่ออยู่ตรงกลาง ("lost in the middle")

### 5.9.2 KV cache: ทำไม generate เป็น O(n) ต่อ token

ตอนสร้างข้อความ decoder ทำงานทีละ token: มี n token แล้ว อยากได้ token ที่ n+1 ถ้าทำแบบซื่อ ๆ ต้องคำนวณ attention ของทุก token ใหม่ทั้งหมด คือ O(n²) ต่อ token แต่สังเกตว่า k และ v ของ token เก่าไม่เปลี่ยน (causal mask ทำให้ token เก่าไม่เห็น token ใหม่) จึงเก็บไว้ (cache) แล้วคำนวณเฉพาะ q ของ token ใหม่ไปคูณกับ K, V ที่เก็บไว้ ต้นทุนต่อ token จึงเป็น O(n) [28]

ต้นทุนหน่วยความจำของ cache ต่อ token:

$$\text{bytes/token} = 2 \times L \times h_{kv} \times d_{head} \times \text{bytes}$$

2 คือ K และ V, L จำนวนชั้น, $h_{kv}$ จำนวนหัว key/value, $d_{head}$ มิติต่อหัว ตัวอย่าง Qwen3-8B: 36 ชั้น, 8 หัว KV (GQA), 128 มิติ, bf16 = 2 × 36 × 8 × 128 × 2 = 147 KB ต่อ token ที่ 10,000 token = 1.47 GB ถ้าไม่มี GQA (32 หัว KV) จะเป็น 5.9 GB นี่คือเหตุผลที่ GQA/MQA [10][11] มีอยู่ และเป็นเหตุผลที่ Qwen3.6 เหลือ KV แค่ 2 หัว

### 5.9.3 โยงกับ "classify เร็วกว่าถอดเต็ม 7 เท่า"

ใน t03 เราแยก pass0 (classify หน้า: คำตอบสั้นไม่กี่ token) ออกจาก pass2 (ถอดเต็ม: JSON หลายพัน token) และวัดได้ว่า classify เร็วกว่าราว 7 เท่า อธิบายด้วยทฤษฎีนี้ได้ตรง ๆ

- ทั้งสอง pass จ่ายค่า **prefill** เท่ากัน: ประมวลผลภาพ 3,796 token + prompt ครั้งเดียว ขั้นนี้ขนานได้ ใช้ GPU เต็มที่
- แต่ **decode** ต่างกันมหาศาล: classify พ่นสัก 10 token ส่วนถอดเต็มพ่น 2,000-5,000 token แต่ละ token ต้องโหลดพารามิเตอร์ทั้งโมเดลจาก VRAM มาคูณกับเวกเตอร์เดียว (memory-bound ไม่ใช่ compute-bound) และต้องอ่าน KV cache ที่ยาวขึ้นเรื่อย ๆ
- เวลาต่อ token ตอน decode จึงเกือบคงที่ + เพิ่มเล็กน้อยตาม n เวลารวมของ JSON ≈ prefill + (จำนวน token × เวลาต่อ token) ยิ่ง JSON ยาว ยิ่งช้าแบบเชิงเส้น

นี่คือเหตุผลเชิงโครงสร้างที่ควรทำให้ JSON กระชับ (key สั้น ไม่มี whitespace ไม่ใส่ field ว่าง) และเป็นเหตุผลที่ตอนบั๊กข้อ 4 (greedy วนซ้ำ B2 ไม่รู้จบ) เครื่องช้าลงจนต้อง timeout: โมเดลไม่ได้ค้าง แต่กำลัง decode ไปเรื่อย ๆ ด้วยต้นทุน O(n) ต่อ token จนชน max token

🎨 **ภาพที่จะวาดใน HTML:** ไทม์ไลน์แนวนอนสองแถว (classify vs ถอดเต็ม) แสดงบล็อก "prefill" สีหนึ่งยาวเท่ากัน ตามด้วยบล็อก "decode" ที่ยาวตามจำนวน token output (สไลเดอร์ 10 → 5,000) ด้านล่างเป็นมิเตอร์ VRAM ที่แสดงน้ำหนักโมเดล (คงที่) + KV cache ที่โตตามจำนวน token โดยผู้เรียนเลือกจำนวนหัว KV (32 / 8 / 2) เพื่อเห็นว่า GQA ลด cache ลงกี่เท่า และมีปุ่ม "โมเดลวนซ้ำ B2" ที่ให้บล็อก decode ยืดออกไปเรื่อย ๆ จนชนเส้น timeout

```python
L, h_kv, d_head, bytes_ = 36, 8, 128, 2         # Qwen3-8B, bf16
per_token = 2 * L * h_kv * d_head * bytes_
for n in [1000, 5000, 10240, 32000]:
    print(f"{n:>6} tokens -> KV cache {per_token*n/1e9:.2f} GB (GQA 8 heads)"
          f" | {per_token*4*n/1e9:.2f} GB (32 heads)")
```

## 5.10 Mixture of Experts: 35B ที่คิดเร็วเหมือน 3B แต่กิน VRAM เท่า 35B

### 5.10.1 แนวคิด: ไม่ต้องใช้ทุกส่วนกับทุก token

Shazeer และคณะ 2017 [29] เสนอ Sparsely-Gated MoE: แทนที่ FFN ชั้นเดียวด้วย FFN หลายตัว (expert) และมี router เล็ก ๆ เลือกว่า token นี้จะส่งไป expert ไหน token "0.20" อาจไปหา expert ที่ถนัดตัวเลข token "เหล็กปลอก" ไปหา expert ที่ถนัดคำศัพท์ก่อสร้าง แต่ละ token คำนวณแค่ expert ที่ถูกเลือก (เช่น 8 จาก 256) จึงได้ "ความจุ" ของโมเดลใหญ่ ในราคาคำนวณของโมเดลเล็ก

$$y = \sum_{i \in \text{TopK}} g_i(x)\, E_i(x)$$

$g_i$ คือน้ำหนักจาก router (softmax บน top-k), $E_i$ คือ expert ที่ i

เทียบงานเรา: บริษัทที่ปรึกษามีวิศวกร 256 คน แต่แบบแต่ละหน้าส่งให้แค่ 8 คนที่ตรงสาย ค่าจ้างต่อหน้า = 8 คน แต่ต้องมีทั้ง 256 คนนั่งอยู่ในออฟฟิศ (VRAM)

### 5.10.2 ลำดับพัฒนาการ (state of the art เปลี่ยนเร็ว)

- Switch Transformer 2021 [30]: เลือก expert เดียวต่อ token ทำให้ง่ายและเสถียรขึ้น สเกลถึง 1.6T พารามิเตอร์
- ST-MoE 2022 [31]: ระบุปัญหา training instability ของ MoE และเสนอ router z-loss เป็นคู่มือออกแบบ
- Mixtral 8x7B 2024 [32]: 8 expert เลือก 2 รวม 47B active 13B แสดงว่า MoE open-weight ใช้งานจริงได้
- DeepSeekMoE 2024 [33]: expert ละเอียด (fine-grained) จำนวนมาก + shared expert ที่เปิดตลอด และ DeepSeek-V3 2024 [34]: 671B total / 37B active
- Qwen3.6-35B-A3B (เมษายน 2026) [15]: 256 expert เลือก 8 + shared 1, 35B total / 3B active, 40 ชั้น และเป็น hybrid ที่สลับ Gated DeltaNet (linear attention) 3 ชั้นต่อ attention เต็ม 1 ชั้น

### 5.10.3 ทำไม VRAM ต้องโหลดทั้ง 35B

router ตัดสินใจ **ต่อ token ต่อชั้น** ว่าจะใช้ expert ไหน ล่วงหน้าไม่รู้ ดังนั้น expert ทุกตัวต้องพร้อมอยู่ใน VRAM ตลอดเวลา ที่ bf16 คือ 35 × 10⁹ × 2 byte = 70 GB (สอดคล้องกับขนาด repo 71.9 GB [15]) การคำนวณต่อ token แตะแค่ 3B พารามิเตอร์ จึงเร็วเท่าโมเดล 3B แต่หน่วยความจำเท่า 35B

### 5.10.4 ทำไม MoE ทำ OOM และเทรนยาก (บั๊กข้อ 7)

1. **น้ำหนักเต็ม 35B ต้องอยู่ใน VRAM** แม้ใช้ QLoRA 4-bit ก็ยัง ~18-20 GB สำหรับน้ำหนักอย่างเดียว ยังไม่รวม activation, KV, gradient ของ LoRA และ optimizer state
2. **Load balancing**: ถ้า router ส่ง token ไป expert เดิม ๆ ทุกครั้ง expert อื่นไม่ได้เรียน ต้องมี auxiliary loss บังคับกระจาย (Switch [30], ST-MoE [31]; DeepSeek-V3 ใช้วิธี loss-free [34]) TRL มีพารามิเตอร์ `router_aux_loss_coef` สำหรับเรื่องนี้ [35]
3. **ความไม่เสถียร**: ST-MoE [31] รายงานว่า MoE loss spike ง่ายกว่า dense และ router ทำให้ค่าผิดปกติ (outlier) ขยายตัว
4. **หน่วยความจำกระโดดตาม batch**: token ใน batch เดียวอาจกระจุกไปที่ expert เดียว ทำให้ expert นั้นต้องรับ tensor ใหญ่ชั่วคราว การจอง VRAM จึงไม่คงที่ ทำงานได้หลาย step แล้ว OOM ทีหลังก็เป็นไปได้
5. **LoRA บน MoE**: ต้องเลือกว่าจะแปะ adapter บน attention เท่านั้น หรือบนทุก expert (พารามิเตอร์ LoRA คูณด้วยจำนวน expert) ทางเลือกหลังกินหน่วยความจำและเรียนช้าเพราะแต่ละ expert เห็น token น้อย

🎨 **ภาพที่จะวาดใน HTML:** แผนผัง MoE ชั้นเดียว: token 6 ตัวทางซ้าย router ตรงกลาง expert 16 กล่องทางขวา (ย่อจาก 256) เมื่อกด "ส่ง" ลูกศรจาก token แต่ละตัววิ่งไปหา expert 2-3 ตัวที่ router เลือก และ expert ที่ถูกใช้สว่างขึ้น ด้านล่างมีสองมิเตอร์: "พารามิเตอร์ที่คำนวณ" (นับเฉพาะ expert สว่าง) และ "พารามิเตอร์ใน VRAM" (นับทั้งหมด) สไลเดอร์ "ความไม่สมดุลของ router" ที่เมื่อสูงขึ้นจะให้ token ทั้งหมดวิ่งไป expert เดียวและมิเตอร์ VRAM ชั่วคราวของ expert นั้นพุ่งขึ้นจนแตะเส้น OOM

```python
import numpy as np
rng = np.random.default_rng(0)
n_tok, n_exp, k = 6, 8, 2
logits = rng.normal(size=(n_tok, n_exp))
top = np.argsort(-logits, axis=1)[:, :k]            # router เลือก top-k
for t in range(n_tok): print(f"token {t} -> experts {top[t]}")
load = np.bincount(top.ravel(), minlength=n_exp)
print("load per expert:", load, "| ideal:", n_tok*k/n_exp)
print("aux loss (สัดส่วนสมดุล) =", np.round((load/load.sum()*n_exp).var(),3))
```

## 5.11 จำนวนพารามิเตอร์ → VRAM: สูตรที่ควรคิดในหัวได้

$$\text{VRAM}_{\text{weights}} = N \times \text{bytes/param}$$

| รูปแบบ | bytes/param | Qwen3-VL-8B (≈8B) | Qwen3.6-35B-A3B (35B) |
|---|---|---|---|
| fp32 | 4 | 32 GB | 140 GB |
| bf16 / fp16 | 2 | 16 GB | 70 GB |
| int8 / Q8_0 | ~1 | 8 GB | 35 GB |
| 4-bit (nf4, Q4_K_M) | ~0.5-0.6 | 4-5 GB | 18-21 GB |

นี่คือ **เฉพาะน้ำหนัก** ตอนเทรนต้องบวก

- gradient ของพารามิเตอร์ที่เทรน (LoRA เล็ก จึงประหยัดตรงนี้)
- optimizer state (AdamW เก็บ 2 ค่าต่อพารามิเตอร์ที่เทรน)
- activation ทุกชั้นสำหรับ backprop (โตตามความยาวลำดับ × batch; gradient checkpointing แลกเวลาเพื่อลดส่วนนี้)
- KV cache และ logits ขนาด (ลำดับ × 151,669) ตอนคำนวณ loss

ที่ t02 เราใช้ QLoRA 4-bit บน 8B กับ batch 1, grad_accum 8, max_length 10k-13k คือการเลือกให้น้ำหนัก ~5 GB แล้วเหลือที่ให้ activation ของลำดับยาว ๆ ถ้าเพิ่ม batch เป็น 2 activation จะสองเท่าทันที ในขณะที่น้ำหนักเท่าเดิม

🎨 **ภาพที่จะวาดใน HTML:** เครื่องคิด VRAM: เลือกโมเดล (8B / 32B / 35B-A3B) เลือกความละเอียด (fp32 / bf16 / int8 / 4-bit) เลือกโหมด (inference / LoRA / QLoRA / full fine-tune) สไลเดอร์ความยาวลำดับและ batch ผลลัพธ์เป็นแท่งซ้อน (น้ำหนัก / optimizer / gradient / activation / KV) เทียบกับเส้น GPU ที่เลือก (24 / 48 / 80 GB) เปลี่ยนสีแดงเมื่อเกิน ให้ผู้เรียนลองหาว่าจะยัด 35B-A3B QLoRA ลง 48 GB ได้ที่ความยาวลำดับเท่าไร

## 5.13 ระดับนักวิจัย: คำถามที่ยังเปิดอยู่

1. **Attention เต็มจำเป็นแค่ไหน?** Qwen3.6 ใช้ Gated DeltaNet (linear attention ที่ต้นทุนไม่โตตาม n²) สลับกับ attention เต็มในอัตรา 3:1 [15] DeepSeek-V3 ใช้ Multi-head Latent Attention บีบ KV cache [34] คำถามเปิดคือส่วนผสมไหนรักษาความสามารถ "ค้นกลับไปดูของไกล" (needle-in-haystack) ได้ในขณะที่ลดต้นทุน สำหรับงานเราที่ visual token 3,796 + JSON ยาว นี่กระทบตรง ๆ
2. **Scaling law ของข้อมูลเฉพาะทาง**: Chinchilla [24] วัดกับข้อความทั่วไป ไม่มีใครรู้ว่าสำหรับ "แบบก่อสร้างไทย → JSON" อัตรา token ต่อพารามิเตอร์ที่เหมาะสมคือเท่าไร dataset ~1,000 ตัวอย่างต่อ fold ของ t05 อยู่ไกลจากทุกสูตร และ LoRA เปลี่ยนสมการอีก
3. **Emergence จริงหรือตัววัด?** [25] vs [26] ยังไม่จบ สำหรับเรา element recall เป็นตัววัดไม่ต่อเนื่อง การเพิ่มตัววัดต่อเนื่อง (เช่น per-token log-likelihood ของ JSON ground truth) อาจทำให้เห็นความก้าวหน้าระหว่างรอบทูนที่ recall ยังไม่ขยับ
4. **MoE กับ fine-tuning ข้อมูลน้อย**: expert ละเอียด 256 ตัว [33] แต่ละตัวเห็น token จาก dataset เล็ก ๆ ของเราน้อยมาก มีงานเสนอ upcycle dense เป็น MoE [36] และหลายงานรายงานว่า MoE ไม่เสถียรกว่า dense ตอน post-training ตำแหน่งที่ควรแปะ LoRA บน MoE ยังเป็นคำถามเชิงประจักษ์
5. **Tokenizer ที่เป็นธรรมกับภาษา**: งานปี 2026 เทียบ tokenizer 11 ภาษาเอเชียตะวันออกเฉียงใต้ [4] และคำถามที่ตามมาคือ ถ้าเปลี่ยน tokenizer ของโมเดลที่ pretrain แล้ว จะต้อง pretrain ต่ออีกเท่าไรจึงคุ้ม สำหรับ JSON ของเรา คำถามที่ปฏิบัติได้กว่าคือออกแบบ schema ให้ token น้อย (key สั้น, เลขจำนวนเต็มเป็น mm แทนทศนิยมเป็น m)

## 5.14 แบบฝึกหัด

**ข้อ 1 (คิด)** ทำไม `0.20` ถึงกิน 4 token แต่ `20` กิน 1-2 token ถ้าเปลี่ยน schema ของเราให้ใช้หน่วย mm (เช่น `200`) แทน m (`0.20`) กับคาน 60 ตัว หน้าละ 4 ค่าตัวเลข จะประหยัดกี่ token โดยประมาณ

<details><summary>เฉลย</summary>
BPE ของ Qwen หั่นตัวเลขทีละหลักและจุดเป็น token แยก `0.20` = '0','.','2','0' = 4 token; `200` = 3 หลัก ≈ 3 token (บางกรณี 1-2 ถ้ามี merge) ประหยัดอย่างน้อย 1 token ต่อค่า × 4 ค่า × 60 คาน = 240 token ต่อหน้า และประหยัดเวลา decode เชิงเส้นตามนั้น รวมถึงลดโอกาส truncate ที่ max_length
</details>

**ข้อ 2 (คำนวณ)** จากตัวอย่าง 5.4.3 เปลี่ยน $W_V$ เป็นเมทริกซ์เอกลักษณ์ คำนวณแถวที่ 3 ของผลลัพธ์ $Z$ (ใช้น้ำหนัก A แถว 3 = (0.248, 0.248, 0.503))

<details><summary>เฉลย</summary>
V = X = [[1,0],[0,1],[1,1]] ดังนั้น Z₃ = 0.248×(1,0) + 0.248×(0,1) + 0.503×(1,1) = (0.751, 0.751) token ที่ 3 ได้เวกเตอร์ที่เป็นค่าเฉลี่ยถ่วงน้ำหนักของทุก token โดยหนักไปทางตัวเอง
</details>

**ข้อ 3 (คำนวณ)** Qwen3-VL-32B ที่ bf16 ต้องการ VRAM สำหรับน้ำหนักเท่าไร ถ้าใช้ QLoRA 4-bit (≈0.55 byte/param) เท่าไร และถ้าลำดับยาว 12,000 token กับ KV cache ที่ 64 ชั้น, 8 หัว KV, 128 มิติ, bf16 จะกิน cache เพิ่มกี่ GB

<details><summary>เฉลย</summary>
bf16: 32×10⁹×2 = 64 GB; 4-bit: 32×10⁹×0.55 ≈ 17.6 GB; KV: 2×64×8×128×2 = 262 KB/token × 12,000 = 3.1 GB (ตัวเลขชั้น/หัวเป็นตัวอย่างสมมติสำหรับฝึกคำนวณ ตรวจค่าจริงจาก config.json ของโมเดล)
</details>

**ข้อ 4 (รันโค้ด)** แก้โค้ด 5.4.4 ให้ใช้ d = 4096 (มิติของ Qwen3-8B) และดูว่าถ้าไม่หาร √d น้ำหนัก softmax จะเป็นอย่างไร แล้วอธิบายว่าทำไม gradient จะไหลไม่ได้

<details><summary>เฉลย</summary>
std ของคะแนนดิบ ≈ 64 softmax จะเป็น one-hot (1 ที่ค่าสูงสุด 0 ที่เหลือ) อนุพันธ์ของ softmax ที่จุดอิ่มตัวคือ p(1-p) ≈ 0 ทุกตัว gradient ที่ส่งกลับไป W_Q, W_K จึงเกือบศูนย์ โมเดลไม่เรียนรู้ การหาร √d ทำให้ std กลับมาใกล้ 1
</details>

**ข้อ 5 (คิด)** โมเดล MoE 35B/3B กับ dense 8B ที่ VRAM 24 GB แบบไหน inference ได้ และแบบไหนเร็วกว่าถ้าทั้งคู่โหลดได้

<details><summary>เฉลย</summary>
dense 8B ที่ bf16 = 16 GB โหลดได้ MoE 35B ที่ bf16 = 70 GB โหลดไม่ได้ ต้องลดเป็น 4-bit (~19 GB) จึงพอดี ถ้าโหลดได้ทั้งคู่ MoE จะ decode เร็วกว่าเพราะคำนวณแค่ 3B ต่อ token (memory-bound: อ่านน้ำหนักน้อยกว่า) แต่ต้องแลกกับความเสี่ยง OOM จาก activation ที่ไม่คงที่ตามการเลือก expert
</details>

## สรุปบทนี้ใน 5 บรรทัด

1. ข้อความถูกหั่นเป็น subword token ด้วย BPE ที่ตัวหนังสือไทยและตัวเลขทศนิยมแพงกว่าอังกฤษ และภาพก็ถูกแปลงเป็น token ในลำดับเดียวกัน `max_length` คือผลรวมทั้งหมด
2. token แต่ละตัวเป็นเวกเตอร์ในปริภูมิความหมาย (embedding) ที่ทิศทางมีความหมาย และ self-attention ให้แต่ละ token ดึงข้อมูลจาก token อื่นตามน้ำหนัก softmax(QKᵀ/√d)V
3. Transformer = attention + FFN + residual + norm ซ้อนหลายสิบชั้น พร้อม RoPE บอกตำแหน่ง และ causal mask ทำให้ decoder-only เทรนด้วย next-token prediction จากข้อความดิบได้โดยไม่ต้องติดป้าย
4. ใหญ่ขึ้นแล้ว loss ลดตาม power law (Kaplan, Chinchilla) แต่ "ความสามารถโผล่กะทันหัน" ส่วนหนึ่งเป็นผลจากตัววัดที่ไม่เชิงเส้น
5. ตอนใช้งาน decode เป็น memory-bound O(n) ต่อ token ผ่าน KV cache (JSON ยาว = ช้าเชิงเส้น) และ MoE ให้ความจุ 35B ในราคาคำนวณ 3B แต่ VRAM ต้องรับทั้ง 35B และเทรนไม่เสถียรกว่า dense
