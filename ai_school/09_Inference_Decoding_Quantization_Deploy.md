## 9.0 คำถามเปิด (ผูกกับงานจริงของเรา)

รอบ t02 เราทูน Qwen3-VL-8B เสร็จ โหลดโมเดลขึ้นมา ตั้ง `do_sample=False` เพราะคิดว่า "งานถอดแบบต้องการคำตอบที่แน่นอน ไม่ควรสุ่ม" ผลคือโมเดลพิมพ์ `"B2", "B2", "B2", ...` วนไม่รู้จบ บางหน้าหลุดเป็นภาษาจีน recall นับคานได้ 0 จาก 34 ต้น

จากนั้นเราไปอ่านเอกสารของ Qwen พบข้อความชัดเจนว่า "DO NOT use greedy decoding, as it can lead to performance degradation and endless repetitions" และแนะนำ temperature=0.7, top_p=0.8, top_k=20 [4][5] พอเปลี่ยนตาม แล้วเพิ่ม xgrammar บังคับให้ออกเป็น JSON, ใส่ repetition_penalty และ timeout โมเดลก็กลับมาทำงานได้

คำถามที่บทนี้จะตอบคือ: ทำไมโมเดล "เดียวกัน น้ำหนักเดียวกัน" ถึงให้ผลต่างกันขนาดนั้นเพียงเพราะวิธีเลือก token ต่างกัน และในทางกลับกัน ทำไมการบีบโมเดลให้เล็กลง (quantize) ซึ่ง "เปลี่ยนน้ำหนัก" ถึงทำให้เราวัดผลผิดโดยไม่รู้ตัว (บั๊กข้อ 2 และ 3 ในรายการของเรา)

เปรียบกับงานโยธา: โมเดลที่ทูนเสร็จคือ "แบบก่อสร้าง" ส่วน decoding, quantization และ serving engine คือ "ผู้รับเหมา เครื่องมือ และวัสดุหน้างาน" แบบดีแค่ไหน ถ้าหน้างานเทคอนกรีตผิดสูตร โครงสร้างก็ไม่ได้กำลังตามแบบ บทนี้ว่าด้วยหน้างาน

## 9.1 Inference คือ forward pass ทีละ token (autoregressive)

### ขั้นที่ 1: โมเดลไม่ได้ "เขียนประโยค" มันทำนายแค่ token ถัดไป

ตอนใช้งาน โมเดลภาษารับลำดับ token ที่มีอยู่แล้ว (prompt + สิ่งที่มันพิมพ์ไปแล้ว) แล้วคืนค่า "คะแนนดิบ" ของ token ถัดไปทุกตัวในคลังคำ (vocabulary) คะแนนดิบนี้เรียกว่า logits เป็นเวกเตอร์ยาวเท่าจำนวนคำในคลัง (Qwen มีคลังประมาณ 150,000 token) จากนั้นระบบเลือก token หนึ่งตัว ต่อท้ายลำดับ แล้ววนกลับไปทำใหม่ วิธีนี้เรียกว่า autoregressive generation คือ "ผลลัพธ์รอบก่อนเป็นอินพุตรอบถัดไป" [18]

$$
p(x_1, x_2, \dots, x_N) = \prod_{t=1}^{N} p(x_t \mid x_1, \dots, x_{t-1})
$$

- $x_t$ คือ token ตัวที่ $t$
- $p(x_t \mid x_{<t})$ คือความน่าจะเป็นของ token ตัวที่ $t$ เมื่อรู้ทุกตัวก่อนหน้า (นี่คือสิ่งเดียวที่โมเดลคำนวณ)
- ผลคูณทั้งหมดคือความน่าจะเป็นของทั้งประโยค

เทียบกับงานโยธา: เหมือนการวิเคราะห์โครงสร้างแบบ step-by-step ที่ค่าแรงในชั้นที่ 3 ขึ้นกับผลของชั้น 1 และ 2 คุณคำนวณข้ามชั้นไม่ได้ ต้องไล่ทีละชั้น นี่คือเหตุผลที่ LLM "ช้า" ตอนถอดเต็มหน้า: JSON 2,000 token = forward pass 2,000 รอบ

### ขั้นที่ 2: logits → softmax → probability

logits เป็นตัวเลขจริงใด ๆ (ติดลบได้) ยังไม่ใช่ความน่าจะเป็น softmax แปลงให้เป็นความน่าจะเป็นที่รวมกันได้ 1:

$$
p_i = \frac{e^{z_i}}{\sum_{j=1}^{V} e^{z_j}}
$$

- $z_i$ คือ logit ของ token $i$
- $V$ คือขนาดคลังคำ
- $p_i$ คือความน่าจะเป็นที่ token $i$ จะถูกเลือก

ตัวอย่างเล็ก ๆ 3 token: สมมติหลังจากพิมพ์ `"beam_id": "` โมเดลให้ logits ของ `B1`, `B2`, `C1` เป็น $z = [2.0, 1.0, 0.5]$

- $e^{2.0} = 7.389$, $e^{1.0} = 2.718$, $e^{0.5} = 1.649$ รวม $= 11.756$
- $p = [0.629, 0.231, 0.140]$

โมเดล "ค่อนข้างมั่นใจ" ว่าเป็น B1 แต่ไม่ถึงกับแน่ใจ นี่คือข้อมูลที่ decoding ต้องตัดสินใจต่อ

🎨 **ภาพที่จะวาดใน HTML:** แถบแนวนอน 3 แถบชื่อ B1 / B2 / C1 ด้านซ้ายเป็น logits (สไลเดอร์ปรับได้ตัวละตัว ช่วง -3 ถึง 5) ด้านขวาเป็น probability หลัง softmax (แถบยาวตามค่า รวม = 1 เสมอ) เมื่อผู้เรียนลาก logit ของ B2 ขึ้น ต้องเห็นแถบ B1 และ C1 หดลงพร้อมกัน เพื่อให้เข้าใจว่า softmax เป็นการ "แบ่งเค้กก้อนเดียว" ไม่ใช่คะแนนอิสระ

```python
import numpy as np
z = np.array([2.0, 1.0, 0.5])          # logits ของ B1, B2, C1
p = np.exp(z) / np.exp(z).sum()
print("prob:", p.round(3), "sum:", p.sum().round(3))
# prob: [0.629 0.231 0.14 ] sum: 1.0
```

## 9.2 Greedy vs Sampling และทำไม greedy ทำให้วนซ้ำ

### ขั้นที่ 1: greedy คือเลือกตัวที่ probability สูงสุดเสมอ

`do_sample=False` ใน transformers คือ greedy search: ทุกก้าวเลือก $\arg\max_i p_i$ [3] จากตัวอย่างข้างบนคือเลือก B1 เสมอ ฟังดูสมเหตุสมผลสำหรับงานที่ต้องการความแน่นอน แต่มีปัญหาสองชั้น

**ปัญหาชั้นแรก: greedy ไม่ได้ให้ประโยคที่มี probability สูงสุด** การเลือกตัวดีที่สุด ณ แต่ละก้าว ไม่รับประกันว่าผลคูณตลอดทั้งลำดับจะสูงสุด (เหมือนการออกแบบให้แต่ละคานเบาที่สุดทีละต้น ไม่ได้ให้โครงสร้างรวมประหยัดที่สุด) เอกสาร transformers เองระบุว่า greedy "breaks down when generating longer sequences because it begins to repeat itself" [3]

**ปัญหาชั้นที่สอง: วงจรป้อนกลับของการซ้ำ (degeneration)** Holtzman และคณะ (2019) ศึกษาเรื่องนี้โดยตรงในเปเปอร์ "The Curious Case of Neural Text Degeneration" [1] ข้อค้นพบสำคัญคือ ข้อความที่ "มี likelihood สูง" ตามโมเดล กลับเป็นข้อความที่ซ้ำซากและไม่เหมือนที่มนุษย์เขียน และเมื่อโมเดลเผลอพิมพ์ซ้ำครั้งหนึ่ง probability ของการซ้ำครั้งถัดไปยิ่งสูงขึ้น (เพราะบริบทตอนนี้ "เต็มไปด้วยการซ้ำ") greedy จึงติดกับดักตัวเอง: `B2` → บริบทมี B2 เยอะ → B2 ยิ่งน่าจะเป็น → `B2` อีก

นี่คือคำอธิบายทางทฤษฎีของบั๊กข้อ 4 ของเรา รายการคานในบ้านจริงมีชื่อซ้ำกันอยู่แล้ว (B1, B2 หลายต้น) พอบริบทเต็มไปด้วย `"B2"` greedy จึงไม่มีทางหลุด และไม่มีกลไกสุ่มมาช่วยกระโดดออก ส่วนอาการ "หลุดภาษาจีน" เป็นอาการที่ตัวโมเดล Qwen เตือนไว้เองว่าเกิดกับ greedy [4] เพราะ token ภาษาจีนมี probability ตามหลังใกล้ ๆ กันหลายตัวในโมเดลที่เทรนด้วยข้อมูลจีน-อังกฤษ เมื่อบริบทเพี้ยนเล็กน้อย argmax เปลี่ยนไปเลือกฝั่งนั้นแล้วไม่กลับ

### ขั้นที่ 2: sampling คือสุ่มตาม probability

`do_sample=True` คือสุ่มเลือก token ตามการแจกแจง $p$ [3] จากตัวอย่าง B1 จะถูกเลือก 62.9% ของครั้ง, B2 23.1%, C1 14.0% ข้อดีคือหลุดจากวงจรซ้ำได้ ข้อเสียคือ "หาง" ของการแจกแจง (token ที่ probability ต่ำมากแต่มีเป็นแสนตัว) รวมกันแล้วมีโอกาสถูกเลือกไม่น้อย ทำให้ออกคำเพี้ยน ทางแก้คือตัดหางทิ้ง ซึ่งเป็นที่มาของ temperature, top-k, top-p ในหัวข้อถัดไป

🎨 **ภาพที่จะวาดใน HTML:** จำลองการพิมพ์ JSON รายการคาน 20 token มีปุ่มสลับ "greedy" / "sampling" ด้านล่างแสดงแถบ probability ของ token ถัดไป (แสดง 8 ตัวบนสุด) เมื่อกด greedy ให้เห็นว่าหลังพิมพ์ B2 ครั้งที่ 2 แถบ B2 สูงขึ้นทุกก้าวจนออกมาเป็น `B2, B2, B2...` เมื่อกด sampling ให้เห็นตัวเลือกกระโดดออกได้ และมี counter นับ "จำนวนครั้งที่ซ้ำติดกัน" เทียบสองโหมด

```python
import numpy as np
rng = np.random.default_rng(0)
vocab = ["B1", "B2", "C1"]
p = np.array([0.629, 0.231, 0.140])
greedy = vocab[p.argmax()]
samples = rng.choice(vocab, size=20, p=p)
print("greedy ทุกครั้ง:", greedy)
print("sampling 20 ครั้ง:", " ".join(samples))
print("สัดส่วน B1:", (samples == "B1").mean())
```

## 9.3 Temperature: หมุนปุ่ม "ความมั่นใจ" ของโมเดล

### ขั้นที่ 1: สูตร

Temperature $T$ หาร logits ก่อนเข้า softmax:

$$
p_i(T) = \frac{e^{z_i / T}}{\sum_j e^{z_j / T}}
$$

- $T \to 0$: ตัวที่สูงสุดกินทั้งหมด (เข้าใกล้ greedy)
- $T = 1$: การแจกแจงเดิมของโมเดล
- $T > 1$: แบนลง ทุกตัวใกล้เคียงกัน (สุ่มมากขึ้น)

### ขั้นที่ 2: คำนวณให้ดูจริงด้วย 3 token เดิม $z = [2.0, 1.0, 0.5]$

| $T$ | $z/T$ | $e^{z/T}$ | $p$ (B1, B2, C1) |
|---|---|---|---|
| 0.1 | [20, 10, 5] | [4.85×10⁸, 22026, 148] | [1.000, 0.000, 0.000] |
| 0.7 | [2.857, 1.429, 0.714] | [17.41, 4.17, 2.04] | [0.737, 0.177, 0.086] |
| 1.0 | [2.0, 1.0, 0.5] | [7.39, 2.72, 1.65] | [0.629, 0.231, 0.140] |
| 1.5 | [1.333, 0.667, 0.333] | [3.79, 1.95, 1.40] | [0.532, 0.273, 0.195] |

สังเกตว่าที่ $T=0.1$ ผลเท่ากับ greedy ในทางปฏิบัติ ที่ $T=0.7$ (ค่าที่ Qwen แนะนำสำหรับงาน VL [5][6]) โมเดลยัง "เอนไปทางตัวที่มั่นใจ" แต่เปิดช่อง 26% ให้ตัวอื่นเพื่อหลุดจากวงจรซ้ำ

เทียบกับงานโยธา: $T$ เหมือน safety factor ในทิศกลับ ค่าต่ำ = เชื่อการคำนวณของตัวเองเต็มที่ ค่าสูง = เผื่อความไม่แน่นอนกว้าง ๆ งานถอดแบบไม่ต้องการ "ความคิดสร้างสรรค์" แต่ต้องการ "ไม่ติดกับดัก" จึงใช้ค่ากลาง ๆ

🎨 **ภาพที่จะวาดใน HTML:** สไลเดอร์ $T$ ตั้งแต่ 0.05 ถึง 2.0 ด้านซ้ายกราฟแท่ง probability ของ 8 token (logits คงที่) ด้านขวาแสดงตัวเลขตาราง 3 แถวเหมือนข้างบนแบบ live เมื่อลาก $T$ ต่ำ ๆ ต้องเห็นแท่งเดียวพุ่งขึ้นและตัวอื่นหาย เมื่อลากสูงต้องเห็นทุกแท่งใกล้เคียงกัน มีเส้นประทำเครื่องหมายที่ $T=0.7$ พร้อมข้อความ "ค่าที่ Qwen แนะนำสำหรับงาน VL"

```python
import numpy as np
z = np.array([2.0, 1.0, 0.5])
for T in [0.1, 0.7, 1.0, 1.5]:
    p = np.exp(z / T) / np.exp(z / T).sum()
    print(f"T={T:<4} p={p.round(3)}")
```

## 9.4 Top-k, Top-p (nucleus) และ min-p: ตัดหางของการแจกแจง

### ขั้นที่ 1: top-k คือเก็บแค่ k ตัวบนสุด

เรียง token ตาม probability เก็บ $k$ ตัวแรก ตั้งที่เหลือเป็นศูนย์ แล้ว normalize ใหม่ ปัญหาคือ $k$ คงที่ไม่รู้บริบท: บางจังหวะโมเดลมั่นใจมาก (ตัวเดียวควรพอ) บางจังหวะไม่มั่นใจเลย (ควรเปิดกว้าง 100 ตัว) [1][2]

### ขั้นที่ 2: top-p (nucleus sampling) คือเก็บตัวบนสุดจนสะสม probability ถึง p

Holtzman และคณะเสนอ nucleus sampling ใน [1]: เลือกเซตเล็กที่สุด $V^{(p)}$ ที่

$$
\sum_{i \in V^{(p)}} p_i \geq p
$$

แล้วสุ่มในเซตนั้น ขนาดเซตจึงปรับตามความมั่นใจของโมเดลอัตโนมัติ ตัวอย่างจาก $p = [0.629, 0.231, 0.140]$ ที่ $p=0.8$: B1 สะสม 0.629 ยังไม่ถึง, B1+B2 = 0.860 ถึงแล้ว ดังนั้น nucleus = {B1, B2} ตัด C1 ทิ้ง แล้ว normalize เป็น [0.731, 0.269]

Qwen แนะนำ top_p=0.8, top_k=20 ใช้คู่กัน [5][6]: top_k=20 เป็นเพดานแข็งกันหางยาว top_p=0.8 เป็นตัวปรับตามบริบท

### ขั้นที่ 3: min-p (งานใหม่ 2024-2025)

Nguyen และคณะ (ICLR 2025) เสนอ min-p: ตัด token ที่ probability ต่ำกว่า $p_{\min} \times p_{\max}$ (สัดส่วนของตัวที่สูงสุด) [7] ข้อดีคือทนต่อ temperature สูงกว่า top-p Qwen ตั้ง MinP=0 เป็นค่าเริ่มต้น [4] จึงเป็นตัวเลือกเสริม ไม่ใช่ค่าที่เราต้องใช้

🎨 **ภาพที่จะวาดใน HTML:** กราฟแท่ง probability 15 token เรียงจากสูงไปต่ำ มีสไลเดอร์สามตัว: top-k (1-15), top-p (0.1-1.0), min-p (0-0.5) แท่งที่ "รอด" เป็นสีเข้ม แท่งที่ถูกตัดเป็นสีจาง มีเส้นสะสม (cumulative) วาดทับ เมื่อลาก top-p ต้องเห็นจุดตัดเลื่อนตามเส้นสะสม ปุ่ม "สลับบริบท" ให้เปลี่ยนชุด logits ระหว่าง "มั่นใจ" (แท่งเดียวสูง) กับ "ไม่มั่นใจ" (แบน) เพื่อให้เห็นว่า top-k ตัดจำนวนเท่าเดิมทั้งสองกรณี แต่ top-p ปรับจำนวนเอง

```python
import numpy as np
p = np.array([0.629, 0.231, 0.140])
names = ["B1", "B2", "C1"]
order = np.argsort(-p); cum = np.cumsum(p[order])
keep = order[: (cum >= 0.8).argmax() + 1]          # top-p = 0.8
q = np.zeros_like(p); q[keep] = p[keep]; q /= q.sum()
print("nucleus:", [names[i] for i in keep], "→ p ใหม่:", q.round(3))
```

## 9.5 Repetition penalty, no_repeat_ngram และเกณฑ์หยุด

### ขั้นที่ 1: ลงโทษ token ที่เคยออกแล้ว

transformers มี `repetition_penalty` (ตัวคูณ/หาร logit ของ token ที่เคยปรากฏ ค่า > 1 คือลงโทษ) และ `no_repeat_ngram_size` (ห้าม n-gram ใด ๆ ซ้ำเป็นครั้งที่สอง) [3] ส่วน Qwen3-VL แนะนำ `presence_penalty=1.5` ซึ่งลบค่าคงที่ออกจาก logit ของ token ที่เคยเห็น [6]

ข้อควรระวังสำหรับงานเรา: JSON ต้องซ้ำโครงสร้างโดยธรรมชาติ (`"beam_id":` ปรากฏทุกต้น) `no_repeat_ngram_size` จึงอันตรายมาก เพราะจะห้ามพิมพ์ `"beam_id": "` ครั้งที่สอง ค่าที่ควรใช้คือ penalty แบบอ่อน ๆ ร่วมกับ sampling ไม่ใช่การห้ามซ้ำแบบเด็ดขาด

### ขั้นที่ 2: เกณฑ์หยุด (stopping criteria)

โมเดลหยุดเมื่อ (ก) พิมพ์ token พิเศษ EOS (end of sequence) หรือ (ข) ถึง `max_new_tokens` หรือ (ค) เจอ stop string ที่เรากำหนด [3] ถ้าไม่ตั้ง `max_new_tokens` ไว้ transformers ใช้ค่าเริ่มต้นเพียง 20 token [3] (นี่คือตัวอย่างชั้นดีของบั๊กข้อ 5: "ค่าที่ไม่ได้ตั้ง" พลิกผล) ส่วน timeout ระดับ process เป็นเข็มขัดนิรภัยชั้นสุดท้าย เพราะโมเดลที่วนซ้ำจะไม่มีวันพิมพ์ EOS

🎨 **ภาพที่จะวาดใน HTML:** ไทม์ไลน์แนวนอนแสดง token ที่พิมพ์ออกมาทีละตัว มีสวิตช์ 3 ตัว: repetition_penalty (1.0-1.5), max_new_tokens (50-4000), timeout (5-120 วิ) ด้านบนมีแถบ "งบ token ที่เหลือ" ลดลงเรื่อย ๆ เมื่อปิด penalty และตั้ง max สูง ต้องเห็นไทม์ไลน์ยาวเต็มไปด้วย B2 จนชนขอบ เมื่อเปิด penalty ต้องเห็น EOS โผล่ก่อนถึงขอบ

## 9.6 Constrained decoding: บังคับรูปแบบด้วยการ mask logits

### ขั้นที่ 1: หลักการ

ระหว่าง decode ทุกก้าว ก่อน softmax เราสามารถตั้ง logit ของ token ที่ "ผิดไวยากรณ์ ณ ตำแหน่งนี้" เป็น $-\infty$ ได้ ทำให้ probability เป็น 0 โมเดลจึงเลือกได้เฉพาะ token ที่ทำให้ผลลัพธ์ยังคงเป็น JSON ที่ถูกต้อง Willard และ Louf (2023) แสดงว่าปัญหานี้แปลงเป็น finite-state machine ได้ และสร้าง index ของคลังคำล่วงหน้าเพื่อให้ mask เร็ว (ไลบรารี Outlines) [8] XGrammar (Dong และคณะ 2024) ขยายไปสู่ context-free grammar โดยแยก token เป็น "ตรวจล่วงหน้าได้" กับ "ต้องตรวจตอนรัน" และซ้อนการคำนวณ grammar กับ GPU ให้ overhead ใกล้ศูนย์ [9] llama.cpp ใช้แนวคิดเดียวกันผ่านไวยากรณ์ GBNF [10] และ vLLM รองรับ xgrammar เป็น backend สำหรับ JSON schema / regex / grammar [11]

ตัวอย่าง: หลังพิมพ์ `{"beams": [` ไวยากรณ์ JSON อนุญาตเฉพาะ `{`, `]`, ช่องว่าง token อย่าง `B2` หรือตัวอักษรจีนถูก mask ทิ้งทันที นี่คือเหตุผลที่ xgrammar แก้อาการ "หลุดภาษาจีน" ได้ในทันที: ไม่ใช่เพราะโมเดลฉลาดขึ้น แต่เพราะทางเลือกผิด ๆ ถูกปิด

### ขั้นที่ 2: ขีดจำกัดที่ต้องรู้

- **บังคับรูปแบบ ไม่ได้บังคับความถูกต้อง** grammar รับประกันว่า `"beam_id"` จะมีค่าเป็นสตริง แต่ไม่รับประกันว่าคานต้นนั้นมีอยู่จริงในแบบ
- **บังคับความยาวไม่ได้** ถ้า schema อนุญาต array ไม่จำกัด โมเดลยังวนสร้าง `{"beam_id":"B2"}` ซ้ำได้ตลอดไปในรูปแบบที่ถูกต้อง 100% นี่คือเหตุผลที่เรายังต้องมี repetition_penalty และ timeout ควบคู่
- **อาจกดความสามารถในการคิด** Tam และคณะ (2024) พบว่าการบังคับรูปแบบเข้มงวดทำให้ผลงานเชิงเหตุผลของ LLM ตกลง [12] สำหรับงานถอดแบบซึ่งเป็นการ "อ่านแล้วคัดลอก" มากกว่า "ให้เหตุผล" ผลกระทบน่าจะน้อยกว่า แต่ยังไม่มีใครวัดกับงานแบบเราโดยตรง (ดู 9.y)

🎨 **ภาพที่จะวาดใน HTML:** ช่องพิมพ์ JSON ที่กำลังงอกทีละ token ด้านล่างแสดง logits 12 ตัวบนสุด ช่องติ๊ก "เปิด grammar" เมื่อเปิด token ที่ผิดไวยากรณ์ ณ ตำแหน่งนั้นถูกขีดฆ่าและแถบยุบเป็นศูนย์ (แสดง $-\infty$) และ probability ที่เหลือถูก normalize ใหม่ มีฉากสาธิตสองฉาก: "หลุดภาษาจีน" (ถูกแก้เมื่อเปิด grammar) และ "วน B2 ในรูปแบบถูกต้อง" (ไม่ถูกแก้ ต้องพึ่ง penalty) เพื่อสอนขีดจำกัด

```python
import numpy as np
vocab = ['"', '{', ']', 'B2', '梁']            # 梁 = คาน (จีน)
z = np.array([1.2, 0.9, 0.3, 1.5, 1.4])
allowed = np.array([1, 1, 1, 0, 0], bool)     # หลัง '[' JSON อนุญาตแค่ 3 ตัวแรก
z_masked = np.where(allowed, z, -np.inf)
p = np.exp(z_masked - z_masked.max()); p /= p.sum()
print(dict(zip(vocab, p.round(3))))
```

## 9.7 KV cache, prefill vs decode และทำไม classify เร็วกว่าถอดเต็ม

### ขั้นที่ 1: KV cache คือการไม่คำนวณซ้ำ

ใน attention (บทที่ 3) token ทุกตัวต้องคำนวณเวกเตอร์ Key และ Value ถ้าเราคำนวณใหม่ทั้งลำดับทุกครั้งที่งอก 1 token ต้นทุนจะโตเป็น $O(N^2)$ ทางแก้คือเก็บ K และ V ของ token เก่าไว้ในหน่วยความจำ GPU เรียกว่า KV cache แล้วคำนวณเฉพาะ token ใหม่ [17] ราคาที่ต้องจ่ายคือ VRAM:

$$
\text{KV bytes/token} = 2 \times L \times H_{kv} \times d_{head} \times b
$$

- 2 คือ K และ V
- $L$ จำนวน layer, $H_{kv}$ จำนวน KV head, $d_{head}$ มิติต่อ head, $b$ ไบต์ต่อค่า (bf16 = 2)

ตัวอย่างสมมติ (ไม่ใช่สเปกโมเดลใดโดยเฉพาะ): $L=32$, $H_{kv}=8$, $d_{head}=128$, bf16 → $2 \times 32 \times 8 \times 128 \times 2 = 131{,}072$ ไบต์ = 128 KB ต่อ token ถ้าหนึ่งหน้าแบบใช้ 3,796 visual token + prompt + JSON 3,000 token ≈ 7,000 token → KV ≈ 0.9 GB ต่อหนึ่งคำขอ นอกเหนือจากน้ำหนักโมเดล และถ้ารันหลายหน้าพร้อมกัน ตัวเลขนี้คูณจำนวนคำขอ นี่คือหนึ่งในต้นตอของ OOM บน GPU เช่า (บั๊กข้อ 7) ที่ไม่ได้มาจากน้ำหนักโมเดลอย่างเดียว

### ขั้นที่ 2: prefill กับ decode เป็นคนละงาน

- **Prefill**: ประมวลผล prompt ทั้งหมด (รวม visual token ทุกตัว) ในหนึ่ง forward pass ใหญ่ เป็นการคูณเมทริกซ์ก้อนโต GPU ทำงานเต็มกำลัง (compute-bound)
- **Decode**: งอกทีละ token แต่ละก้าวต้อง "อ่านน้ำหนักโมเดลทั้งก้อน" ออกจาก VRAM เพื่อคำนวณ token เดียว จึงถูกจำกัดด้วยแบนด์วิดท์หน่วยความจำ (memory-bound) ไม่ใช่กำลังคำนวณ

Agrawal และคณะ (2023) สรุปไว้ตรง ๆ ว่า prefill อิ่มตัวกำลังคำนวณของ GPU ตั้งแต่ batch เล็ก ส่วน decode ใช้กำลังคำนวณต่ำ [15]

ตอนนี้ตอบคำถามจากงานเราได้:

- **ทำไมภาพใหญ่ prefill ช้า**: หน้าแบบ 3309×2339 px ถูกหั่นเป็น visual token ประมาณ 3,796 ตัว (Qwen3-VL ใช้ 1 token ต่อพื้นที่ 32×32 px [5]) prefill ต้องคำนวณ attention ของ token เหล่านี้ทั้งหมด ต้นทุน attention โตตามกำลังสองของจำนวน token
- **ทำไม pass0 classify เร็วกว่าถอดเต็มประมาณ 7 เท่า**: prefill เท่ากัน (ภาพเดียวกัน) แต่ classify ออกแค่ไม่กี่ token ("beam_plan") ส่วนถอดเต็มออกหลายพัน token และทุก token คือหนึ่งรอบ decode ที่ต้องอ่านน้ำหนักทั้งโมเดล เวลารวมจึงถูกครอบงำด้วยความยาวของ output ไม่ใช่ input นี่คือเหตุผลเชิงระบบที่ t03 แยกเป็นหลาย pass คุ้ม: จ่ายค่า prefill ซ้ำหลายรอบ แต่ตัด output ที่ไม่จำเป็นออก

🎨 **ภาพที่จะวาดใน HTML:** แผนภูมิเวลาแนวนอนสองแถว "classify" กับ "ถอดเต็ม" แต่ละแถวมีบล็อก prefill (สีหนึ่ง กว้างตามจำนวน visual token) ตามด้วยบล็อก decode เล็ก ๆ ต่อกัน (บล็อกละ 1 token) สไลเดอร์สองตัว: ขนาดภาพ (512-3309 px → จำนวน visual token) และความยาว output (5-3000 token) ด้านล่างมีมิเตอร์ VRAM ของ KV cache ที่โตตาม token ทั้งหมด ผู้เรียนควรเห็นว่าขยายภาพทำให้ prefill ยาวขึ้นทั้งสองแถวเท่ากัน แต่ตัวที่ทำให้แถว "ถอดเต็ม" ยาวกว่า 7 เท่าคือหาง decode

```python
# แบบจำลองต้นทุนหยาบ ๆ: prefill ~ N_in^2 (attention), decode ~ N_out * (อ่านน้ำหนัก)
def est_time(n_in, n_out, c_pre=1e-7, c_dec=0.02):
    return c_pre * n_in**2 + c_dec * n_out
for name, n_out in [("classify", 5), ("ถอดเต็ม", 2500)]:
    t = est_time(3796 + 200, n_out)
    print(f"{name:8s} out={n_out:5d} token  →  {t:6.1f} s (จำลอง)")
```

## 9.8 Batching และ continuous batching

### ขั้นที่ 1: ทำไมต้อง batch

เพราะ decode เป็น memory-bound การอ่านน้ำหนักทั้งโมเดลหนึ่งครั้งเพื่อคำนวณ token เดียวคือความสิ้นเปลือง ถ้าอ่านหนึ่งครั้งแล้วคำนวณให้ 16 คำขอพร้อมกัน ต้นทุนต่อ token ลดลงเกือบ 16 เท่า นี่คือ batching

### ขั้นที่ 2: static batching เสียเวลารอ

ถ้าจัด batch เป็น "คำขอ" ทั้งก้อน คำขอที่สั้น (classify) ต้องรอคำขอยาว (ถอดเต็ม) จบก่อนถึงจะปล่อยที่ Yu และคณะ (OSDI 2022) เสนอ Orca ที่จัดตารางระดับ "iteration" แทน: ทุกก้าว decode ระบบตรวจว่ามีคำขอไหนจบแล้ว ถอดออก แล้วยัดคำขอใหม่เข้ามาแทนทันที [14] วิธีนี้ถูกเรียกว่า continuous batching และเป็นหัวใจของ vLLM

### ขั้นที่ 3: PagedAttention จัดการ KV cache เหมือน OS จัดการ RAM

ปัญหาถัดมาคือ KV cache ของแต่ละคำขอยาวไม่เท่ากันและงอกเรื่อย ๆ ถ้าจองที่ต่อเนื่องล่วงหน้าตามความยาวสูงสุดจะเสียที่ว่างมหาศาล Kwon และคณะ (SOSP 2023) เสนอ PagedAttention: หั่น KV cache เป็น "หน้า" (block) ขนาดคงที่ วางกระจายที่ไหนก็ได้ใน VRAM แล้วมีตารางแมป เหมือน virtual memory ใน OS ผลคือ vLLM เสียที่ว่างใน KV cache เกือบศูนย์ และ throughput สูงกว่าระบบก่อนหน้า 2-4 เท่าที่ latency เท่ากัน [13]

เทียบกับงานโยธา: static batching เหมือนจัดคิวรถโม่ให้ออกพร้อมกันเป็นชุดและรอทุกคันเทเสร็จ continuous batching เหมือนจุดจ่ายที่คันไหนเทเสร็จออกได้เลย คันใหม่เข้าแทนทันที PagedAttention เหมือนลานกองวัสดุที่ไม่ต้องจองแปลงยาวต่อเนื่องให้แต่ละงาน แต่ใช้ช่องมาตรฐานเล็ก ๆ ที่มีบัญชีบอกว่าอะไรอยู่ช่องไหน

🎨 **ภาพที่จะวาดใน HTML:** กริด GPU แบ่งเป็น 8 slot แนวตั้ง แกนเวลาไหลไปทางขวา คำขอเข้ามาแบบสุ่ม (สั้นบ้างยาวบ้าง) โหมด "static" แสดง slot ว่างเปล่า (สีเทา) รอคำขอยาวที่สุดจบ โหมด "continuous" แสดงคำขอใหม่แทรกเข้าทันทีที่ slot ว่าง มีตัวเลข "GPU utilization %" และ "คำขอ/นาที" เปรียบเทียบสองโหมดสด ๆ ด้านล่างเป็นภาพ VRAM ที่โหมด "จองต่อเนื่อง" มีช่องว่างสีแดง (waste) และโหมด "paged" มีบล็อกเล็ก ๆ กระจายเต็มพื้นที่

## 9.9 Quantization: fp32 → bf16 → int8 → int4

### ขั้นที่ 1: ตัวเลขในโมเดลเก็บอย่างไร

น้ำหนักโมเดลเป็นทศนิยม fp32 ใช้ 32 บิต (8 บิต exponent + 23 บิต mantissa), bf16 ใช้ 16 บิต (8 บิต exponent + 7 บิต mantissa) จึงมี "ช่วง" เท่า fp32 แต่ "ความละเอียด" น้อยกว่า, int8 ใช้ 8 บิตเป็นจำนวนเต็ม [22] โมเดล 8B พารามิเตอร์ที่ bf16 กิน 16 GB, int8 กิน 8 GB, int4 กิน 4 GB (ไม่รวม overhead)

### ขั้นที่ 2: quantize ทำอย่างไร (absmax แบบพื้นฐาน)

แบ่งน้ำหนักเป็นบล็อก หาค่าสัมบูรณ์สูงสุดในบล็อก ใช้เป็นสเกล แล้วปัดทุกค่าให้เป็นจำนวนเต็มในช่วงที่บิตรองรับ:

$$
s = \frac{\max_i |w_i|}{2^{b-1}-1}, \qquad q_i = \text{round}\!\left(\frac{w_i}{s}\right), \qquad \hat{w}_i = q_i \cdot s
$$

- $w_i$ น้ำหนักจริง, $b$ จำนวนบิต (int4 → ช่วง -7 ถึง 7), $s$ สเกล (เก็บเป็น fp16 หนึ่งค่าต่อบล็อก), $\hat{w}_i$ น้ำหนักหลังคืนค่า

ตัวอย่างบล็อก 4 ค่า int4: $w = [0.12, -0.35, 0.80, -1.02]$ → $s = 1.02/7 = 0.1457$ → $q = [1, -2, 5, -7]$ → $\hat{w} = [0.146, -0.291, 0.729, -1.02]$ คลาดเคลื่อน $[0.026, 0.059, 0.071, 0]$ สังเกตว่าค่าเล็ก ๆ คลาดเคลื่อนเป็นสัดส่วนมาก และถ้าบล็อกมี outlier ตัวเดียวใหญ่มาก สเกลจะหยาบจนค่าอื่นทั้งบล็อกเพี้ยน นี่คือปัญหาหลักของ transformer ขนาดใหญ่ที่ Dettmers และคณะพบใน LLM.int8() และแก้ด้วยการแยก outlier ไปคำนวณที่ fp16 [21][22]

เทียบกับงานโยธา: quantization คือการปัดขนาดเหล็กเสริมให้เป็นขนาดมาตรฐานที่มีขาย เหล็ก DB12.7 ไม่มี ต้องเลือก DB12 หรือ DB16 ถ้าปัดทุกต้นทั้งอาคารโดยไม่ตรวจ ก็ไม่รู้ว่าองค์อาคารไหนขาดกำลัง

### ขั้นที่ 3: PTQ vs QAT

- **Post-training quantization (PTQ)**: quantize โมเดลที่เทรนเสร็จแล้ว ถูก เร็ว ไม่ต้องเทรนใหม่ แต่คุณภาพอาจตก
- **Quantization-aware training (QAT)**: จำลองการปัดตั้งแต่ตอนเทรน ให้โมเดลปรับตัวชดเชย (Jacob และคณะ 2017 เป็นงานคลาสสิกฝั่ง CNN) [20] คุณภาพดีกว่าแต่ต้องเทรน

Gholami และคณะ (2021) สำรวจทั้งสองแนว และชี้ว่าการลดจาก float เป็นจำนวนเต็มความละเอียดต่ำลดหน่วยความจำและ latency ได้ 4-8 เท่าในทางปฏิบัติ [19]

### ขั้นที่ 4: ตระกูลเครื่องมือ

| วิธี | แนวคิดสั้น ๆ | ใช้เมื่อ |
|---|---|---|
| bitsandbytes (LLM.int8 / NF4) | quantize ตอนโหลดใน PyTorch, int8 แยก outlier, 4-bit NF4 ใช้เป็นฐานของ QLoRA [21][23][26] | เทรน/ทูนบน GPU เดียว (t02 ของเราใช้ QLoRA 4-bit) |
| GPTQ (Frantar 2022) | PTQ แบบใช้ข้อมูลอนุพันธ์อันดับสองชดเชยความคลาดเคลื่อนทีละคอลัมน์ 3-4 บิต [24] | serve บน GPU ผ่าน vLLM/transformers |
| AWQ (Lin 2023) | PTQ ที่ "ปกป้อง" น้ำหนักส่วนน้อยที่สำคัญโดยดูจาก activation [25] | serve บน GPU, มักเร็วกว่า GPTQ |
| GGUF k-quants (llama.cpp) | quantize แบบบล็อกซ้อนบล็อก (super-block) มี mix หลายระดับ [27] | รันบน CPU/GPU ผู้บริโภค, Mac |

🎨 **ภาพที่จะวาดใน HTML:** เส้นจำนวน (number line) แสดงน้ำหนัก 16 ค่าในหนึ่งบล็อกเป็นจุดสีน้ำเงิน สไลเดอร์ "บิต" (2, 3, 4, 8) วาดขีดระดับที่อนุญาต (2^b ระดับ) และจุดสีแดงคือค่าหลังปัด พร้อมเส้นเชื่อมแสดงระยะคลาดเคลื่อน ปุ่ม "ใส่ outlier" เพิ่มค่าหนึ่งเป็น 5.0 แล้วผู้เรียนต้องเห็นขีดระดับถ่างออกและจุดอื่นทั้งหมดปัดเพี้ยนหนักขึ้น ด้านล่างมี MSE รวมและขนาดไฟล์ (MB) เปลี่ยนตามบิต

```python
import numpy as np
w = np.array([0.12, -0.35, 0.80, -1.02])
def quant(w, bits):
    qmax = 2 ** (bits - 1) - 1
    s = np.abs(w).max() / qmax
    q = np.round(w / s)
    return q, q * s
for b in [8, 4, 3]:
    q, w_hat = quant(w, b)
    print(f"int{b}: q={q.astype(int)}  w_hat={w_hat.round(3)}  err_max={np.abs(w-w_hat).max():.3f}")
```

## 9.10 GGUF, Q4_K_M และหลักการ "วัดซ้ำหลัง quantize"

### ขั้นที่ 1: GGUF คืออะไร

GGUF เป็นรูปแบบไฟล์ของโครงการ ggml/llama.cpp (Georgi Gerganov) สำหรับเก็บโมเดลเพื่อ inference ในไฟล์เดียว มี metadata แบบ key-value (สถาปัตยกรรม, tokenizer, ค่าตั้งต่าง ๆ) ตามด้วย tensor ทั้งหมด จึงโหลดได้โดยไม่ต้องพึ่งไฟล์ config ภายนอก [28] llama.cpp เป็นเอนจิน C/C++ ที่รันไฟล์นี้บน CPU, GPU และ Apple Silicon

### ขั้นที่ 2: อ่านชื่อ Q4_K_M

จาก PR k-quants #1684 ของ llama.cpp [27]:

- **Q4** = 4 บิตต่อน้ำหนัก (โดยประมาณ เพราะต้องบวกสเกลของบล็อก)
- **K** = ตระกูล k-quants ซึ่งใช้ super-block: Q4_K จัด 8 บล็อก บล็อกละ 32 น้ำหนัก มีสเกลสองชั้น
- **S / M / L** = small / medium / large คือ "สูตรผสม" ว่า tensor ไหนใช้บิตสูงกว่า เช่น เอกสาร Unsloth อธิบาย q4_k_m ว่าใช้ Q6_K กับครึ่งหนึ่งของ attention.wv และ feed_forward.w2 ที่เหลือใช้ Q4_K [31] M จึงไม่ใช่ 4 บิตล้วน แต่เป็นการเลือกเก็บความละเอียดไว้ในชั้นที่ไวต่อความคลาดเคลื่อน

### ขั้นที่ 3: ผลต่อคุณภาพและทำไมบางตระกูลตกมาก

ตัววัดคลาสสิกคือ perplexity (ยิ่ง quantize หนัก ยิ่งเพิ่ม) แต่ Unsloth โต้แย้งว่า perplexity หลอกได้เพราะความคลาดเคลื่อนของ token หักล้างกันเอง และเสนอให้ใช้ KL divergence ระหว่างการแจกแจงของโมเดลเต็มกับโมเดล quantize เป็นมาตรฐาน [32] เอกสารเดียวกันรายงานว่าที่ 2 บิตลงไปมีอาการ "ตกหน้าผา" (ความแม่นทำนาย 32 token ตกจากราว 25% เหลือต่ำกว่า 8-10% ระหว่างสองระดับที่ติดกัน) และเกิด "excessive looping" กับ "empty responses" [32] และชี้ว่าแต่ละ layer / แต่ละสถาปัตยกรรมไวไม่เท่ากัน จึงต้องเลือกบิตต่างกันรายชั้น (dynamic quants) [32]

สาเหตุที่ MoE (เช่น Qwen3.6-35B-A3B ของ t01/t05) และโมเดลใหม่ ๆ มักไวกว่า: น้ำหนักที่ "active" ต่อ token มีเพียง 3B พารามิเตอร์ ความคลาดเคลื่อนต่อค่าจึงมีน้ำหนักต่อผลลัพธ์มากกว่าโมเดล dense ขนาดเท่ากัน และ router ที่เลือก expert ก็ไวต่อการปัดค่าเช่นกัน (นี่คือคำอธิบายเชิงกลไกที่สมเหตุสมผล แต่ยังไม่มีตัวเลขจากงานเราเองยืนยัน)

### ขั้นที่ 4: กฎ "วัดซ้ำหลัง quantize"

บั๊กข้อ 3 ของเราคือ deploy ด้วย Q4_K_M ทั้งที่ผู้ทำโมเดลเตือน แล้วไม่วัดซ้ำ ทฤษฎีข้างบนบอกว่านี่คือการเปลี่ยนน้ำหนักทุกตัวในโมเดล ผลที่วัดตอน bf16 จึงไม่ใช่ผลของสิ่งที่ deploy จริง กฎง่าย ๆ:

1. วัด recall บนชุดทดสอบเดียวกันที่ bf16 (หรือ fp16) ก่อน
2. quantize แล้ววัดซ้ำด้วยชุดเดียวกัน ค่า sampling เดียวกัน
3. ถ้าต่างกันเกินความแปรปรวนจาก seed (บทที่ 10) ให้ถอยไป Q5_K_M / Q6_K / Q8_0 หรือใช้ dynamic quants
4. บันทึกทั้งสองตัวเลขไว้คู่กันเสมอ

🎨 **ภาพที่จะวาดใน HTML:** กราฟสองแกน แกน x = ขนาดไฟล์ (GB) แกน y = คุณภาพ (recall จำลอง หรือ KL divergence) จุดสำหรับ F16, Q8_0, Q6_K, Q5_K_M, Q4_K_M, Q3_K_M, Q2_K เชื่อมด้วยเส้น มีสวิตช์ "ตระกูลโมเดล: dense / MoE" ที่ทำให้เส้น MoE ตกชันกว่าที่ 4 บิตลงมา (ป้ายกำกับว่าเป็นภาพประกอบเชิงคุณภาพ ไม่ใช่ข้อมูลวัดจริง) และมีจุดสีแดง "ที่เราวัด (bf16)" กับ "ที่เรา deploy (Q4_K_M) ไม่ได้วัด" เพื่อสื่อว่าช่องว่างนี้คือสิ่งที่เราไม่รู้

## 9.11 mmproj, การ merge LoRA ก่อน convert และการพิสูจน์ว่า merge จริง

### ขั้นที่ 1: โมเดล vision ใน llama.cpp ต้องมีสองไฟล์

llama.cpp แยก "ตัวเข้ารหัสภาพ + projector" ออกเป็นไฟล์ GGUF ต่างหากชื่อ mmproj (multimodal projector) ซึ่งแปลงภาพเป็น embedding ให้ส่วนภาษา ตอนรันต้องระบุ `--mmproj file.gguf` คู่กับโมเดลภาษา และตอนแปลงใช้ `convert_hf_to_gguf.py --mmproj` [29][30] ถ้าลืม mmproj หรือใช้ mmproj ของโมเดลฐานคนละรุ่น ผลลัพธ์จะเพี้ยนโดยไม่มี error ชัดเจน

### ขั้นที่ 2: ทำไมต้อง merge LoRA ก่อน convert

LoRA (บทที่ 6) เก็บน้ำหนักที่ทูนเป็นเมทริกซ์เล็ก $A$, $B$ แยกจากโมเดลฐาน ตอนใช้งานคำนวณ $W + BA$ ทุกครั้ง GGUF โดยหลักเก็บเมทริกซ์ $W$ เดียว การ merge คือคำนวณ $W' = W + BA$ แล้วบันทึกเป็นน้ำหนักเดียว PEFT ทำผ่าน `merge_and_unload()` และเตือนว่าไม่ใช่ in-place ต้องรับค่าที่คืนมาไปใช้ [34] Unsloth ทำผ่าน `save_pretrained_merged(..., save_method="merged_16bit")` แล้วค่อยแปลงเป็น GGUF [31]

บั๊กข้อ 2 ของเราคือขั้นนี้: ถ้า merge ไม่เกิดจริง (เช่น ลืมรับค่าคืน, บันทึกโมเดลฐานแทนโมเดลที่ merge, หรือแปลงจากโฟลเดอร์ผิด) ไฟล์ GGUF ที่ได้คือโมเดลเปล่า และตัวเลข "90%" ที่เชื่อว่าเป็นผลของการทูน อาจเป็นผลของโมเดลฐานล้วน ๆ

### ขั้นที่ 3: วิธีพิสูจน์ว่า adapter merge จริง

ไม่มีทางรู้จากชื่อไฟล์หรือขนาดไฟล์ (โมเดลที่ merge แล้วขนาดเท่าโมเดลฐานพอดี) ต้องพิสูจน์จากพฤติกรรม:

1. เตรียมภาพทดสอบ 3-5 หน้าและ prompt คงที่
2. รันโมเดลฐาน (base) ด้วย greedy ชั่วคราวเพื่อให้ผลนิ่ง หรือรัน sampling หลายรอบด้วย seed คงที่
3. รันไฟล์ที่ merge/convert แล้ว ด้วยค่าเดียวกันทุกอย่าง
4. เทียบ output: ถ้าเหมือนกันทุกตัวอักษรบนหลายหน้า แปลว่า adapter ไม่ได้อยู่ในไฟล์นั้น
5. เสริมด้วยการเทียบน้ำหนักโดยตรง: โหลด tensor ตัวใดตัวหนึ่งที่ LoRA แตะ (เช่น q_proj ของ layer แรก) จาก base กับจาก merged แล้วดูว่า `max|diff| > 0`

```python
import torch
from safetensors.torch import load_file
base = load_file("base/model-00001-of-000N.safetensors")
merged = load_file("merged/model-00001-of-000N.safetensors")
key = next(k for k in base if "q_proj.weight" in k)
diff = (base[key].float() - merged[key].float()).abs()
print(key, "max|diff| =", diff.max().item(), "mean =", diff.mean().item())
# ถ้า max|diff| == 0 แปลว่า adapter ไม่ได้ถูก merge เข้าไปในไฟล์นี้
```

🎨 **ภาพที่จะวาดใน HTML:** แผนผังไหลจากซ้ายไปขวา: [base W] + [LoRA A,B] → (merge) → [W'] → (convert) → [GGUF] + [mmproj] → llama.cpp มีสวิตช์ "merge สำเร็จ / merge ล้มเหลว" เมื่อล้มเหลว กล่อง W' เปลี่ยนเป็น W (สีเดิม) และ output ตัวอย่างสองช่อง (base vs merged) แสดงข้อความเหมือนกันทุกตัวอักษร พร้อมไฮไลต์สีแดง "identical = adapter หาย" เมื่อสำเร็จ ข้อความต่างกันและตัวเลข max|diff| > 0

## 9.12 เลือกเอนจิน: transformers vs llama.cpp vs vLLM

| | transformers (+bitsandbytes) | llama.cpp / GGUF | vLLM |
|---|---|---|---|
| จุดแข็ง | ยืดหยุ่นสุด ใช้ adapter ตรง ๆ ได้ ทดลองเร็ว | รันบนเครื่องธรรมดา/CPU/Mac ไฟล์เดียว grammar GBNF ในตัว [10] | throughput สูงสุดจาก continuous batching + PagedAttention [13][14] xgrammar ในตัว [11] |
| จุดอ่อน | ช้าเมื่อรันหลายคำขอ จัดการ KV cache ไม่ประหยัด | ต้อง merge + convert + mmproj ทุกครั้งที่ทูนใหม่ quantize เกือบบังคับ | ต้องการ GPU และ VRAM มาก ตั้งค่ายาก |
| เหมาะกับงานเรา | ประเมินผลหลังทูนทันที (วัด recall ก่อน quantize) | สาธิตบนโน้ตบุ๊กหน้างาน, บ้านทีละหลัง | ประมวลผลบ้านหลายสิบหลังพร้อมกันบน GPU เช่า |

หลักการเลือก: ใช้ transformers เป็น "มาตรฐานอ้างอิง" ที่ต้องวัดผลก่อนเสมอ ส่วน llama.cpp และ vLLM คือทางเลือกในการ deploy ที่ต้องวัดซ้ำเทียบกับมาตรฐานนั้น ทุกครั้งที่เปลี่ยนเอนจิน คุณเปลี่ยนสามอย่างพร้อมกัน: ตัวเลข (quantize), วิธี sampling (แต่ละเอนจินมี default ต่างกัน) และการจัดการภาพ (mmproj vs processor ของ HF) ผลลัพธ์ต่างกันได้โดยที่ "โมเดลเดียวกัน"

🎨 **ภาพที่จะวาดใน HTML:** ต้นไม้ตัดสินใจแบบคลิกได้: "มี GPU ไหม?" → "กี่คำขอพร้อมกัน?" → "ต้องการ grammar ไหม?" → "ทูนบ่อยแค่ไหน?" ปลายกิ่งเป็นการ์ดเอนจินพร้อมสรุปข้อควรวัดซ้ำ ด้านข้างมีแถบ "สิ่งที่เปลี่ยนเมื่อย้ายเอนจิน" สามช่อง (ตัวเลข / sampling default / image pipeline) ที่ติดไฟเตือนเมื่อผู้เรียนเลือกเส้นทางที่ข้ามเอนจิน

## 9.13 ต้นทุน: token/วินาที, VRAM, GPU เช่า และ monitoring

### ขั้นที่ 1: ตัวเลขที่ต้องรู้ก่อนสั่งงาน

- **token/วินาที (decode)**: ประมาณด้วยแบนด์วิดท์ VRAM ÷ ขนาดโมเดล เช่น โมเดล 8 GB (int8) บนการ์ดแบนด์วิดท์ 1,000 GB/s ได้เพดานราว 125 token/s ต่อหนึ่งคำขอ (ประมาณการหยาบ ๆ) batching เพิ่ม throughput รวม แต่ไม่เพิ่มความเร็วต่อคำขอ
- **VRAM**: น้ำหนัก + KV cache (9.7) + activation ของ prefill (ภาพใหญ่ = activation ใหญ่) + overhead ของเอนจิน
- **ต้นทุนต่อบ้าน**: (จำนวนหน้า × เวลาต่อหน้า) × ราคา GPU ต่อชั่วโมง เวลาต่อหน้าถูกครอบงำด้วยความยาว output ตาม 9.7

### ขั้นที่ 2: GPU เช่าแบบ interruptible

Vast.ai แยก instance เป็น on-demand (ราคาคงที่ ไม่ถูกขัดจังหวะ) กับ interruptible (เราตั้งราคาประมูล ถูกกว่า 50-80% แต่ถ้ามีคนประมูลสูงกว่า instance จะถูกหยุดโดย "killing running processes") เอกสารแนะนำให้บันทึกงานลงดิสก์บ่อย ๆ ใช้ cloud storage สำรอง และทำ checkpoint [35] ข้อสรุปเชิงปฏิบัติสำหรับเรา:

1. อัปโหลด adapter / merged model / ผลลัพธ์ JSON ออกจากเครื่องทันทีที่ได้ (ก่อนวัดผลด้วยซ้ำ)
2. ห้ามเก็บสิ่งที่ทำซ้ำไม่ได้ไว้บนดิสก์ instance เพียงที่เดียว
3. ก่อนกด destroy ให้เช็กลิสต์: adapter, merged, GGUF, mmproj, log การเทรน, ค่า config ทั้งหมด

### ขั้นที่ 3: monitoring และคำเตือนตอนโหลดโมเดล

บั๊กข้อ 6 ของเราคือคำเตือนตอนโหลดโมเดล (Qwen-VL ต้องการ image token ขั้นต่ำ) ถูกมองข้าม ปัญหาเชิงระบบคือ log ตอนโหลดยาวหลายร้อยบรรทัด คำเตือนสำคัญจมอยู่ในนั้น กฎที่ควรใช้:

- จับทุกบรรทัดที่มี `Warning`, `deprecated`, `mismatch`, `not found`, `ignored` ลงไฟล์แยก และอ่านก่อนเริ่มรันจริง
- บันทึก `generation_config` ที่ใช้จริง (ไม่ใช่ที่คิดว่าใช้) ลง log ทุกครั้ง เพราะ default ของแต่ละเอนจินต่างกัน (บั๊กข้อ 5)
- ระหว่างรัน วัด token/s, VRAM สูงสุด, จำนวน timeout, จำนวนครั้งที่ output ไม่ผ่าน JSON parse แล้วดูแนวโน้ม

🎨 **ภาพที่จะวาดใน HTML:** แดชบอร์ดจำลองของการรันบ้าน 1 หลัง: กราฟ token/s ตามเวลา, มิเตอร์ VRAM, ตัวนับ timeout, ตัวนับ JSON ไม่ผ่าน และช่อง log ที่มีบรรทัดไหลผ่าน มีปุ่ม "highlight warnings" ที่ทำให้บรรทัด warning ลอยขึ้นมาเป็นสีส้ม สไลเดอร์ "ราคาประมูล" ของ interruptible instance ซึ่งเมื่อต่ำกว่าเส้นตลาด แดชบอร์ดจะดับพร้อมข้อความ "instance ถูกหยุด: ไฟล์ที่ยังไม่สำรองหายไป" เพื่อฝังนิสัยสำรองก่อน

```python
import re, sys
keys = ("warn", "deprecat", "mismatch", "not found", "ignored", "min_pixels", "image token")
with open("load_model.log", encoding="utf-8", errors="ignore") as f:
    hits = [l.rstrip() for l in f if any(k in l.lower() for k in keys)]
print(f"พบ {len(hits)} บรรทัดที่ควรอ่านก่อนรันจริง")
print("\n".join(hits[:20]))
```

## 9.y ระดับนักวิจัย: คำถามที่ยังเปิดอยู่

1. **Constrained decoding ลดคุณภาพจริงหรือไม่ และเมื่อไหร่** Tam และคณะ (2024) รายงานว่าการบังคับรูปแบบทำให้ reasoning ตก [12] ขณะที่ XGrammar และ Outlines เน้นว่า overhead เชิงเวลาต่ำ [8][9] แต่ไม่ได้วัดผลเชิงคุณภาพเท่ากัน คำถามเปิดคือผลกระทบต่อกรณี "อ่านแล้วคัดลอก" อย่างการถอดแบบ ซึ่งต่างจากโจทย์คณิตศาสตร์ในเปเปอร์ วิธีทดลองที่ทำได้กับข้อมูลเรา: รันชุดเดียวกันด้วย grammar เปิด/ปิด แล้ว parse ด้วยตัวเองในกรณีปิด เทียบ recall

2. **ตัววัดคุณภาพหลัง quantize ควรเป็นอะไร** Unsloth โต้ว่า perplexity หลอกได้และเสนอ KL divergence [32] ส่วนงานวิชาการเช่น GPTQ/AWQ ยังรายงาน perplexity และ benchmark ปลายทาง [24][25] สำหรับงานเราไม่มีตัววัดใดแทน "recall นับคาน" ได้ คำถามคือ KL ระดับไหนที่ยังปลอดภัยต่อ recall ซึ่งต้องสร้างกราฟความสัมพันธ์เอง

3. **Mixed-precision รายชั้นควรตัดสินด้วยอะไร** Dynamic quants ของ Unsloth เลือกบิตต่อชั้นด้วย heuristic และ calibration [32] งานอย่าง SliM-LLM เสนอเลือกบิตระดับกลุ่มจาก salience [36] ยังไม่มีข้อตกลงว่าเกณฑ์ไหนถูกต้องสำหรับ MoE และ vision tower ซึ่งเป็นสองส่วนที่โมเดลของเราใช้

4. **Speculative decoding กับงาน output ยาว** Leviathan และคณะ (2022) เสนอใช้โมเดลเล็กเดาหลาย token แล้วให้โมเดลใหญ่ตรวจ ได้ความเร็ว 2-3 เท่าโดยไม่เปลี่ยนการแจกแจง [16] เพราะงานเราถูกครอบงำด้วย decode (9.7) นี่คือทางลดเวลาถอดเต็มที่ยังไม่ได้ลอง คำถามคือโมเดลเล็กสำหรับ VLM แบบ 8B ควรเป็นอะไร และ JSON ที่ซ้ำโครงสร้างมากน่าจะเดาง่าย (acceptance สูง) จริงหรือไม่

5. **Chunked prefill สำหรับภาพใหญ่** SARATHI เสนอหั่น prefill เป็นชิ้นแล้วสอด decode ของคำขออื่นเข้าไป [15] กับภาพ 3,796 token ต่อหน้า นี่คือกลไกที่ทำให้ serve หลายบ้านพร้อมกันไม่ค้างเพราะ prefill ของหน้าใหม่ แต่ผลต่อ latency ของหน้าที่กำลัง decode อยู่ยังต้องวัด

## 9.z แบบฝึกหัด

**ข้อ 1 (คำนวณ)** logits ของ 4 token เป็น $[3.0, 2.5, 0.0, -1.0]$ จงหา probability ที่ $T=1$ และ $T=0.5$ แล้วบอกว่าที่ top_p=0.9 nucleus แต่ละกรณีมีกี่ตัว

<details><summary>เฉลย</summary>

$T=1$: $e^z = [20.09, 12.18, 1.00, 0.37]$ รวม 33.64 → $p = [0.597, 0.362, 0.030, 0.011]$ สะสม 0.597, 0.959 → nucleus 2 ตัว
$T=0.5$: $z/T = [6, 5, 0, -2]$, $e = [403.4, 148.4, 1.0, 0.135]$ รวม 552.9 → $p = [0.730, 0.268, 0.002, 0.000]$ สะสม 0.730, 0.998 → nucleus 2 ตัว (แต่ตัวที่สองเหลือ 0.268 จาก 0.362)
</details>

**ข้อ 2 (คิด)** ทำไม `no_repeat_ngram_size=3` ถึงทำให้ JSON รายการคานพังทั้งที่แก้อาการวน B2 ได้ ให้ยกตัวอย่าง 3-gram ที่จำเป็นต้องซ้ำ

<details><summary>เฉลย</summary>

`"beam_id": "` แยกเป็น token ได้อย่างน้อย 3 ตัว (`"beam`, `_id`, `":`) ซึ่งต้องปรากฏทุกต้นคาน เมื่อห้าม 3-gram ซ้ำ โมเดลจะถูกบังคับให้พิมพ์ key ชื่ออื่นตั้งแต่คานต้นที่สอง JSON จึงผิด schema ทางแก้คือใช้ repetition_penalty อ่อน ๆ + grammar + limit จำนวนรายการใน schema แทน
</details>

**ข้อ 3 (คำนวณ)** โมเดลสมมติ $L=36$, $H_{kv}=8$, $d_{head}=128$, bf16 ถ้า serve 4 หน้าพร้อมกัน หน้าละ 7,500 token KV cache รวมกี่ GB (ไม่รวมน้ำหนัก)

<details><summary>เฉลย</summary>

ต่อ token: $2 \times 36 \times 8 \times 128 \times 2 = 147{,}456$ ไบต์ ≈ 144 KB
ต่อหน้า: $147{,}456 \times 7{,}500 ≈ 1.106$ GB
4 หน้า ≈ 4.42 GB ถ้าเปลี่ยนเป็น KV cache แบบ int8 จะเหลือครึ่งหนึ่ง
</details>

**ข้อ 4 (รันโค้ด)** แก้โค้ดใน 9.9 ให้ quantize บล็อก 32 ค่าสุ่มจาก normal(0, 0.5) ที่ 4 บิต แล้ววัด MSE จากนั้นแทรก outlier ค่า 4.0 หนึ่งตัว MSE เปลี่ยนไปกี่เท่า

<details><summary>เฉลย</summary>

ผลขึ้นกับ seed แต่โดยทั่วไป MSE เพิ่มขึ้นหลายสิบเท่า เพราะสเกลถูกกำหนดโดย outlier ตัวเดียว (4.0/7 ≈ 0.57 ต่อระดับ) ทำให้ค่าส่วนใหญ่ที่อยู่ในช่วง ±1 ถูกปัดเหลือแค่ 3-4 ระดับ นี่คือเหตุผลของ block เล็กใน k-quants และการแยก outlier ใน LLM.int8()
</details>

**ข้อ 5 (คิด)** ออกแบบการทดลอง 1 หน้ากระดาษเพื่อพิสูจน์ว่าไฟล์ GGUF ของ t01 มี adapter จริง โดยที่คุณมีเพียง base GGUF, merged GGUF, llama.cpp และภาพ 5 หน้า

<details><summary>เฉลย</summary>

(1) ใช้ prompt เดียวกัน seed เดียวกัน temperature 0 หรือ sampling ที่ seed คงที่ทั้งสองไฟล์ (2) รัน 5 หน้า × 3 รอบ (3) ถ้า output เหมือนกันทุกตัวอักษรทั้ง 15 คู่ → adapter หาย (4) ถ้าต่าง ให้วัด recall ทั้งสองไฟล์ต่อ GT: merged ต้องดีกว่า base อย่างมีนัย (5) บันทึก hash ของไฟล์ทั้งสอง ค่า config และเวอร์ชัน llama.cpp ลงรายงาน
</details>

## สรุปบทนี้ใน 5 บรรทัด

1. Inference คือ forward pass ทีละ token: logits → softmax → เลือก 1 ตัว → วนใหม่ ความยาว output จึงกำหนดเวลา ไม่ใช่ความยาว input
2. greedy ติดวงจรซ้ำเพราะการซ้ำเพิ่ม probability ของการซ้ำถัดไป (Holtzman) ทางแก้คือ sampling ที่ตัดหาง: temperature 0.7, top_p 0.8, top_k 20 ตามที่ Qwen แนะนำ
3. Constrained decoding mask logits ที่ผิดไวยากรณ์ รับประกันรูปแบบ แต่ไม่รับประกันความถูกต้องหรือความยาว จึงต้องมี penalty และ timeout คู่กัน
4. Quantization เปลี่ยนน้ำหนักทุกตัว Q4_K_M = 4 บิต, k-quant super-block, สูตรผสม medium คุณภาพตกไม่เท่ากันรายชั้นและรายตระกูล ต้องวัดซ้ำหลัง quantize เสมอ
5. GGUF ต้อง merge LoRA ก่อน convert และต้องพิสูจน์ด้วย base-vs-merged เอนจินต่างกัน (transformers / llama.cpp / vLLM) เปลี่ยนตัวเลข, sampling default และ image pipeline พร้อมกัน สำรองไฟล์ก่อนทำลาย instance และอ่านคำเตือนตอนโหลดทุกครั้ง
