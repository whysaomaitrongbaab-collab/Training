# § hint design — pass 2.4 ป้อนอะไรให้ Qwen

## ปัญหา: จำนวนอย่างเดียวไร้ประโยชน์

บอกว่า "หน้านี้มีเสา 14 ต้น" โมเดลทำอะไรกับข้อมูลนี้ไม่ได้เลย นอกจากเดาเติมให้ครบ 14 —
ซึ่งคือ **การเชิญให้หลอน** ตรงๆ เลวร้ายกว่าไม่บอกอะไรเสียอีก

## ทางออก: ส่ง 2 ช่องทางพร้อมกัน — มาร์คบนภาพ + ตารางข้อความ

**ช่องที่ 1 — มาร์คลงบนภาพจริง (Set-of-Mark)**
วาดกรอบ + **เลขกำกับ** ลงบนจุดที่ CV เจอ แล้วส่งภาพที่มาร์คแล้วให้โมเดลแทนภาพเปล่า

มีงานวิจัยรองรับตรงๆ: **Set-of-Mark Prompting** (Microsoft Research, arXiv 2310.11441) —
เอาเลข/กรอบไปแปะบนภาพ แล้ว GPT-4V แบบ zero-shot ชนะโมเดลที่ fine-tune มาเฉพาะทาง
บน RefCOCOg ได้ หลักการคือ **โมเดลอ่าน "ตรงเลข 3" ง่ายกว่าอ่าน "ที่พิกัด x=340,y=210" มาก** —
พิกัดตัวเลขในข้อความ โมเดลต้องแปลงกลับเป็นตำแหน่งบนภาพเอง ซึ่งมันทำได้แย่

และนี่คือสิ่งที่มะขามสั่งไว้ตั้งแต่แรกอยู่แล้ว: *"ผมอยากให้มันไปทำการไฮไลด์หรือทำ mark ไว้เลย"*
— `pattern_recognition.py` วาดมาร์คเป็นอยู่แล้ว แค่ยังไม่เคยส่งภาพที่มาร์คแล้วเข้าโมเดล

**ช่องที่ 2 — ตารางข้อความสั้นๆ กำกับ**

```
### สิ่งที่เครื่องตรวจภาพเห็น — hint ไม่ใช่คำตอบ
บนภาพมีกรอบเลขกำกับจุดที่เครื่องเห็น ให้อ่านป้ายที่จุดเหล่านั้น

column (14): #1 g≈C-1 · #2 g≈C-2 · #3 g≈C-3 · ...
footing (14): #15 g≈C-1 · #16 g≈C-2 · ...
beam: แถบนอน 9 · แถบตั้ง 7
```

`g≈` = กริดที่เดาจากพิกัด (ดู "แปลง pixel → grid ref" ข้างล่าง) ใส่ `?` เมื่อยังไม่มี grid master

## ทำไมต้องมี grid ref ในhint

`grid_refs` เป็นฟิลด์ที่โมเดล**ต้องตอบอยู่แล้ว และตอบผิดบ่อยสุด** — CV รู้พิกัด pixel,
pass 2 gridline สร้าง grid master (ตำแหน่ง pixel ของทุกเส้นกริด) ไว้ก่อนอยู่แล้ว
→ เอามาคูณกันได้ **grid ref ที่ใกล้ที่สุดของทุกจุดที่ CV เจอ** ฟรีๆ

ลำดับใน pass 2 คือ gridline → plan_* อยู่แล้ว (organize.py `NEEDS_GRID`) ดังนั้นตอน 2.4
grid master มีแน่นอน ถ้าไม่มีให้เขียน `g≈?` ตรงๆ ห้ามเดา

## ❌ สิ่งที่ห้ามใส่ใน hint เด็ดขาด: ระยะ

CV วัดความยาวคานจากพิกเซลได้ก็จริง แต่ **ห้ามส่งเข้า prompt** เพราะขัดกฎเหล็กข้อ 1
"ห้ามเดาระยะจากรูปร่างที่เห็นบนแบบ" — ส่งเข้าไปคือสอนโมเดลให้แหกกฎนั้นด้วยมือเราเอง

ระยะที่ CV วัดได้ให้ใช้เป็น **ตัวจับผิดฝั่งโค้ด** ใน pass 2.5/3 แทน:
โมเดลตอบ span 3.0 ม. แต่ CV+กริดบอก ~8 ม. → ยกธง `span_contradicts_pixels` ให้คนดู
ไม่ใช่แก้ตัวเลขให้

## กฎกันหลอน 4 ข้อ ที่ต้องอยู่ในบล็อก hint

1. hint คือ**สิ่งที่เครื่องเห็น ไม่ใช่คำตอบ** — จุดไหนอ่านป้ายไม่ออก ให้ `element_id` เป็นชื่อบรรยาย
   + ติดธง **ห้ามแต่งชื่อมาร์คขึ้นมาเอง**
2. **hint ไม่ใช่เพดาน** — เห็นมากกว่าที่ hint บอก ให้ตอบตามที่เห็น
3. **hint ไม่ใช่พื้น** — hint ชี้ 14 จุด แต่แกอ่านได้จริง 9 → ตอบ 9 แล้วเขียนใน `warnings[]`
   ห้ามเติมอีก 5 ตัวให้ครบ
4. จุดที่ hint ชี้แล้วไม่มีอะไรจริง → บอกใน `warnings[]` (นี่คือ feedback ว่า template เรามั่ว)

**และมีตัวจับผิดฝั่งโค้ดคู่กันเสมอ** — เทียบจำนวนที่โมเดลตอบ vs ที่ CV เห็น ต่างกันทั้งสองทิศ
ให้ยกธง ไม่ใช่แก้ให้ตรง

## การทดลอง: 3 แขน ไม่ใช่ 2

หน้าเดียวกัน โมเดลตัวเดียวกัน ต่างกันแค่ input:

| แขน | ภาพ | ข้อความ hint |
|---|---|---|
| **2** | เปล่า | ไม่มี | ← ตัวคุม = พฤติกรรมวันนี้ |
| **2.4a** | เปล่า | มี (ตาราง+กริด) | แยกผลของ "ข้อความ" ล้วนๆ |
| **2.4b** | **มาร์คเลข** | มี | เต็มสูตร SoM |

ต้องมี 3 แขนเพราะถ้าเทียบแค่ 2 vs 2.4b แล้วดีขึ้น **จะไม่รู้เลยว่าดีขึ้นเพราะมาร์คบนภาพ
หรือเพราะข้อความ** — และสองอย่างนี้ต้นทุนต่างกันมากตอนเอาไปเทรนจริง
ค่ายิงเพิ่มแค่ 1 รอบต่อบ้าน ถูกกว่าการเดาผิดเยอะ

**วัดอะไร:** `recall_printed` (ตัวหลัก) · จำนวน element ที่ตอบ · จำนวนที่หลอน
(ตอบ id ที่ไม่มีใน GT) · จำนวนที่ยอมตอบ `null` อย่างซื่อสัตย์

## เรื่อง "โมเดลไม่เคยเห็น hint ตอนเทรน" — ยังเป็นข้อกังวลจริง

SoM ใช้ได้ zero-shot กับ VLM ทั่วไป แต่โมเดลเรา fine-tune มาแล้ว ซึ่งอาจทำให้มันแคบลง
จนมองข้าม hint — **ไม่มีใครรู้จนกว่าจะยิง** และนั่นคือเหตุผลที่ทำ 3 แขนก่อนตัดสินใจเทรน

ข่าวดี: ถ้าแขนไหนชนะ การเอาไปใส่ในชุดเทรนถูกมาก — มาร์คภาพเราวาดเอง `build_dataset_t03.py`
ก็มีภาพครบอยู่แล้ว แค่รัน CV แล้วแปะ ไม่ต้องขอข้อมูลใหม่จากใคร เสียแค่ค่า GPU รอบเทรน
