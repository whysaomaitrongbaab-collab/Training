**4) อัปโหลดชุดข้อมูล (dataset)** — ใช้ `scp` (โปรแกรมคัดลอกไฟล์ผ่าน SSH เดียวกัน) ส่งโฟลเดอร์ `data_before_tune/` (320 ไฟล์ ~158MB — ส่วนใหญ่เป็นภาพหน้าแบบ + ไฟล์ .jsonl ที่มีคำถาม-คำตอบสำหรับฝึกโมเดล) ข้อสังเกต: `scp` ใช้ `-P` (พิมพ์ใหญ่) สำหรับ port ต่างจาก `ssh` ที่ใช้ `-p` (พิมพ์เล็ก) — จุดพลาดเล็กๆ ที่ทำให้งงตอนแรก

**5) เช็คว่าเครื่องพร้อมจริง (`verify_env.py`)** — สคริปต์ที่เตรียมไว้ล่วงหน้าเพื่อเช็ค 5 อย่างก่อนเริ่มงานจริง: (a) การ์ดจอเป็นรุ่น Blackwell จริงไหม (compute capability 12.0), (b) VRAM (หน่วยความจำการ์ดจอ) พอไหม (ได้ 95GB จากที่ต้องการอย่างน้อย 74GB), (c) ไลบรารี Unsloth (เครื่องมือช่วยเทรนให้เร็ว/ประหยัด VRAM) โหลดได้ไหม, (d) ไลบรารี Triton (คอมไพล์ GPU kernel) เวอร์ชันถูกไหม, (e) ดาวน์โหลด tokenizer (ตัวแปลงข้อความเป็นตัวเลขที่โมเดลเข้าใจ) จาก HuggingFace ได้จริงไหม — **ผ่านหมดทุกข้อ**

**6) ข้อสังเกตเล็กๆ:** เครื่องเช่านี้มีแค่คำสั่ง `python3` ไม่มี `python` เฉยๆ (ปกติของ Docker image บางตัว) ต้องพิมพ์ `python3` เสมอ

### ปัญหาที่เจอระหว่างทาง + วิธีแก้ (ส่วนที่ควรเรียนรู้)

**ปัญหา A — Terminal แสดงตัวอักษรมั่วๆ (`^[[B^[[A` ฯลฯ):** ไม่ใช่ error ครับ เป็นแค่รหัสควบคุมการขยับ cursor ของ progress bar (แถบโหลด %) ที่โปรแกรม copy ข้อความดิบมาแสดงตรงๆ ไม่ได้ render สวยงามเหมือนตอนดูสดในหน้าจอ — วิธีเช็คให้ชัวร์ว่าเครื่องไม่ได้ค้างจริง คือดู GPU utilization ด้วย `nvidia-smi` (ถ้ามี % และกิน VRAM อยู่ = กำลังทำงานจริง)

**ปัญหา B — คำสั่งบางบรรทัดหายไปเฉยๆ:** ตอน paste คำสั่งหลายบรรทัดติดกันเร็วเกินไป ตัวอักษรมั่วๆ จากปัญหา A ไปแทรกกลาง ทำให้บางคำสั่ง (เช่น `cd`) หายไปไม่ได้รัน วิธีแก้: พิมพ์/วางทีละบรรทัด รอให้ prompt นิ่งก่อนพิมพ์บรรทัดต่อไป

**ปัญหา C — งานรันซ้ำเองโดยไม่ได้สั่ง:** หลัง baseline eval (`eval_fields.py --base --limit 20`) รันจบแสดงผลสรุปแล้ว จู่ๆ มันเริ่มรันซ้ำเองอีกรอบ — สันนิษฐานว่ารหัสมั่วๆ จากปัญหา A ถูก bash (โปรแกรม terminal) ตีความเป็นการกดปุ่มลูกศรขึ้น (เรียกคำสั่งเก่ากลับมา) บวกกด Enter โดยไม่ตั้งใจ ทำให้เรียกคำสั่งเดิมซ้ำ **เสียเงิน/เวลาไปฟรีๆ** — แก้โดยใช้ `pkill`/`kill -9` หยุด process ซ้ำทันทีที่สังเกตเห็น บทเรียน: หลังงานสำคัญจบต้องเช็คว่ามันไม่ได้เผลอรันซ้ำ

**ปัญหา D — บั๊กจริงในโค้ด #1 (`AttributeError: property ... has no setter`):** ตอนสั่ง `eval_fields.py --base` ครั้งแรก โปรแกรมพังตรงบรรทัดที่พยายามตั้งความละเอียดภาพ (`ip.max_pixels = ...`) เพราะไลบรารี transformers เวอร์ชันที่เครื่องเช่าติดตั้งมา **เปลี่ยนวิธีตั้งค่านี้** (จากที่เคยตั้งตรงๆ ได้ กลายเป็นค่าที่อ่านได้อย่างเดียว คำนวณมาจากที่อื่น) หาข้อมูลจาก GitHub ของ HuggingFace/Qwen เจอว่าต้องตั้งผ่าน `ip.size["longest_edge"]`/`["shortest_edge"]` แทน แก้แล้วอัปโหลดใหม่

**ปัญหา E — บั๊กจริงในโค้ด #2 (isinstance check ตีเป็นเท็จเงียบๆ):** ตอนแก้ปัญหา D รอบแรก ใส่เงื่อนไข `if isinstance(ip.size, dict)` ป้องกันไว้ก่อน — แต่พอไปทดสอบ `train_qwen36.py` (แบบสั้น 5 step) กลับพบว่าค่าความละเอียดภาพที่ตั้งใจไว้ (5,120 tokens) **ไม่ถูกใช้จริง** ยังเป็นค่า default เดิม (16,384 tokens) เขียนสคริปต์เล็กๆ ทดสอบตรงบนเครื่องเช่า (ไม่ต้องโหลดโมเดลเต็ม ประหยัดเวลา) พบว่า `ip.size` เป็นคลาสชื่อ `SizeDict` ซึ่ง**ไม่ได้สืบทอดมาจาก `dict` จริงๆ** (เลยเช็ค isinstance แล้วได้ False เสมอ ทำให้โค้ดข้ามการตั้งค่าไปเงียบๆ โดยไม่มี error ให้เห็นเลย) แต่มันรองรับการเขียนค่าแบบ `["key"]=value` ปกติ — แก้โดยตัดเงื่อนไข isinstance ทิ้ง เขียนตรงๆ เลย บทเรียนสำคัญ: **บั๊กแบบ "เงียบ ไม่มี error" อันตรายกว่าบั๊กที่ error ชัดๆ** เพราะไม่รู้ตัวว่าพัง ต้องทดสอบแล้วอ่านค่าที่ได้จริงเทียบกับที่ตั้งใจเสมอ

**ปัญหา F — บั๊กจริงในโค้ด #3 (`lora_dropout` เข้ากันไม่ได้กับ MoE):** ทดสอบ `train_qwen36.py` แบบ 5 step (ก่อนรันเต็ม 3 รอบจริงเพื่อประหยัดเงิน/เวลา ถ้าพังจะพังไวและถูกกว่า) เจอ error `lora.ParamWrapper does not work with lora_dropout != 0` — โมเดลนี้เป็นแบบ MoE (Mixture of Experts คือมี "ผู้เชี่ยวชาญย่อย" หลายตัวในโมเดลเดียว เลือกใช้บางตัวต่อคำ) ซึ่งวิธีที่ Unsloth ใช้ปรับแต่ง (LoRA) ผู้เชี่ยวชาญเหล่านี้ไม่รองรับค่า dropout (เทคนิคป้องกัน overfitting แบบสุ่มปิดบางส่วนของโมเดลระหว่างเทรน) ที่ไม่ใช่ 0 — แก้โดยเปลี่ยน `lora_dropout=0.05` เป็น `0`

### เพิ่มเครื่องมือทดสอบก่อนรันเต็ม (ป้องกันเสียเงินซ้ำ)
เพิ่ม toggle `TEST_STEPS` เข้า `train_qwen36.py` — ปกติรันคำสั่งเฉยๆ จะเทรนเต็ม 3 รอบ (นาน/แพง) แต่ถ้าตั้ง `TEST_STEPS=5 python3 train_qwen36.py` จะรันแค่ 5 ก้าวสั้นๆ พอเช็คว่าไม่ error/ไม่ OOM (หน่วยความจำเต็ม) ก่อน — เหมือนซ้อมก่อนแข่งจริง

### บทเรียนที่บันทึกไว้ใน memory ของ Claude (ข้ามเซสชันได้)
- **ควรเช่าเครื่องถูกๆ ทดสอบสคริปต์ก่อน แล้วค่อยเช่าเครื่องแพงจริง** — รอบนี้พลาดเช่าเครื่องแพง ($1+/ชม.) แล้วมานั่งดีบั๊กสด มะขามท้วงติงเรื่องนี้ตรงๆ ("ไอแชตนายก็รู้ว่ามันเปลืองเงิน")
- **หลังงานทูนรอบนี้จบ ต้องสอนมะขามทำเองได้ทั้งกระบวนการ** ไม่ใช่ให้ Claude ทำแทนตลอด

### ผลลัพธ์ baseline (ก่อนทูน) ที่วัดได้จริง
JSON valid 0/20 (0%), element หาเจอ 0/170 (0%) — โมเดลก่อนทูนตอบผิดรูปแบบทั้งหมด (คาดไว้แล้ว เพราะไม่เคยเห็น schema นี้มาก่อน) หมายเหตุ: baseline รอบนี้อาจรันด้วยความละเอียดภาพ default (ปัญหา E) ไม่ใช่ 5,120 tokens ตามตั้งใจ แต่ไม่กระทบข้อสรุป (0% ยังไงก็แย่สุดอยู่แล้ว)

### สถานะปัจจุบัน ณ ตอนบันทึก
กำลังรันทดสอบ `TEST_STEPS=5` รอบใหม่ (หลังแก้บั๊ก E+F) รอผลอยู่ — ยังไม่ได้เริ่มเทรนเต็ม 3 epoch จริง

**ไฟล์ที่เปลี่ยนวันนี้:** `train_qwen36.py` (แก้ 4 รอบ: max_pixels ครั้งที่1, +TEST_STEPS toggle, max_pixels ครั้งที่2 จริง, lora_dropout), `eval_fields.py` (แก้ 2 รอบเช่นกัน)

## Claude — ต่อจาก entry บนสุด: ปัญหา "หน่วยความจำ GPU เต็ม" (CUDA out of memory) — อธิบายละเอียดมาก ตามที่มะขามขอ

### ผลทดสอบ TEST_STEPS=5 รอบแรก (หลังแก้บั๊ก D/E/F): ผ่านทุกจุดเดิม แต่พังจุดใหม่

ยืนยันจาก log ว่าบั๊กเดิมทั้งหมดหายจริง — บรรทัด `image processor: max=5242880 px (≈5120 visual tokens/ภาพ)` โผล่มาถูกต้องแล้ว (ตรงกับค่าที่ตั้งใจ 5,120 ไม่ใช่ 16,384 default อีกต่อไป) และไม่มี error จาก `lora_dropout` อีกเลย — **เดินหน้าผ่านทั้ง forward pass (ให้โมเดลอ่านภาพ+ทาย) ไปถึง backward pass (ขั้นตอนคำนวณว่าต้องปรับน้ำหนักโมเดลยังไง) ได้สำเร็จ** แต่แล้วก็พังตรงนั้นพอดี ด้วย error:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 100.00 MiB.
GPU 0 has a total capacity of 94.97 GiB of which 96.25 MiB is free.
```

### "CUDA out of memory" คืออะไร (อธิบายแบบไม่ต้องรู้พื้นฐานมาก่อน)

GPU มีหน่วยความจำของตัวเอง (VRAM) แยกต่างหากจาก RAM ปกติของคอม — เครื่องเช่านี้มี VRAM 95GB ตอนเทรนโมเดล AI ตัวโมเดลเองต้องถูกโหลดเก็บไว้ใน VRAM ก่อน (35 พันล้าน parameter แบบ bf16 กิน VRAM ไปแล้วส่วนใหญ่) แล้วตอนคำนวณ (ทั้งตอนอ่านภาพ/ทายคำตอบ และตอนคำนวณปรับน้ำหนัก) ต้องมีที่ว่างเหลือไว้เก็บ "ค่ากลาง" ระหว่างการคำนวณด้วย (เรียกว่า activation memory) — ยิ่งข้อความ/ภาพที่ป้อนเข้าไปยาว/ใหญ่เท่าไหร่ ค่ากลางที่ต้องเก็บก็ยิ่งเยอะตาม

ที่พังตรงนี้เพราะ **ใช้ VRAM ไปแล้ว 94.87GB จากทั้งหมด 94.97GB (เหลือว่างแค่ 96MB) แต่ต้องการเพิ่มอีกแค่ 100MB ก็ยังไม่พอ** — เฉียดฉิวมาก (ขาดแค่ ~0.1% ของทั้งหมด) ไม่ใช่พังเพราะตั้งค่าผิดร้ายแรง แค่ตั้งไว้ "เผื่อเกินจริง" นิดหน่อยจนล้นไปนิดเดียว

### ทำไมถึงเฉียดฉิวขนาดนี้ — พบว่า `MAX_LENGTH` ตั้งไว้เผื่อเกินจำเป็น

`MAX_LENGTH` คือความยาวสูงสุด (นับเป็น "token" ซึ่งเป็นหน่วยย่อยของข้อความ ประมาณคำหรือพยางค์) ที่ยอมให้ 1 ตัวอย่างมีได้ ตอนแรกตั้งไว้ที่ 10,240 โดยประมาณคร่าวๆ ว่า "คำสั่ง ~1,020 + รูปภาพ 5,120 + คำตอบยาวสุด ~2,750 + เผื่อเหนียว"

แต่พอไปเปิดไฟล์ `stats.json` (ไฟล์สรุปสถิติที่สร้างไว้ตอนเตรียม dataset) ดูตัวเลข**จริง**จากข้อมูล 226+88 ตัวอย่าง พบว่า:
- คำสั่ง (instruction) = 1,022 token (ตรงกับที่ประมาณไว้)
- คำตอบยาวสุดจริงที่เจอ (ทั้ง train และ val) = 2,748 token (ไม่ใช่แค่ "ประมาณ 2,750" แต่นี่คือค่าที่วัดจากของจริงทุกตัวอย่างแล้ว)
- รวมกับภาพ 5,120 token = 1,022 + 5,120 + 2,748 = 8,890 token คือความยาวสูงสุดที่ "จะเกิดขึ้นจริง" ได้

เพราะฉะนั้น 10,240 ที่ตั้งไว้เดิมมีช่องว่างเหลือเฟือถึง 1,350 token ที่ไม่มีวันถูกใช้จริง (ไม่มีตัวอย่างไหนยาวขนาดนั้น) — ช่องว่างที่ "จองไว้เฉยๆ" นี้ทำให้ GPU ต้องเตรียมที่เก็บ activation memory สำหรับความยาวสูงสุดที่ตั้งไว้ (ไม่ใช่ความยาวจริงที่ใช้) ทำให้เปลืองที่โดยไม่จำเป็น

### 3 วิธีแก้ที่ใช้ (ทั้งหมด "ไม่กระทบคุณภาพโมเดล" — แค่จัดการหน่วยความจำให้ฉลาดขึ้น ไม่ได้ลดสิ่งที่โมเดลเห็น/เรียนรู้)

**(1) ลด `MAX_LENGTH` จาก 10,240 → 9,216**
ใช้ตัวเลขจริงจาก stats.json (8,890) บวกกันชนไว้อีก ~330 token (เผื่อ token พิเศษเล็กๆ น้อยๆ ที่ template อาจแทรกเพิ่ม) แทนที่จะเผื่อเกินจริงแบบเดิม — ตัด "ที่ว่างที่ไม่มีวันได้ใช้" ออกไป ไม่ตัดเนื้อหาจริงตัวอย่างไหนเลยสักตัว (เพราะไม่มีตัวอย่างไหนยาวเกิน 8,890 อยู่แล้ว)

**(2) เพิ่ม `PYTORCH_ALLOC_CONF=expandable_segments:True`**
นี่คือค่าที่ตั้งให้ตัวจัดการหน่วยความจำของ PyTorch (โปรแกรมที่ใช้คำนวณ AI) เอง — ปกติเวลาโปรแกรมขอ-คืนหน่วยความจำ GPU ไปเรื่อยๆ จะเกิด "หน่วยความจำเป็นเสี่ยงๆ ไม่ต่อเนื่องกัน" (fragmentation) เหมือนที่จอดรถที่มีช่องว่างกระจายเป็นชิ้นเล็กๆ ทั่วลาน แม้รวมกันจะพอจอดรถคันใหญ่ได้ แต่ไม่มีช่องเดียวที่ยาวพอ — `expandable_segments:True` คือสั่งให้ปรับขนาดก้อนหน่วยความจำที่จองไว้ให้ยืดหยุ่นได้มากขึ้น ลดปัญหานี้ (PyTorch เองแนะนำ flag นี้ตรงๆ ใน error message ที่เจอ)

**(3) เปลี่ยน optimizer จาก `adamw_8bit` → `paged_adamw_8bit`**
"Optimizer" คือส่วนที่คำนวณว่าจะปรับน้ำหนักโมเดลไปทางไหน/เท่าไหร่ในแต่ละก้าว มันต้องเก็บ "ค่าสถิติ" ของแต่ละพารามิเตอร์ไว้ด้วย (กิน VRAM เพิ่ม) — แบบ "paged" คือยืมแนวคิดจาก "virtual memory" ของคอมทั่วไป (ตอน RAM ไม่พอ คอมจะย้ายบางส่วนไปพักที่ฮาร์ดดิสก์ชั่วคราว) มาใช้กับ VRAM/RAM แทน ป้องกันไม่ให้ตอน optimizer ทำงานแล้วขอหน่วยความจำพุ่งพรวดเดียวจนล้น (เปลี่ยนจาก optimizer ตัวเดิมที่คำนวณแบบเดียวกันทุกอย่าง แค่วิธีจัดการหน่วยความจำต่างกัน ไม่กระทบผลลัพธ์การเทรน)

### ทำไมไม่แก้ด้วยการ "ลดความละเอียดภาพ" (`MAX_PIXELS`) แทน
เป็นอีกทางที่ทำได้ (ภาพเล็กลง = token น้อยลง = ประหยัด VRAM) แต่**ไม่เลือกทำ**เพราะค่า 5,120 tokens ไม่ใช่เลขสุ่ม — เป็นค่าที่ทดสอบจริงมาก่อนหน้านี้แล้วว่าเป็นจุดต่ำสุดที่ยังแยกจุดเหล็กบน/ล่างในแบบ (rebar dots) ออกจากกันได้ ถ้าลดต่ำกว่านี้จะเสี่ยงโมเดลอ่านตัวเลขเหล็กผิด (ปัญหาที่เจอบ่อยตามที่บันทึกไว้ใน CLAUDE.md ของโปรเจกต์) — จึงเลือกแก้จุดอื่นที่ไม่กระทบคุณภาพแทน ตามกฎที่ตั้งไว้ใน `rule_of_tune.md` ข้อ 2 (ค่าที่กระทบว่าโมเดลเห็น/เรียนรู้อะไร ต้องเตือน/ขออนุญาตก่อนแก้เสมอ — 3 วิธีที่เลือกใช้ข้างบนไม่เข้าข่ายนี้ เพราะเป็นแค่การจัดการหน่วยความจำ)

### สถานะล่าสุด ณ ตอนบันทึกนี้
อัปโหลดไฟล์ที่แก้แล้ว เริ่มรันทดสอบ `TEST_STEPS=5` รอบที่ 3 อยู่ (รอบ 1 = เจอบั๊ก D/E/F, รอบ 2 = บั๊กหมดแต่ OOM, รอบ 3 = หลังแก้ OOM) — ยังไม่ทราบผล

**ไฟล์ที่เปลี่ยนเพิ่มรอบนี้:** `train_qwen36.py` — เพิ่ม `os.environ.setdefault("PYTORCH_ALLOC_CONF", ...)` ต้นไฟล์ (ก่อน import torch), ลด `MAX_LENGTH` 10240→9216, เปลี่ยน `optim="adamw_8bit"` → `"paged_adamw_8bit"`

### ผลทดสอบรอบ 3 (หลังแก้ MAX_LENGTH/PYTORCH_ALLOC_CONF/paged optimizer): ยังพัง OOM เหมือนเดิม

ตัวเลขเปลี่ยนแทบไม่มีนัยสำคัญ (เหลือว่าง 98.25MB แทน 96.25MB — แทบเท่าเดิม) แปลว่า 3 อย่างที่แก้ไปรอบก่อน**ไม่ใช่ตัวการหลัก** ของปัญหานี้จริงๆ — เหตุผลคือ MAX_LENGTH ที่ตั้งไว้เป็นแค่ "เพดานสูงสุดที่ยอมให้ได้" แต่ตัวอย่างจริงที่ใช้ทดสอบ (5 step) อาจไม่ได้ยาวใกล้เพดานนั้นอยู่แล้ว การลดเพดานที่ไม่มีวันถูกแตะไม่ช่วยอะไร

### เจาะ log ลึกกว่าเดิม พบจุดพังจริง: บัฟเฟอร์ของ LoRA เอง ไม่ใช่ความยาวข้อความ

อ่าน error แบบเจาะบรรทัดพบว่าโค้ดพังตรง `lora_delta = torch.empty(...)` ใน `forward_native_grouped_mm` — เป็นขั้นตอนคำนวณ **LoRA** (เทคนิคปรับแต่งโมเดลแบบประหยัด ไม่ต้องแก้น้ำหนักทั้งก้อน แค่เพิ่ม "ตัวปรับแต่งเสริม" ขนาดเล็กเข้าไปแทน) ของ **MoE experts** (ผู้เชี่ยวชาญย่อย 256 ตัวในโมเดล) — ยิ่ง LoRA ตัวปรับแต่งนี้มีขนาด (rank) ใหญ่เท่าไหร่ ก็ยิ่งกิน VRAM ตอนคำนวณเท่านั้น และเพราะมี MoE experts ถึง 256 ตัว (ไม่ใช่แค่ 1 ชุด) ตัวปรับแต่งนี้เลยคูณกันเข้าไปเยอะกว่าโมเดลทั่วไปมาก

### ทางเลือกที่เสนอมะขาม (จุดนี้กระทบคุณภาพการทูนจริง ต้องขอก่อนตามกฎ rule_of_tune.md ข้อ 2)
เสนอ 3 ทาง: (1) ลด `LORA_R` 64→32 (ประหยัด ไม่ต้องเช่าเครื่องใหม่ แต่ตัวปรับแต่งเล็กลง), (2) เช่า GPU ใหญ่กว่า (H200 141GB) แทน (ไม่ต้องลดคุณภาพอะไรเลย แต่แพงขึ้น+ต้องสร้าง instance ใหม่), (3) ตัด LoRA ออกจากชั้น MoE experts ไปเลย (คงคุณภาพเฉพาะจุดอื่น แต่ MoE routing ที่เป็นหัวใจของโมเดลนี้จะไม่ถูกปรับเลย)

**มะขามเลือกทางที่ 1 — ลด `LORA_R` 64→32** (พร้อม `LORA_ALPHA` 128→64 ตามสัดส่วนเดิม) เหตุผลที่สนับสนุนทางนี้เพิ่มเติม: งานวิจัยเรื่อง fine-tuning ที่คุยกันไปตอนเลือกโมเดล (บันทึกไว้ตอน 2026-07-20) บอกว่า dataset เล็ก (226 ตัวอย่าง) เข้ากับ rank ต่ำกว่ามากกว่า ไม่งั้นเสี่ยง overfitting/บิดเบือนความรู้เดิมของโมเดล (catastrophic forgetting) — เพราะฉะนั้นการลด rank รอบนี้ไม่ใช่แค่ "ยอมเสียคุณภาพเพื่อประหยัด VRAM" เฉยๆ แต่อาจจะเหมาะสมกับขนาด dataset ของเรามากกว่าเดิมด้วยซ้ำ

### สถานะล่าสุด ณ ตอนบันทึกนี้

**บทเรียนบันทึกลง memory:** ห้าม `pip install` ในเครื่องเดียวกันขณะมีงานสำคัญรันอยู่ ต้องแยก venv เสมอ (นอกจากนี้ยังพบว่า `llama.cpp` build ด้วย CUDA พังเพราะ cmake หา nvcc ไม่เจอ + เจอ `$PATH` โดน PowerShell ตีความเองจนพัง PATH ของ window นั้นไปด้วย — สรุปว่ายังไม่จำเป็นต้องมี CUDA build สำหรับงานแปลง GGUF/quantize เพราะเป็นงาน CPU ล้วน เปลี่ยนไปทำ CPU-only build แทนได้)

### สถานะล่าสุด ณ ตอนบันทึก
Environment ซ่อมเสร็จสมบูรณ์ กำลังรัน `eval_fields.py --adapter outputs_qwen36/lora --limit 20` เพื่อวัดผลจริงของโมเดลที่ทูนแล้ว เทียบกับ baseline (0/20 JSON valid, 0/170 element หาเจอ) — ยังไม่ทราบผล

**ไฟล์ที่เปลี่ยน:** ไม่มีไฟล์โค้ด (แก้ที่ pip package บนเครื่องเช่าเท่านั้น)

## Claude — ผลวัดคุณภาพจริง + merge/GGUF/quantize จบรอบคืนนี้

### ผลวัดคุณภาพโมเดลที่ทูนแล้ว (`eval_fields.py --adapter`, เทียบ baseline)

| ตัวชี้วัด | ก่อนทูน | หลังทูน |
|---|---|---|
| JSON valid | 0/20 (0%) | **18/20 (90%)** |
| View ตรงเป๊ะ | 0/20 (0%) | **12/20 (60%)** |
| Element หาเจอ | 0/170 (0%) | 16/170 (9.4%, เกิน 61 ตัว) |
| field exact-match (จับคู่ได้) | — | element_id 100%, element_type 87.5%, count 100% |

**สรุป: การทูนได้ผลจริง** (0%→90% JSON valid) จุดที่ต้องปรับปรุงต่อ (รอบทูนหน้า) คือ element recall

### Merge → GGUF → Quantize (ทำสำเร็จ, มีปัญหาระหว่างทางหลายจุด)

1. `merge_lora.py` — รวม LoRA adapter เข้ากับโมเดลต้นฉบับ (PEFT `merge_and_unload()`) สำเร็จ
2. **บั๊ก disk เต็มซ้ำหลายรอบ:** ต้องลบ checkpoint เก่า (44GB), ลบ HF cache โมเดลต้นฉบับหลังโหลดเข้า RAM แล้ว (67GB), ลบ pip cache (5.4GB), ลบไฟล์ intermediate (q8_0/f16 หลังใช้เสร็จ) ตลอดกระบวนการ — ครั้งหนึ่งดิสก์เต็ม 100% พอดีตอนแปลง f16 เสร็จ ต้องลบ merged/ ด่วน
3. **บั๊ก:** ลองแปลงเป็น `q8_0` ก่อน (เล็กกว่า ประหยัดดิสก์) แต่ `llama-quantize` ปฏิเสธ "requantizing from type q8_0 is disabled" — ต้องแปลงใหม่จาก `f16` (ใหญ่กว่า ~70GB) แทน
4. **บั๊ก:** `llama.cpp` build ด้วย CUDA พังซ้ำ 3 รอบ (cmake หา nvcc ไม่เจอ + เปิด CUDA auto-detect เองแม้ระบุ OFF) — สุดท้ายพบว่างาน convert/quantize ไม่ต้องการ GPU เลย ใช้ CPU-only build (`-DGGML_CUDA=OFF` รันในหน้าต่างสะอาดใหม่) แก้ปัญหาได้
5. **quantize สำเร็จ:** f16 (66,152 MiB) → Q4_K_M (20,176 MiB, 4.88 bits/weight) ได้ไฟล์ `qwen36-tuned-Q4_K_M.gguf` 21.2GB

### ⚠️ ปัญหาที่ยังไม่แก้: mmproj (ส่วนอ่านภาพ)

โมเดลนี้เป็น vision model (ต้องอ่านภาพแบบก่อสร้าง) แต่ **ไฟล์ GGUF ที่ได้ตอนนี้รองรับแค่ข้อความ** — mmproj (ส่วนแปลงภาพ) ต้องสกัดแยกจากโมเดลต้นฉบับ (ลบ `merged/` ไปแล้วก่อนสกัด เป็นความผิดพลาด) และเอกสาร llama.cpp เขียนเตือนเองว่า `--mmproj` "จะได้ผลแค่กับบางโมเดล" — สถาปัตยกรรม Qwen3.6 ใหม่มาก อาจไม่รองรับการแยก vision ออกจาก GGUF ได้เลย ต้องทดสอบเพิ่มวันหลัง

**มะขามตัดสินใจ:** หยุดที่นี่คืนนี้ ไม่เสี่ยงลองต่อ (ใช้เวลา+อาจพัง) — **ทางที่ยืนยันแล้วว่าอ่านภาพได้จริง 100% คือรันผ่าน Python/Unsloth บนเครื่องเช่า GPU** (แบบที่ `eval_fields.py` เพิ่งวัดผลสำเร็จ) ไม่ใช่ทาง GGUF

### ค้างไว้ / ทำต่อวันหลัง
- อัปโหลด `qwen36-tuned-Q4_K_M.gguf` ขึ้น HuggingFace (ยังไม่ได้ทำ — ต้องมี HF token ก่อน)
- แก้ปัญหา mmproj/vision ใน GGUF (ไม่แน่ใจว่า llama.cpp รองรับสถาปัตยกรรมนี้ไหม)
- ทูนรอบหน้า: แก้ปัญหา element recall ต่ำ (9.4%) — อาจต้องเพิ่มข้อมูล/epoch/ปรับ prompt
