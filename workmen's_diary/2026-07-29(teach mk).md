### What's broken — and broken in a very strange way

**a. Not a single page answers in the schema it was trained on (0/6)**

```
gold uses keys:  "png" / "doc_page" / "discipline" / "sheet_code"
AI answered:     "page" (page 01)
```

**b. Hallucinating things that do not exist (page 06 is the worst)**

**`A-05` is not a column name, it is a sheet number** (A-05 = the elevation sheet, A-07 = the section sheet)
The drawing carries text along the lines of *"ดูรายละเอียดที่แผ่น A-05"* — the AI saw it and **assumed it was the column's name**

> Like reading a book, coming across *"continued on page 57"*, and concluding that **"there is a character named Mr. Page 57"**
> — it can read the text, but **does not understand what that text is there to do**

**c. Inventing its own geometry numbers**

```
gold horizontal grid:  D=0,   C=4.0,  B=6.0,  A=9.5
AI answered:           A=0,   B=1.5,  C=5.0,  D=9.5
```

And on page 06 it built a `grid_table` giving one value per grid **intersection**,

→ **every span computed downstream of this is wrong**

**d. Contradicting itself**
```
F6 = ["C-2","C-3","D-3","D-2"]  → "เตรียมอาหาร"
F7 = ["C-3","C-2","D-2","D-3"]  → "นอน 2"
```

**e. The entire confidence layer is gone** — the gold has `confidence_score` + `confidence_flags`

## 3. 🔑 The key clue: "broken in a way that is unnatural for a model that has actually been tuned"

This is the heart of it — read slowly

### The fact that changes everything

**Pages 03-06 are t01's own training data** — the model has seen these pages together with their answer key
during training, **3 times (epochs)**

### So why is that strange

In fine-tuning there is one thing a model **always learns fastest**: **the "shape of the answer" (format)**
— which key names to use, what the JSON structure looks like. The model picks that up within the first few hundred steps of training.

**Content** is far harder (it has to read the numbers on the drawing correctly) — getting that wrong is not strange.

But tonight we found **exactly the opposite:**
```
content (the hard part):  done well — มอก. numbers 8/8, floor levels 7/8, rooms 8/8
format (the easy part):   entirely broken — 0/6 pages, and 3 forms alternating with each other
```

**This is unnatural.** If the model had really been tuned, the format would always be exact before the content is.

### What this kind of result most resembles is...

**A blank model that has never been tuned, handed a prompt that describes the schema to it**
— it will try to follow the prompt (hence the `views`/`pattern` the prompt calls for)
but it will not know keys like `png`/`doc_page`, which **exist only in the gold and are never written in the prompt**

**And that is exactly what we are seeing**

## 4. 🔑 The evidence that raises the suspicion that the LoRA is not in the GGUF

I opened the real code and found 2 things that join up into a single story

### Evidence A — t01 uses the same LoRA mechanism that broke t02

Open `train_qwen36.py` line 152 — there is a comment we wrote ourselves back on the 21st:

```python
lora_dropout=0,   # ต้องเป็น 0 — MoE ParamWrapper ของโมเดลนี้ไม่รองรับ dropout!=0
```

**The word `ParamWrapper` matters enormously** — it is peft's special mechanism for attaching a LoRA
onto the "experts" of an MoE-style model

**And on the night of the 28th we already proved with our own hands that:**
> `merge_and_unload()` (the function that merges the LoRA into the model before GGUF conversion)
> **merges a ParamWrapper-style LoRA on MoE incorrectly** — we measured the real values across an entire tensor of 201 million values
> and found that only **0.67%** of them changed, when far more should have changed
> = **the structure passes, no error is raised, but the behavior falls almost all the way back to the blank model**

**t01 uses the same function, on the same kind of MoE model, with the same ParamWrapper**

### Evidence B — t01's check is so weak that even a blank model passes it

During GGUF conversion we already have a check guarding against a "silent merge failure".
Open `export_gguf.py` line 107:

```python
_looks_tuned = _pred.lstrip().startswith("{") and any(k in _pred[:400]
               for k in ('"png"', '"views"', '"pattern"', '"doc_page"'))
```

Which means: *"if the answer starts with `{` **and** contains any one of these 4 words → consider it tuned"*

**The problem is that our own prompt says outright:**
```
...emit one entry per view in "views"
Each view carries its own "pattern": plan, section, schedule, ...
```

→ **the prompt hands the words `views` and `pattern` to the model already**
→ any model capable of following the prompt will emit those two words
→ **a model that has never been tuned at all sails right through this check**

At the GGUF conversion on the 24th this check showed a green ✓ **and we believed it**
— but in truth **it proved nothing whatsoever, not even slightly**

### Why t02 got caught but t01 slipped through

```
t02 (on the 28th):  the check compared "the real key names" → found page_number/title/project
                    instead of png/doc_page/... → ❌ stopped immediately ✅ worked correctly

t01 (on the 24th):  the check only asked "is the word views or pattern present?"
                    → ✓ passed (but passed because the prompt said so, not because the tuning succeeded)
```

**The same bug — the only difference is the quality of the check**

### 🧪 How to prove it — cheap and fast, can be done tomorrow

> Take the **blank Qwen3.6 model (base, untuned)** and run page 03 with the same prompt
> - If the output **looks like** t01's → **confirmed: the LoRA is not in the GGUF**
> - If the output is **clearly worse** → the LoRA really is there, and we must look at other causes
>
> Takes ~20 minutes, **free, nothing needs renting**, and **must be done before spending money on anything at all**

## 5. Two more secondary causes (both real, but neither is the main one)

### 5.1 Training and inference see the image at resolutions 14× apart

`llama-server`'s log reports the actual number of visual tokens fed in:
```
2048 + 1748 = 3,796 tokens/image   ← at inference tonight
        ~266 tokens/image          ← at training (the collator bug shrank it to 512px)
        a 14.3× difference
```

> **An analogy:** teach a child to read maps using blurry black-and-white maps all semester; the child scores 90 on the blurry-map exam.
> On the real exam day you hand them a colour map at 14× the resolution — the child has not gotten dumber,
> it is just **"nothing like what they ever practised on"**

llama.cpp even warned us in the log itself (but nobody read it):
```
W load_hparams: Qwen-VL models require at minimum 1024 image tokens to function correctly
W load_hparams: if you encounter problems with accuracy, try adding --image-min-tokens 1024
```

**Sub-lesson:** warnings at model load are routinely overlooked because they appear mixed in with hundreds of other lines
— **this is the same pattern happening for the 2nd time** (the first was the collator printing
`Model does not have a default image size - using 512` and nobody seeing it — exactly the same)

### 5.2 The compression (quantization) that the model's own makers warn against

**What quantization is:** a model is billions of numbers, normally stored at high precision (bf16).
Quantizing = lowering that precision so the file is small enough to run on a small machine.
`Q4_K_M` → from 70GB **down to 21GB**

> Like JPEG-compressing a photo — compress a little and you barely see a difference; compress a lot and blocky blur starts to show

**The `t01_workflow.md` document itself records that** Unsloth (the model's makers) warn that this family
*"loses quality abnormally once quantized"* — which is the reason we **mandated bf16 training and banned 4-bit**

**But when it came time to use it, we compressed it to Q4_K_M anyway** (out of necessity — a laptop with 8GB VRAM
cannot take 70GB) **and then never went back to re-measure whether it was still accurate after compression**

→ **We were careful about this during training, but forgot to be careful at inference**

```
Path A — at evaluation time (eval_fields.py)
  the full 70GB bf16 model  +  LoRA adapter attached at runtime (not merged)
  → gives 90% JSON valid, 28.2% element recall
```

I opened `eval_fields.py` line 29 and it says `load_in_4bit=False`
= **measured with the full model, uncompressed, and without going through the merge step**

> **An analogy:** testing a new car only for "does it start, does it go into gear" → it does →

## 7. Why it is slow — the real numbers and the reason

| Thing | Speed |
|---|---|
| reading the image + prompt | 3,924 tokens @ ~28 t/s = **~140 seconds** |
| writing the answer | **3.46 tokens/second** |
| full extraction of 1 page | ~13-21 minutes |
| classify 1 page | ~2.4 minutes |

### The reason — simple arithmetic
```
model file  21 GB
VRAM         8 GB      → only ~1 in 3 fits onto the graphics card; the rest runs on the CPU
```
The log confirms it outright: `failed to fit params to free device memory ... abort`

**An interesting detail:** the GPU shows 100% but draws only **33.7W** (this card can draw far more than that)
— meaning the card **is not working hard, it is just waiting on the CPU the whole time**. The CPU is the real bottleneck.

### Why classify is 7× faster than a full extraction, even though it looks at the same image

Because most of the time goes into **"writing the answer"**, not "looking at the image"
```
classify:      look at image 140 s + write ["plan","schedule"] ~10 tokens = 3 s   → ~144 s
full extract:  look at image 140 s + write long JSON ~3,800 tokens = 1,100 s      → ~1,250 s
```
**At 3.46 tokens/second, every token that has to be written is real time spent**
→ this is why the 2-phase plan (fast scan first, then extract only the pages needed) genuinely helps

## 8. The bug I made myself tonight — the lesson "silent ≠ hung"

I set the timeout to 1,200 seconds (20 minutes), calculated from pages 01-02.
Then page 03 came along and took 1,256 seconds → **I killed work that was genuinely still running**

**How we knew it was not hung:** check `nvidia-smi` → the GPU is still working at 100% (a real hang would show 0%)

**Lesson 1:** "no output" ≠ "hung" — a model that is thinking is silent in exactly the same way.
Other indicators have to be checked (GPU util, a file growing) before concluding it is dead.
Had I believed the silence, I would have spent the whole night fixing the wrong thing.

**Lesson 2:** pages 01-02 are **the cover and the table of contents** = the lightest in the book.
Taking the timing from those two pages and setting the threshold for the whole book → wrong from the start.
**The sample used to set a threshold must cover the heaviest case, not the case that happened to come first.**

## 9. ⚠️ Caveats when interpreting tonight's results (important, do not skip)

Do not rush to conclude that "this model is unusable", because **tonight's test was itself unfair to the model**:

1. **Pages 03/04/05 = index / notes / material_list / site_plan**
   which are patterns that the new plan (`KEEP_PATTERNS`) **already filters out**
   → judging the model on them = judging it on work it will never be used for

2. **Not a single structural page (S-*) has been extracted yet** — pages 07-11 were only classified
   → the prompt's biggest rule (*"แยกเหล็กบน/ล่างเสมอ"*) **has no evidence either good or bad**
   → **we still have no idea how well it extracts rebar**, which is the real job we want

3. **The classification itself is not accurate either** — pages 07/08/09 were classified as `section`
   but the gold is `side_profile` (reading an **elevation** as a **section**), and it claimed 5 views when there are really 2
   → if the classification is wrong, pages that should be extracted may get skipped, or pages that should be skipped get extracted

## 10. Tonight's lessons — 6 things worth remembering

1. **"tuned successfully" ≠ "usable"**
   Between those two there are several more layers: merge → quantize → switch the program that runs it.
   **Every layer can change the result, and every layer has to be re-measured.**

2. **A check that is too easy to pass is worse than no check at all**
   because it gives false confidence. `export_gguf.py:107` showed a green ✓ from the 24th onward
   and we believed it ever since. **A check has to be asked: "if the thing really were broken, would this check catch it?"**
   — if the answer is "no", that check is worthless.

3. **Watch the "shape of the errors", not just "how much is wrong"**
   Tonight's most important clue was not "lots of errors" but **"wrong on the easy things, right on the hard things"**,
   which is unnatural → and that led to finding the real cause.
   Looking only at an aggregate score would never have found it.

4. **An accuracy figure has to come with the question "measured on what?"**
   Our 90% was measured on bf16 + an unmerged adapter — not on the thing that actually runs on the machine.

5. **The input at inference must be the same as the input at training**
   (the formal term: *train/inference mismatch*) — the moment they differ by 14×, the knowledge from training is instantly unusable.

6. **Warnings the program prints have to be read** — this pattern has now come up twice.
   Next time, read through the model-load warnings every time before starting a long run.
