### 1.2 What is "element recall" — a term you need to understand before reading on

This term shows up throughout the document, so you need to understand it first

Suppose a beam-plan page **has 15 real beams** (this is the "answer key" a person sat down, read off the drawing and wrote down)
We have the AI read the same page; the AI answers with 3, and only 2 of them are actually correct

- **recall** = real items found ÷ all real items = 2 ÷ 15 = **13%**
- In plain words: "**what percentage of what should be found was actually found**"

**recall 0% means the AI didn't find a single one** — not that it found them but read the values wrong, but that it **didn't see them at all**

### 1.3 Why is it that bad

When we looked at what the AI actually answered, we found that on the hard beam-plan pages it wrote this:

```json
{
  "png": "20",
  "sheet_code": "S-03",
  "elements": []          ← empty
}
```

**It wrote only the page-header info and then closed the file right away, without putting in a single beam** — and worse than that,
the header info it wrote even pointed to the wrong house (it said house 22 even though it was reading house 08)
It's as if it **remembered a template from examples it had seen before and pasted it in**, without really looking at the image in front of it

This isn't a "misread the numbers" problem, it's a "**can't see that something is there**" problem
— and this is the key clue that led to today's work

## 3. What Template Matching is — taught from scratch

Now into the main content, explained from scratch — no prior background needed

### 3.1 The principle: a "spot the difference" game the computer plays for us

Picture this:

1. You cut a small window out of paper, the size of one footing symbol — it's called a **template (แม่แบบ)**
2. You lay that window over the big construction drawing sheet, starting at the very top-left corner
3. Give it a score for "how similar is this spot to the template" — the score runs from 0 to 1
4. **Slide 1 pixel to the right** and score it again
5. Keep doing this until you've covered the whole sheet, one pixel at a time

When it's done, we get a "score map" that tells how similar every position on the drawing is to the template
Wherever the score is high = that's where the thing we're looking for is

**The command that does all of this is just one line:**

```python
คะแนน = cv2.matchTemplate(ภาพใหญ่, แม่แบบ, cv2.TM_CCOEFF_NORMED)
```

`cv2` is the name of the OpenCV library — an image-processing tool used all over the world for 20 years, and it's free

### 3.2 Why it's so fast (and needs no GPU)

One page of our drawings is 3309 × 2339 pixels = **7.7 million positions** to lay the template over and score
That sounds like a lot, but the machine finishes in **under 1 second** on an ordinary CPU

Because it's only multiply-and-add arithmetic with no "thinking" at all — unlike AI, which has to compute through
a neural network of several billion parameters

> **This is why this tool is valuable:** it's free, fast, and **gives the same result every time**
> Run it ten times and you get exactly the same answer — unlike AI, which doesn't give the same answer twice

### 3.3 6 scoring methods — and why we chose this one

OpenCV lets you choose from 6 formulas for scoring similarity:

| Formula | How to read the result |
|---|---|
| `TM_SQDIFF`, `TM_SQDIFF_NORMED` | **the lower, the more similar** (measures difference) |
| `TM_CCORR`, `TM_CCORR_NORMED` | the higher, the more similar |
| `TM_CCOEFF`, **`TM_CCOEFF_NORMED`** | the higher, the more similar ← **we use this one** |

**Why we chose `TM_CCOEFF_NORMED`:**

- The word **`NORMED`** (normalized = adjusted to a standard scale) means the score always stays in the range **0 to 1**,
  which lets us set a threshold, e.g. "keep only those above 0.6". Without normalizing, the score would be some
  who-knows-what number and no threshold could be set
- The word **`CCOEFF`** (correlation coefficient) is the formula that **subtracts the average brightness before comparing**
  This matters a lot for our work, because the drawings are **scanned** images — some pages scan out greyish, some come out very white
  This formula looks at the "pattern", not the "brightness" → even a page that scanned dark can still be detected

### 3.4 threshold (cutoff) — the knob you have to turn yourself

Once we have the score map, we have to say "how high does a score have to be to count as a find" — that's the **threshold**

- **Set too high (e.g. 0.95)** → few finds, lots of real ones slip through
- **Set too low (e.g. 0.3)** → lots of finds, but it also grabs text/table borders

The values we actually use (found by actually trying, not guessed):

| Type | Threshold | Reason |
|---|---|---|
| Footing | 0.60 | Very distinctive shape — setting anywhere from 0.5-0.8 gives the same 14/14 |
| Column | 0.65 | Small shape — needs to be a bit stricter, otherwise it makes false hits |
| Beam | 0.70 | Plain lines that look like lots of other lines — needs to be the strictest |

### 3.5 NMS — the problem everyone runs into, and how to fix it

**Problem:** if a footing sits at coordinates (1240, 766) and we slide the template to (1241, 766) — moving it
just 1 pixel — it **still matches** and the score is still high

So 1 footing produces high-scoring points **by the hundreds**, clustered around each other
In reality we have 14 footings, but the system reports **235 points**

**The fix is called NMS (Non-Maximum Suppression)** — literally "suppressing the ones that aren't the maximum"
The idea is very simple:

1. Sort all the points from the highest score down
2. Take the highest-scoring point and keep it = "this one is definitely real"
3. **Delete every point close to that point** (closer than half the template's size) — because it's the same object
4. Take the next one that's still left, loop back to step 2

**Our actual result:** 235 points → NMS → **14 points**, an exact match with reality

### 3.6 Limitations to know from the start

The research I read (SkeySpot, 2025 — work on detecting symbols on electrical drawings) says it clearly:

**Template matching breaks when:**

1. **The symbol is rotated** — if the template is vertical but the real one is tilted 30 degrees, it won't catch it at all
2. **The symbol is a different size** — a 56px template against a real 40px one doesn't match either
3. **The symbol is drawn differently** — different design offices draw it differently

**We actually ran into both #2 and #3 today** (told in chapter 5)
The research recommends Deep Learning (YOLO) instead — but YOLO needs someone to sit and **draw boxes to train it**
on thousands of images first, which we don't have time for, so template matching is the better-value route for now

### 4.3 Beams are special — not cropped from an image, but **drawn by us**

Beams are the exception, because **beams have no fixed size** — a short-span beam is 300px long, a long-span beam 900px long
so you can't crop one into a template, because you wouldn't know how long to crop it

**What stays constant is its "cross-section"** — on a plan, a beam is drawn as **2 parallel black lines**
(the beam's two edges), so we drew the template ourselves like this:

```python
def beam_template(gap=21, thick=3, length=60):
    tpl = all white, size (33 × 60)
    tpl[6:9,   :] = black   # top edge line of the beam
    tpl[27:30, :] = black   # bottom edge line of the beam
    return tpl
```

The number `gap=21` (a 21-pixel spacing) **wasn't guessed** — I measured it on a real image and found the beam's top edge
sits at rows y=758-760 and the bottom edge at y=777-779 → 21 pixels apart

Then: search for this short template across the whole page → you get points strung out along long lines → **join adjacent points into a single band**
→ throw away bands shorter than 100 pixels (so it doesn't catch text)

> **⚠️ A caveat already noted in the code:** this number 21 is tied to this set's scan resolution
> (3309×2339, scale 1:75) — if you come across a house scanned at a different resolution, you have to adjust it yourself
> with the `--beam-gap` option

## 5. The 2 bugs found today — and how to think when fixing them

This part matters more than the tool itself, because it's a way of thinking you can reuse on every job

### 5.1 Bug 1 — F1 and F2 don't differ just in "size", they differ in "shape"

**Symptom:** when we tried house 12 (the 2nd house), the system found only **6 of 12** footings

**My first hypothesis (wrong):** "it's probably because this house draws the icons at a different size"
So I added **multi-scale**, i.e. shrinking/enlarging the template to 6 sizes (0.7, 0.8, 0.9, 1.0, 1.1, 1.2×)
and searching at every size

**Result: still 6, same as before** → the hypothesis was wrong

**So I went and actually opened the image** — cropped the two icons out to look at side by side, and saw it right away:

| | F1 | F2 |
|---|---|---|
| Shape | Nested **squares** | Vertical **rectangle** |
| Inside | 1 cross | 1 cross + **2 pile dots, top and bottom** |

![The 3 footing templates](img_teach_2026-08-25/templates.png)

*The actual templates used — left/middle are F1 from the two houses (nested squares), right is F2 (rectangle + pile dots top and bottom)*

**They're two different things, not the same thing at different sizes** — F1 is a 1-pile footing,
F2 is a 2-pile footing; they differ by design, not by how they're drawn

**The fix: a template bank (a library of templates)** — instead of having a single template, keep several kinds in a folder
and search for every one of them, then merge the results and run NMS once

```python
def load_templates():
    # read every file whose name starts with tpl_footing
    for p in sorted(TEMPLATE_DIR.glob("tpl_footing*.png")):
        ...
```

The upside is that **if we hit a house that draws its footings a new way, we just crop the image and add it to the folder — no code changes at all**

**Result after the fix: 12/12** ✅

![House 12 foundation plan after the fix — 12/12](img_teach_2026-08-25/house12.png)

*House 12 after adding the template bank — catches both F1 (top/bottom rows) and F2 (middle row), all 12 of them; notice that F2's red boxes are taller, because the icon is a different shape*

> **Lesson:** a first hypothesis that sounds reasonable (different sizes) can be wrong
> The right way to prove it is to **open the real thing and look with your own eyes**, not keep guessing and write more code
> — this is the same lesson as rule 14 in `rule_of_tune.md`

### 5.2 Bug 2 — footings showing up on the beam plan, even though a beam plan has no footings

**Symptom:** once the F2 template (vertical rectangle) was put into use, it turned out that on house 12's **beam plan**
it drew 3 red boxes — even though a beam plan has no footings in the first place

**Cause:** picture **a vertical beam running through a column box** — it forms the shape of "a vertical rectangle
with something in the middle", which **looks a lot like F2**. The computer only sees shapes, so it can't tell them apart

**The fix I first had in mind (not good):** make the threshold stricter
→ but that would also make the real F2s on the foundation plan drop out = moving the problem, not fixing it

**The fix actually used — bring in knowledge of construction drawings to help:**

> **On a real foundation plan, there are no beams to detect at all** (because the two are plans of different levels)
> So: **if a spot we think is a footing turns out to sit inside a detected beam strip → drop it**

```python
# drop footings whose center point falls inside a beam strip
out["footing"] = [f for f in out["footing"]
                  if not any(in_beam_strip(f, strip) for strip in beams)]
```

**Why this rule is 100% safe:** because on a real foundation plan, the beams the system detects = 0 strips
so this rule has no way of ever dropping a real footing (there's no strip for it to fall into)

**Result after the fix: the beam plan gets 0 footings** ✅ and **the foundation plan still gets 12/12, same as before** ✅

> **Lesson:** sometimes the best fix isn't tuning numbers but **putting knowledge of the real work**
> in as a rule — the knowledge that "a foundation plan has no beams" is an engineer's knowledge, not a programmer's

### 7.1 A lesson in how to think: there are 2 kinds of "bad numbers", and you have to tell them apart

### 7.2 Going to look at how "0%" is actually counted

The evaluation code uses this line:

```python
hit = len(set(gt_ids) & set(pred_ids))    # exact string match
```

Then I went and opened up what the `element_id` values in the section ground truth really look like:

```
gate_front · door_lock_detail · SP_at_bathroom · purlin_rafter_connection
FCO_detail · SP_unsupported_beam_edge · ห้องนอน · ระดับพื้นอาคาร
```

**These names aren't printed on the drawings** — they're names that **the annotator made up** to tell sub-details apart
There's no way the AI (or a person) could guess `SP_at_edge_beam` from looking at the image, because not a single letter of that text
appears anywhere on the paper

> **Analogy:** it's like showing a kid a picture of a dog and asking "what's this dog's name?" — the answer is "Bobby",
> which the owner made up. No matter how good the kid's eyesight is, they can't answer — and that's not the kid's fault

### 7.3 Putting a number on it — the "ceiling" of each task

I wrote a tool, `measure_id_ceiling.py`, that separates the 2 kinds of names and counts them:

| Task | Total names | Actually readable from the drawings | **Max ceiling** | t03 achieved | Meaning |
|---|---|---|---|---|---|
| plan_beam | 2,484 | 2,175 | **88%** | 0% | 🔴 **the model is genuinely broken** |
| plan_slab | 283 | 261 | 92% | 20% | 🔴 the model is genuinely broken |
| plan_footing | 462 | 345 | 75% | 33% | 🟡 some room to improve |
| schedule | 662 | 403 | 61% | 22% | 🟡 some room to improve |
| **section** | 2,436 | 902 | **37%** | 0% | 🟠 **the metric is half broken** |
| notes | 272 | 5 | 2% | – | 🟠 the metric is almost completely broken |

**And for house 08 alone — the house actually used for evaluation — the section ceiling = 1 out of 23 = 4%**
because house 08 is a single-storey house whose section pages are almost all **fence/door/water-pipe** details,
not beam-column cross-sections → **even a perfect AI couldn't get more than 4%**

### 7.4 Conclusion — these two 0%s are two different diseases

| | plan_beam 0% | section 0% |
|---|---|---|
| Ceiling | 88% | **4%** (the house we measure on) |
| Meaning | The model genuinely can't read it | The metric is measuring something impossible |
| Can pattern recognition help? | **✅ Yes, this is the right target** | ❌ No, there's nothing on the paper to detect |

**If you lump these two together and conclude "the model is bad at reading" = wrong conclusion**
plan_beam has to be fixed in the model, while section needs its metric fixed first — otherwise next round we'll have no way of knowing
whether what we did actually worked

### 7.5 Actually tried before concluding — recorded so nobody else repeats it

I didn't just conclude out of thin air — I tried 3 methods first:

| Method | House 17 | House 12 | House 01 |
|---|---|---|---|
| Find the circles enclosing the names (B1)(B2) with HoughCircles | **5/5 ✅ not a single false hit** | 3/20 ❌ | 0/18 ❌ |

Worked beautifully on house 17 but **failed completely on the other 2 houses**, because **each design office's section pages
are drawn differently** — house 17 circles the names, house 01 prints "B1 1:20" underlined with no circle at all
Unlike the structural plans (column/beam/footing), whose symbols are much more consistent — and that's why
today's tool works on structural plans but not on section

### 7.6 Proposed fixes (not done yet, because touching the ground truth = need permission first)

1. **Split the metric's columns** — report the score for names printed on the drawing separately from names people made up themselves
   *(only changes the scoring script, doesn't touch the ground truth = safest, can be done right away if ordered)*
2. **Strip spaces / normalize upper-lower case before comparing** — so `"B1 "` no longer fails to match `"B1"`
3. Change the naming convention for section `element_id` (touches the ground truth = a big job, needs permission)

## 9. Today's vocabulary

| Term | Plain meaning |
|---|---|
| **template** | Master pattern — the small image we lay over the big image to search with |
| **template matching** | Sliding the template over the whole big image and scoring how similar each spot is |
| **threshold** | Cutoff — the minimum score that counts as "found" |
| **NMS** | Removing overlapping points so only 1 representative point is left per object |
| **multi-scale** | Searching at several sizes — shrink/enlarge the template and search at every size |
| **false positive** | A bogus hit — says it found something when nothing is actually there |
| **recall** | What % of the things it should find it actually finds |
| **CPU / GPU** | CPU = an ordinary computer's brain (this job only needs this) / GPU = graphics card (has to be rented, expensive) |
| **B (in a model's name)** | Billion parameters = the size of the AI's brain |
| **max_frames** | Maximum number of frames of a **video** (we don't use it) |
| **MAX_LENGTH** | Total length the AI can take in per call (this one we really use) |

## 12. Appendix — trying to find an AI model other than Qwen

That same night, Makham ordered a search for 100-200B vision models that are **not from the Qwen family**
(neither by brand name nor by the "brain" inside) to compare against — 8 models checked

### 12.1 The one that's good but can't be used — Pixtral-Large

- **Size ~124B** (Mistral AI) — good at **reading documents/tables/charts** and supports very long text
- **Has a pixel-counting system** like the Qwen we're using — it doesn't force images to be shrunk into a fixed square
  but cuts them into patches according to the image's real size (different sizes/aspect ratios use different numbers of patches)
- **But it can't be used at all** — the license is the **Mistral Research License**, which bans commercial use
  unless you buy a separate license from Mistral. **No matter how good it is, it's eliminated on this one point alone**

### 12.2 Why the others were eliminated too

| Model | Eliminated because |
|---|---|
| InternVL3-78B / InternVL3.5-241B | A different brand, but inside it uses Qwen2.5/Qwen3 as its brain — still counts as Qwen |
| GLM-4.6V | License is OK, but it has a bug that makes LoRA training impossible (nobody has fixed it yet) |
| Molmo-72B, NVLM-D-72B | No training tool has confirmed yet that they actually work |

**Only 2 survived:** GLM-4.6V (stuck on the bug) and **Llama-4-Scout** (Meta, free to use if <700 million users/month,
actually trainable) — but for both, **nobody has tested yet how well they read Thai**

### 12.3 Update — re-checking the 2 models still left pending

- **NVLM-D-72B (NVIDIA)** — truly ruled out: the license is **CC-BY-NC-4.0, flatly no commercial use**
  so it was off-limits for STECON from the start, no need to even talk about the framework — and vLLM itself can't run it yet either
  (NVIDIA admitted this themselves in an HF thread)
- **ERNIE-4.5-VL-28B-A3B (Baidu)** — correcting earlier info: it actually **has an Unsloth notebook that works right away**
  (previously misunderstood as needing ERNIEKit only) but this one is only **28B**, smaller than the requested 122B±50 criterion
- **Also found:** OmniDocBench (a real-results leaderboard that is still maintained) has **InternVL3-78B scoring 83.76
  points**, the only one of all 10 models checked that actually appears on the leaderboard — this adds a little credibility
  to InternVL3-78B (although it would still need a framework switch from Unsloth to LLaMA-Factory
  and it still counts as a Qwen backbone anyway)

### 12.4 Continuing the hunt for an NVLM-D-72B substitute — no exact replacement found yet

Makham liked NVLM-D-72B (even though it was eliminated), so asked me to keep looking for anything similar — found 3 new ones
but **none of them can replace it to spec yet** (72B + commercial + easy to train):

| Model | Size | License | Summary |
|---|---|---|---|
| **Nemotron 3 Nano Omni** (NVIDIA, Apr 2026) | 30B (active 3B) | **actually usable commercially** ✅ | NVLM's spiritual successor, but **much smaller than requested**; the cleanest license of everything checked so far |
| GLM-5V-Turbo (Z.ai, Apr 2026) | Not disclosed | Closed — API only | **Can't be downloaded to train ourselves at all**, eliminated immediately |

**Overall summary of section 12:** the field right now is split into 2 camps — **the truly open camp** (Qwen/DeepSeek/Gemma)
which has almost no mid-size vision models at all, and **the camp that's good at vision** (Mistral/MiniMax/NVIDIA)
but almost every one of them ties its license to hidden conditions. Haven't found one that has all 3 yet (size + clean license + actually trainable)
