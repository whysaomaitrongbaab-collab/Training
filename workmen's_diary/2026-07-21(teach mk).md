## 2. Why "rent" a computer (GPU) instead of using your own

A **GPU** (graphics card) is a computer component that can calculate huge amounts of numbers simultaneously, very fast — normally used for gaming/video editing, but AI needs the same kind of calculation too (because AI is essentially multiplying-and-adding numbers millions of times over, repeatedly).

The AI model we're using (Qwen3.6) is very large — it has **35 billion "parameters"** (numbers the model uses to make decisions). A graphics card in an ordinary computer (e.g. the RTX 5060 you have, with 8GB of VRAM) can't hold a model this size at all — it needs a card with **at least 74GB of VRAM (the graphics card's own memory)**. A card at this level costs hundreds of thousands of baht to buy outright, so instead we chose to **"rent" it by the hour** (like renting a car instead of buying one) through the Vast.ai website — paying only for actual usage time ($1.056/hr for the card rented today).

## 3. What is SSH, and why not use the web (Jupyter)

**SSH** is a method of "connecting a cable in to control another computer remotely" via a terminal (a black screen where you type commands) — like being able to sit at home and type commands to control a computer in another country entirely.

Initially tried connecting via **Jupyter** (a web page that lets you type code), but ran into "won't open" errors repeatedly, several times. Upon looking into it, found that people who train AI seriously worldwide mainly use SSH, since it's more stable, faster, and comes with **`tmux`** built in (a program that lets you close the window while the job keeps running on the rented machine, so you don't have to sit and watch the screen the whole time).

**The SSH key:** instead of typing a password every time, we create 2 "digital keys" — one (private) is kept on your own computer, the other (public) is deposited with Vast.ai. When connecting to the rented machine, the two keys check each other to see if they match — safer than a password, and done once, usable forever afterward.

## 4. What is Unsloth — why don't you need to "log into" it like a website

This is a great question, since it's a common misunderstanding: **Unsloth is not a website or an app you need to log into**.

Unsloth is a **"library"** — think of it as **a recipe book sitting on a shelf**. When we're about to cook (write a program), we just "pick up the book and open it" (type the command `import unsloth` in Python code), then use the recipes inside directly — no signing up, no logging in, not even connecting to the internet to reach the Unsloth company at all (only the very first installation needs to download the files to store on the machine, like buying the book once to put on the shelf — after that, you just pick it up and use it whenever you like).

**What Unsloth does:** it makes teaching an AI model (fine-tuning) **use less VRAM and go faster**, using specialized techniques (like managing memory more cleverly), compared to writing model-teaching code entirely from scratch with no helper tool at all — like having a kitchen assistant who knows shortcuts that make things finish faster and use fewer ingredients.

**The thing that does need a "real website/service" is HuggingFace** (where the Qwen3.6 model itself is stored for download) — this genuinely requires an internet connection the first time to actually download the model file (~70GB), but after that it's already stored on the rented machine, no need to download it again.

## 5. What is fine-tuning ("การทูน")

The downloaded AI model (Qwen3.6) has already been taught from millions of pages of general data on the internet — it's skilled at general things, but **has never seen our Thai construction drawings at all**, and doesn't know what format we want the answer in (what kind of JSON, what fields it should have).

**Fine-tuning (การทูน)** takes this already-skilled model and **"teaches it further, specialized"**, using our examples (226 pairs of drawing image+correct answer), so it becomes familiar with this specific task — like a doctor who's already studied general medicine, then goes on to study a specialty like orthopedics — no need to study medicine all over again from the beginning.

---

## 6. What is LoRA

The model has 35 billion parameters. If we tried to "teach it more" by editing every single number, it would **use enormous VRAM and risk breaking the model's existing knowledge** (like rewriting an entire book from scratch).

**LoRA** (short for Low-Rank Adaptation) is a technique that **doesn't edit a single original parameter at all**, but instead creates a small "supplementary adjustment" attached alongside — like not rewriting the original book, but sticking **small post-it notes** onto the front of each page you want to change. When the model is about to answer something, it looks at both the original content + the post-its stuck onto it together.

**LORA_R** is "the size of the post-it note" — the higher the number (e.g. 64), the bigger the post-it, letting more detail be written on it, but also consuming more VRAM. Today it was initially set to 64, then a memory-full problem was hit (see item 8), so it was reduced to 32 — a slightly smaller post-it, but still enough to write what's necessary, and research says that if the training data is small (226 examples is considered small), a smaller post-it is actually even more appropriate (otherwise risking "learning it wrong" and damaging the model's existing knowledge).

**Another advantage:** once training finishes, we get a "post-it" file (the LoRA adapter) that's **very small** (a few hundred MB), instead of having to store the entire 35-billion-parameter model all over again (which would weigh dozens of GB).

## 7. What is MoE (Mixture of Experts) — why it relates to today's problem

The Qwen3.6 model being used isn't "one single brain" like a normal model, but is a **MoE (has several sub-experts)** — inside this model there are **256 "sub-experts" (experts)** hidden inside. Every time it's about to answer a word, the model **chooses only a few experts** to help answer (not using all 256 at once every time) — meaning that even though the model is very large in total (35 billion parameters), the actual computation only uses ~3,000 million (3 billion) at a time (faster than if it had to use all of it).

**Why this relates to today's memory-full problem:** when sticking the "LoRA post-it" (item 6) onto the experts — because there are as many as 256 experts, the post-it has to be stuck on repeatedly, 256 times (one per expert), consuming far more memory than an ordinary non-MoE model. This is the real cause of today's memory-full problem.

---

## 8. What is "out of memory" (CUDA Out of Memory / OOM)

A graphics card has its own memory (VRAM), separate from a computer's ordinary RAM — today's rented card has 95GB of VRAM.

While teaching the model (training), several things must be stored in VRAM at the same time:
1. The model itself (~70GB for 35 billion parameters).
2. The "LoRA post-it" (items 6-7).
3. **Intermediate calculation values** (activation memory) — the longer the text/image fed in, the more intermediate values need to be stored.

Today, the 95GB of VRAM was **almost exactly full** (94.87GB used, only ~100MB left), and then when the model needed just a little more space (100MB), it couldn't find it anywhere → the error "**CUDA out of memory**" (literally: the graphics card [using a technology called CUDA] has run out of memory).

Like a backpack packed so tightly that only a tiny gap of space is left — when one more item needs to go in (even a very small one), it just won't fit anymore.

**The fixes tried today (in the order they were tried):**
1. Adjusted memory management to be smarter (reducing space "reserved just in case" but never actually used) — **tried, but not enough**.
2. Reduced the size of the "LoRA post-it" (item 6, from 64 down to 32) — **this genuinely worked**, since MoE has 256 experts (item 7), reducing the post-it's size saves memory multiplied by 256 times.

## 10. How to read the results during training/evaluation — what these numbers mean

**During training, you'll see numbers like this:**
```
{'train_loss': '1.811', 'epoch': '0.177'}
```
- **loss** = "the error value" — the lower the number, the better (the model's guessed answer is closer to the real one). It starts high, then gradually decreases as training goes on.
- **epoch** = "a round" — teaching through every example in the train set once = epoch 1 (today's plan was to teach 3 rounds = `epoch=3`). The number 0.177 means training got through 17.7% of 1 round (since this was just a short 5-step test, not a full round).
- **step** = "a step" — 1 step = adjusting the model's weights once (teaching it a batch of examples, then adjusting).

**When evaluating against the test set (`eval_fields.py`), you'll see this:**
```
JSON valid           : 0/20  (0.0%)
element found        : 0/170  (0.0%)
```
- **JSON valid** = out of the answers the model gave, what % were correctly formatted JSON (parseable) — before teaching (baseline), this was 0%, since the model had never seen this format before at all.
- **Element found** = out of all the rebar/beam/column items that should be found (170 items across the 20 test examples), how many did the model answer matching correctly.
- **Field exact-match** = among the items that were found, what % of each data field (e.g. beam length, rebar size) was answered exactly right.

**Principle for reading this:** before teaching (baseline), these numbers should be very bad (close to 0%) — this is normal, not something broken, since the model has never seen this task before. **The goal is that after teaching finishes, these numbers must improve clearly.** If, after teaching, the measurement is still just as bad, it means the teaching didn't work, and it's back to the drawing board.

## 12. The confusing incident of "why doesn't the log file I ordered exist" — a lesson about terminal command queuing

After the 5-step test passed (items 8-9), an order was given to start **the real full 3-epoch training**, by typing a new command straight into the same existing terminal window immediately — but upon checking afterward, it turned out **the full-training log file (`full_train.log`) didn't actually exist at all**, even though the command had been seen "typed" onto the screen.

### Why this confusion could happen — a simple comparison

A terminal (the black window where you type commands) works as **"a single queue, one thing at a time"**, like a counter clerk who can only take one order at a time — if the first customer (the 5-step test command) hasn't finished paying yet (hasn't finished running), then even if the second customer (the full-training command) walks in and says their order, the clerk still won't start on it — they just "remember what was said" and wait for the current queue to genuinely finish before starting the new order.

What actually happened: even though the 5-step test command had "finished training" and "finished saving the file", the script itself (`train_qwen36.py`) still had **a final step** that wasn't done yet — having the model try answering 3 real sample questions (to show the results immediately, not just look at the loss number alone). This step takes a long time (the model has to genuinely "think of an answer" character by character), so **the original program genuinely wasn't finished yet**, even though it looked like it had already finished.

### How it was investigated (detective-style)

Used a command to check **"processes"** (programs currently running on the machine) and found the same original program was still running (it had been running for 885 seconds = almost 15 minutes, which is longer than the 5-step test should have taken), then checked which file it was writing its log to, and found it was still writing to the original file (`test_run.log`), not the new file (`full_train.log`) — clearly confirming that the new command typed in **hadn't actually started running**, it had just been "remembered, waiting in the queue".

### Lesson

When working through a terminal like this, **you must wait until you actually see the prompt (the sign that it's ready for a new command) come back**, before typing the next command. If you type ahead of the queue, the command doesn't disappear anywhere (no need to retype it) — you just have to wait for the current queue to clear before it automatically starts on its own. A more reliable way to check than just looking at the screen is to check "processes" to see whether the previous job is genuinely still running — the same way it was done in this incident.

## 13. The incident "training finished, then it broke anyway" — a lesson about a "shared environment"

The full 3-epoch training finished successfully (loss dropped from 2.0 down to 0.14 — very good), **the result file (the LoRA adapter) was also saved successfully** — but immediately after that, the bonus step at the end of the script (having the model try answering 3 sample questions to show the result) **broke with a file-not-found error**.

### The cause — Claude's own mistake

While waiting for the training, Claude opened a separate terminal window to prepare the `llama.cpp` program in advance (for the GGUF conversion step discussed earlier), and ran `pip install` (Python's software installer) in that window.

**The problem was:** both windows (training the model + preparing llama.cpp) **used the same "storage room"** (the same Python environment across the whole machine) — when llama.cpp's `pip install` installed/updated a library called `transformers` (the main library used to run the AI model), it overwrote the existing version that Unsloth had specifically prepared for this model (which had the file supporting Qwen3.5 MoE) with an ordinary standard version that **didn't have that file**. When the training script (still running, not finished yet) needed to go back and use that file again after saving (while trying to show the 3 sample answers), it couldn't find it anymore, and broke.

### A simple comparison

Like 2 people sharing the same "toolbox" at the same time — one person (the training job) is currently using a certain screwdriver, and the other (the llama.cpp prep job) goes and swaps that exact same screwdriver for a different model while the first person is still using it. When the first person goes to reach for the screwdriver again (the same familiar one), it's become a completely different tool.

### Key lesson

**Never install/modify shared software (pip install) while another important job is running on the same machine.** If you want to do supplementary work while waiting, you must clearly separate the "storage room" (a technique called a **virtual environment**), not share the same room as the main job currently running. Luckily this time, the important result file (the LoRA adapter) had already finished saving right before it broke, otherwise the whole thing might have had to be trained again from scratch (wasting time+money for nothing).

**Impact:** now the environment has to be repaired back to correct first, before the model's quality can be measured (`eval_fields.py --adapter`) as planned.
