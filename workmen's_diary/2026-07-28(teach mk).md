## 2. A new bug never seen in the t01 round — because "the library version drifted"

### The problem
As soon as the real run began (Phase 4) the program errored immediately:
```
AttributeError: property of 'Qwen2VLImageProcessor' object has no setter
```

### Explaining simply what happened
The code as written sets "image resolution" by overwriting `ip.max_pixels = ...` directly — back
when the code was written, that worked. But when we rented a new machine today, the `transformers`
library that pip installed turned out to be a newer version than what had ever been tested (5.5.0),
and **the library's developers had changed how you set that value**, so the old way no longer works.

**Analogy:** like a phone app that updates itself automatically, and one day a button you used to
press is gone because the company redesigned the app — our code hit the same thing, just with a
library instead of an app.

### Why nobody knew in advance
This code (`train_qwen3vl.py`) was written before the dataset grew, and **had never actually been
run** until today — the library kept moving through versions while the code just sat there.
Lesson: **code written long ago and never run is riskier than you'd think**, because the world
around it keeps changing (libraries update) even though the code itself wasn't wrong when written.

### The real fix
Opened the library's actual source code (rather than guessing) and found the way that still works is
`ip.size["longest_edge"] = ...` — changed it to use only that path, deleted the old one, retested, passed.

## 3. Reading the loss curve during training — what is loss, what does it tell us

**loss** is a number telling you "how wrong the model's guesses are" in each round — **the lower the
better** (0 = guessed exactly right, a high number = guessing wildly). Today we saw the real values
throughout training:

```
start: 1.795 → falling steadily → ending around 0.18-0.21
```

A downward path like this is a good sign — it means the model **is genuinely learning**, not sitting
still or getting worse. (If loss doesn't fall at all, or bounces up and down with no direction, that's
a sign something is wrong, e.g. the learning rate being too high.)

**But low loss ≠ genuinely usable** — this is the key point the whole `rule_of_tune.md` file warns
about (lesson 4 of the old CLAUDE.md file). Loss only measures "how close the guess is to the answer
mathematically"; it does not measure **whether the rebar numbers were read correctly, or the part
names read correctly** — you need a Phase 7-style measurement (counting matching fields one by one)
to know the real answer.

## 4. VRAM going up and down during training — why

During training you can see VRAM isn't steady all the way through (sometimes 81GB, sometimes spiking
to 94GB out of 95GB total — nearly the whole card). The reason: **the training examples aren't all
the same size** — this dataset has 5 special examples called "gridmaster" that use 2-4 images at once
(remember from the 07-24 file, the MAX_LENGTH story). When training reaches those examples it needs
more memory temporarily, and once past them it drops back to normal.

It's like driving — flat road uses little fuel, going uphill temporarily uses more; it doesn't mean
the car is broken.

## 5. Why Qwen3-VL is 2.9x slower than Qwen3.6, with all settings identical

t01 finished training in 29:23, while t02 took 84:53 — **every hyperparameter is set exactly the same**
(carefully verified in the document, this isn't a mistake). The difference comes from **the model's own
internal architecture** — Qwen3-VL and Qwen3.6 are both MoE (Mixture of Experts), but their internal
designs (number of layers, how images are handled, etc.) differ, which can make the speed per step
differ a great deal even when the "total size" is similar.

**Lesson:** model size (30B vs 35B) doesn't settle the speed question. The internal design matters
more than the bare size number.

## 7. Why Phase 7.5 has to load the whole model again — what a LoRA adapter really is

The question Makham asked today: "why does it take so long to load" — the answer connects to
understanding **LoRA** a bit more deeply.

Remember from earlier files that LoRA is like a **"post-it note stuck on top"** — here's the real
reason why: LoRA **doesn't store a whole new model**, it only stores a small **"difference"** saying
"when you meet a situation like this, nudge the answer slightly this way" — t01's adapter file is only
~7.5GB, whereas the full model (Qwen3.6-35B-A3B) weighs in at ~70GB.

**The consequence:** the adapter alone **is completely unusable** — you always need the full base model
underneath it, just as a post-it stuck on a blank sheet of paper means nothing; you need the whole
notebook to stick it onto first.

Today, throughout Phase 4-7, the rented machine only loaded **Qwen3-VL-30B-A3B** (t02's model) and never
touched **Qwen3.6-35B-A3B** (t01's model) at all. So to measure t01 again (Phase 7.5) it had to download
t01's full base model all over again first, before the adapter (already downloaded) could be stuck on top.

## 8. New vocabulary today (continuing from the glossary at the end of the 07-24 file)

| Term | Short meaning |
|---|---|
| Controlled experiment | Change only one variable at a time, holding everything else identical, so you know exactly what the difference came from |
| Loss | A number saying how wrong the model's guesses are; lower is better, but it only says "mathematically close to the answer", not "actually correct" |
| A/B test | Comparing two options with variables controlled (the name comes from comparing plan A with plan B) |
| Property (of a class in a program) | A value that can be read/written through an attribute name, though some are locked "read-only" and can't be overwritten |
| Library version drift | The libraries you use keep changing versions over time, so old code that used to work may stop working |

## 9. The biggest thing of the day — the whole day's results flipped because of "a value never set", not "a value set wrong"

### What was discovered

After Phase 7.5 finished, I ordered another extremely detailed check (43 agents hunting for holes together) — and found something big:
**t01 (Qwen3.6) was trained on images ~14x blurrier than t02 (Qwen3-VL)**, with nobody intending it

### How this could happen despite checking so carefully

Remember **"bug 2"** found during Phase 0.4 (while reading the scripts before renting the machine)? Back
then we found that without explicitly setting `resize="max"`, the program silently shrinks images to 512px.
**That problem was fixed — but fixed only on t02's script side.** Nobody thought to go back and check
whether t01's script (written a month earlier) had the same problem.

**Why the parity table, made so carefully, didn't catch it:** because that table only compared
**"values deliberately set"** (e.g. learning rate, batch size, number of epochs) — it didn't compare
**"values left at their default with nothing typed at all"**, and `resize="max"` is the latter kind — on
t02's side it's typed explicitly, on t01's side nothing is typed at all (because it was written before
this problem was known). With no line to compare, nobody noticed they differed.

**Analogy:** like checking two recipes to see whether they use the same salt/sugar/chilli (the things
written in the recipe) but forgetting to check "how high is the heat", when neither recipe writes the heat
level down (each using their own stove's default) — then when the two dishes taste different, you assume
it's because of different ingredients, when in fact the heat was different from the start.

### Confirmed by real measurement, not by reading the code and guessing

Loaded the Qwen3.6 model for real, built an "image shrinker" (collator) exactly as `train_qwen36.py` uses
it (with no resize= passed), then fed in 1 real image — and the program printed out by itself:

```
Unsloth: Model does not have a default image size - using 512
```

and the count came out to only **~266 visual tokens**, compared with the **~3,796-5,100 tokens** t02 trained
with (a ~14x difference) — this is **proof**, not speculation.

### Why this flips everything concluded earlier

All day the conclusion had been "Qwen3.6 reads Thai construction drawings better than Qwen3-VL" — that now
has to become **"Qwen3.6, seeing far blurrier images, still does better than Qwen3-VL seeing sharp images"**,
which is a different conclusion — the first answers the question set from the start (which family is better),
the second can't, because the experiment was unfair from the beginning (like making one runner race with
weights strapped to their legs: if the weighted runner still wins, that proves they're genuinely good, but it
can't tell you "by how much faster they'd be without the weights").

### The options offered + what Makham chose

Two options were offered: **(A)** stop here and accept the results with a clear warning attached, or **(B)**
retrain t01 with `resize="max"` so it sees images as sharp as t02's and measure again genuinely fairly
(costing extra time+money). **Makham chose (A)** — accept the results as they are with warnings attached
everywhere in the documents, no retraining.

### The lesson recorded permanently

Added as **Lesson 12** in `rule_of_tune.md`: **a variable-comparison table for an A/B experiment must list
every argument passed into a shared function/class, not just the values you deliberately chose** — a value
left at its default is a variable too, and precisely because there is no line to compare it against, it is
the easiest thing of all to miss. Next round, every argument must be compared from the real source code,
not just from the list of things you remember changing.
