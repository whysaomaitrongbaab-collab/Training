## 4. 0.3 — a "dress rehearsal" on your own computer first (local dry run)

This is the step that prevents the 21st's problem most directly. Explaining each term afresh:

### What is GGUF
An AI model in its normal form (during training) is stored in a format that takes up a lot of space and only runs on powerful graphics cards. **GGUF** is a "file format" that compresses a model to be smaller and runnable on an ordinary computer (even without a very powerful graphics card) — the final goal of this whole project is to get a GGUF file for use on Makham's own computer

### What is Quantization (compression)
A model stores numbers at very fine precision (e.g. bf16 = 16-bit numbers). **Quantization** is rounding those numbers to be coarser (e.g. 4-bit) so the file becomes far smaller, in exchange for a small loss of accuracy — like compressing a high-quality JPEG photo into a low-quality JPEG: much smaller file, the picture is still recognizable but a bit of detail is gone

### What is mmproj — and why it was the big problem on the 21st
The model we're using must **"be able to read images"**, not just read text — the part that "translates images into numbers the model can understand" is a separate file called **mmproj**. On the 21st this file failed to be extracted (the model was too new, the tooling didn't support it), leaving us with a GGUF that could only read text and couldn't read construction drawings at all — **even though that is this project's entire job**

**The good news discovered afterwards:** because the training script (`train_qwen36.py`) is configured to **"never touch the image-reading part"** (`finetune_vision_layers=False` — it teaches language only, never touching the image-reading part), the image-reading part of the tuned model is **100% identical to the original model** — so there's no need to try "extracting a new file" any more, just download the mmproj file the company that owns the model already made (899MB) and use it alongside our own tuned GGUF — the problem that had been stuck since the 21st is solved without depending on tooling that doesn't support it any more

### What is llama.cpp
**llama.cpp** is the program that "runs" a GGUF file on an ordinary computer — you have to feed it both the model file (GGUF) and the mmproj file together if you want it to be able to read images

### What was actually done today (rehearsing the whole process before spending money)
1. Downloaded the real mmproj file (899MB) — the real one that will be used once tuning is done
2. Downloaded a small sample model (not tuned, maximally compressed, ~10.8GB) purely to "test that the system runs", not caring how well it answers
3. Downloaded and installed the llama.cpp program
4. Fed in a real construction drawing (house01 page19) and asked "describe this image"
5. **Result: passed** — the model read the Thai text in the image correctly ("แผนลุนฐานรากแผ่ และฐานรากเสาเข็ม"), picked up the grid correctly (1/2/3 x A/B/C/D), read the footing labels correctly (F1, C1, etc.)

**What this proves:** Makham's own computer (RTX 5060, only 8GB of VRAM) **can genuinely run a model like this** (even though the VRAM isn't enough, part of the work is offloaded to ordinary RAM), and the mmproj genuinely works — so once tuning is really finished, it's just "swapping one model file", with nothing else surprising left. Unlike the 21st, when we only discovered mmproj had a problem with the job nearly done

After testing, the test model file (10GB) was deleted, keeping only the mmproj for later use

## 5. 0.4 — re-reading the scripts seriously, and finding a bug nobody knew about

### What is a Token (new term today)
An AI model doesn't read letter by letter or word by word the way a person does — it chops text (and images) into small pieces called **tokens** and processes them one piece at a time. The longer/more detailed the text or image, the more tokens there are.

**A single image also counts as tokens** — a more detailed image gets chopped into more tokens (this model's formula: the largest image size configured = about 5,120 tokens/image)

### What is MAX_LENGTH — and why it was a bug
A training script has to set in advance the "maximum acceptable length per example" (`MAX_LENGTH`) — if any example is longer than that, the program will **"cut off the tail"** of the excess

The problem found today: the value originally set (9,216 tokens) **was calculated from an example with only 1 image** — but in the real dataset there are 5 special examples (called "grid master" — 1 per house, teaching the grid lines of the whole building) that use **2-4 images at once**. Counting them properly, those examples need up to ~22,000 tokens (2.4 times more than what was set)

**What that means:** if unfixed, during real training the program would cut off the tail of these examples — and the tail of an example is **the correct answer we're trying to teach the model** (not just some unnecessary part). That amounts to teaching the model with incomplete answers. And these examples happen to be the only ones that teach "the grid lines of the whole building" (the point the script itself flags as the most frequently missed) — leaving it alone would mean this round of tuning teaches that topic wrong from the start

### The options available + what Makham chose
There were 4 ways to fix it (raise the acceptable size / lower image resolution for just this group / leave it alone / drop this group of examples entirely) — **Makham chose to raise the acceptable size** (from 9,216 to 24,576) so that no image detail is lost at all

**The trade-off you need to know:** this higher value makes it **more likely that memory runs out (OOM, see item 8 in the 07-21 file)** during training on these 5 examples specifically, because in the previous round only ~100MB out of 95GB of memory was left with the value at 9,216 — if OOM does hit at this point, the fix is to shrink the "LoRA post-it note" further, or lower image resolution for just those 5 examples, not to lower this value back to what it was (because that goes back to cutting the answers off again)

**Key point:** this bug **existed even before house 05 was added** — nobody ever caught it because nobody had ever read the script against the real numbers in the dataset this carefully before. This is exactly why Rule 4 (item 1) says you must **"actually do and actually check, not just skim"**

## 6.5. What exactly is llama.cpp — and why not use Unsloth to run it in real use

Item 4 mentioned llama.cpp briefly (the program that runs GGUF), but a good question came up later as Phase 10 approached (testing a real run on Makham's own computer): **"can I use Unsloth instead when running it?"** — the answer is no, it isn't suitable, and the reason helps clarify the whole picture

**Unsloth and llama.cpp do different jobs, at different times:**

| | Unsloth | llama.cpp |
|---|---|---|
| Used when | During **training** (on a rented powerful GPU machine) | During **real use** (on Makham's own computer) |
| Needs what | The full bf16 model (~70GB) + a graphics card with 74GB+ VRAM | A compressed GGUF file (~21GB), runs even with only 8GB VRAM |
| Analogy | Like a "factory" that needs big machinery | Like a "player" anyone can open to view the finished product |

If you tried running Unsloth on Makham's computer (8GB VRAM) it couldn't cope at all, because Unsloth still expects the full-size model just like during training — **this is the entire reason we spend time making a GGUF + quantizing it (item 4 above)**: compressing the model small enough for llama.cpp to run it on a small machine. Skip this step and there is no way to genuinely "run it on your own computer" as originally intended (see the goal in item 1 of the 07-21 file)

Put simply: **Unsloth = the craftsman's tool used while building, llama.cpp = the remote control used while watching**. The two aren't interchangeable, because they're designed for different jobs

## 8. New vocabulary today (continuing from the glossary at the end of the 07-21 file)

| Term | Short meaning |
|---|---|
| GGUF | A model file format compressed to be smaller and runnable on an ordinary computer |
| Quantization | Rounding the numbers in a model to be coarser, making the file smaller in exchange for a little accuracy |
| mmproj | The "translate image into numbers" part of the model, kept in a separate file from the main model |
| llama.cpp | The program used to run GGUF files on an ordinary computer (a different thing from Unsloth, used during training — see item 6.5) |
| Token | The small unit a model chops text/images into and processes one piece at a time |
| MAX_LENGTH / sequence length | The maximum length (counted in tokens) one training example may use; anything longer gets cut off |
| Truncation (cutting off) | When an example is longer than MAX_LENGTH, the excess really is cut away, not merely warned about |
| Reliability (%) | The trustworthiness of a rental machine, measured from its history of crashes/dropouts |
| Dry run (dress rehearsal) | Testing the whole process with mock/small versions before using the real thing / spending real money |
