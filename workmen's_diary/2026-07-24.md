## Claude — ต่อจาก entry บน: เช่า GPU จริง + เทรนเต็ม + export ครบวงจร จบรอบนี้สำเร็จ (Phase 1-10)

มะขามเช่า GPU เอง (`m:130161` ก่อน แล้วเปลี่ยนเป็น RTX PRO 6000 WS Hong Kong, ~$0.111/hr, disk 300GB ยืนยันถูกต้อง) แล้วให้ Claude ขับเคลื่อนทุก phase ผ่าน SSH โดยตรง (ผิดจากแผนเดิมที่จะให้มะขามทำเองทั้งหมด — ทำตามที่มะขามสั่ง "คุณทำเลย")

### Phase 1-4: เช่า+connect+อัปโหลด+verify — ผ่านหมด ไม่มีปัญหา
SSH ตรง (`ssh -p 30055 root@94.190.219.147`), อัปโหลด dataset (315 train/88 val/398 images ตรงกับที่ build ไว้), `verify_env.py` เขียวหมด, ข้าม Phase 4 baseline ตามคำแนะนำ doc (ประหยัดเวลา)

### Phase 5-6: เทรนเต็ม 3 epoch สำเร็จ — เจอบั๊ก "process ค้างกิน VRAM" ใหม่
- ทดสอบสั้น (`TEST_STEPS=5`) ผ่าน แต่พบว่า process ไม่ยอม exit เองหลังจบ (ค้างกิน VRAM 83GB) ต้อง kill เอง — เป็นสาเหตุที่ Phase 6 รอบแรกพังด้วย OOM-adjacent error (meta tensor) เพราะ VRAM เหลือไม่พอตอนเริ่มใหม่
- เทรนเต็มจริง (315 ตัวอย่าง, 120 step, 3 epoch) ใช้เวลาแค่ **29.4 นาที** (เร็วกว่ารอบก่อนมาก เพราะการ์ดแรงกว่า) loss ลด 1.8→0.08, eval_loss ต่อ epoch 0.2668→0.1983→0.1936 (ดีขึ้นต่อเนื่อง ดีกว่ารอบก่อน) LoRA adapter เซฟสำเร็จ (7.56GB)
- **บั๊กเดิมซ้ำ**: สคริปต์ค้างที่ epilogue (demo generate 3 ตัวอย่าง) หลังเซฟเสร็จ ทุกรอบ — kill ทิ้งได้เลย ไม่กระทบผลเทรน (ดูสาเหตุจริงในหัวข้อ token/thinking ด้านล่าง)

### Phase 7: วัดผลจริง — ดีขึ้นกว่ารอบก่อนมาก (หลังแก้บั๊ก reasoning-mode)
- รอบแรก **JSON valid 0%** (แย่กว่า baseline!) — ตรวจสอบพบว่าโมเดลเขียน "thinking process" ยาวๆ นำหน้าทุกคำตอบ (โมเดล Qwen3.6 มี reasoning mode ในตัว) กิน token จนไม่ถึง JSON จริง
- **สาเหตุแท้จริง**: `apply_chat_template(add_generation_prompt=True)` ไม่ได้ใส่ `enable_thinking=False` — ตอนเทรนไม่มีปัญหา (ใช้ `add_generation_prompt=False` ไม่เคยแทรก `<think>` tag) แต่ตอน inference ค่า default แทรก `<think>\n` เปล่าๆ ทำให้โมเดลเขียน reasoning ยาวต่อ ไม่ใช่บั๊กจากการเทรน แค่ template ตอน inference ไม่ตรงกับตอนเทรน
- แก้ `eval_fields.py`/`train_qwen36.py`/`export_gguf.py` ทั้ง 3 ไฟล์ ใส่ `enable_thinking=False` — รันใหม่ผ่านทันที
- **ผลจริง (`--limit 20`):** JSON valid 90% (เท่าเดิม), view ตรงเป๊ะ 70% (⬆️ จาก 60%), **element หาเจอ 28.2%** (⬆️⬆️⬆️ จาก 9.4% — ดีขึ้น 3 เท่า) element_id/count ตรง 100%, element_type ตรง 87.5% จุดอ่อน: ทายเกิน 78 ตัว (over-prediction)

### Phase 8: export GGUF + อัปโหลด HuggingFace — เจอบั๊กจริง 5 จุดติดกัน แก้ครบทุกจุด
1. sanity check `max_new_tokens=500` เล็กเกิน → เพิ่มเป็น 3000 → ยังพัง (ตัวอย่างทดสอบเป็นหน้าสารบัญยาวเกิน 3000 token จริง) → เพิ่มเป็น 4096 → ยังพัง (โมเดลทายเกินจริง ไม่ใช่ truncation) → **แก้ถูกจุด**: เปลี่ยนวิธีเช็คจาก "parse JSON เต็มสำเร็จไหม" เป็น "ขึ้นต้นด้วย JSON schema จริงไหม" (generate แค่ 1200 token พอ) + เปลี่ยนตัวอย่างทดสอบเป็นหน้าสั้นกว่า
2. Unsloth auto-detect ว่าโมเดลนี้เป็น VLM แล้วพยายามแปลง mmproj ให้เองอัตโนมัติด้วย (ทั้งที่ตั้งใจข้าม) — พังเพราะสถาปัตยกรรมใหม่เกิน ทำให้ export ทั้งก้อนล้มไปด้วย ลองแก้โดยลบ `model.config.vision_config` ชั่วคราว — **กลับไปพังส่วนอื่นแทน** (tensor name ซ้อนกัน 3 ชั้น `language_model.language_model.language_model...`) เพราะไปกระทบวิธีเซฟโมเดลหลักด้วย ไม่ใช่แค่ mmproj — **แก้จริง**: monkey-patch `unsloth.save.convert_to_gguf` ให้ส่ง `supported_vision_archs=set()` (บังคับ ไม่ใช่แค่ set default เพราะ kwarg มีอยู่แล้วเสมอ) กระตุ้น fallback ที่ Unsloth มีอยู่แล้วในตัว (`is_vlm=False` + print "Converting as text-only model") — ไม่กระทบการเซฟโมเดลหลักเลย
3. ดิสก์เต็ม (`No space left on device`) จากรันซ้ำหลายรอบไม่ได้ลบของเก่า — ลบ checkpoint เก่าที่ซ้ำกับ LoRA adapter จริง (33+11GB) + pip cache (3GB) + `outputs_qwen36/gguf/` เก่าที่ค้าง (66GB) กู้พื้นที่คืนมา 147GB
4. สคริปต์หา path ผิด — Unsloth เซฟไฟล์ GGUF จริงไว้ที่ `outputs_qwen36/gguf_gguf/` (มี suffix ซ้ำ) ไม่ใช่ `outputs_qwen36/gguf/` เปล่าๆ ที่สคริปต์เช็ค ทำให้รายงานว่า "หาไฟล์ไม่เจอ" ทั้งที่แปลง+quantize สำเร็จแล้วจริง — แก้ path ไม่ต้องรัน merge/quantize ใหม่ (ประหยัดเวลา) เขียนสคริปต์แยก `resume_upload.py` อัปโหลดต่อจากไฟล์ที่มีอยู่แล้วเลย
5. **สำเร็จ**: `✅ VERIFIED on HuggingFace: https://huggingface.co/Sicilian44/qwen36-thai-rc` — GGUF 21.2GB, mmproj 0.9GB, lora-adapter/ backup — ผ่านการเช็คจริงผ่าน HF API
