### 3. คำถาม: เอา tuned AI ทำ `บ้าน_ใหญ่_1ชั้น_01` ลง raw json ที่ใช้จริง "มันจะทำให้ได้ใช่ไหม"

ตอบตรง (Mark of Shame กฎ 1 — ห้ามพูดว่าพร้อมถ้ายังไม่ถึง):
- **ทางเทคนิค ได้** — รันในเครื่อง พ่น JSON ตาม schema ออกมาได้
- **ความแม่น ยัง** — element recall วัดได้ ~28% (พลาดเกิน 70%) + ทายเกิน; **แล้วบ้านนี้หนักกว่านั้น**: train/val มีแต่ **บ้านเล็ก** (1ชั้น+2ชั้น) แต่ตัวนี้เป็น **บ้านใหญ่** ที่โมเดลไม่เคยเห็นชนิดนี้เลย (out-of-distribution) → คาดว่าแม่นต่ำกว่า 28% อีก
- **Rule 1**: `raw_json_ตัวที่ใช้งานจริง/` เป็น ground truth ที่**เอาไปเทรนเอง** — เอา AI 28% ยังไม่ตรวจไปวาง = poison ตัวเอง → ตกลงว่า output เป็น **draft** ให้คนตรวจต่อ ลง**โฟลเดอร์แยก** ไม่ใช่ raw ที่ใช้จริง

### 5. Design: "แบ่ง 5 call แบบ Constistant แต่เนื้อใน primary_rawjson" — วิเคราะห์ tradeoff

มะขามเสนอ: แทนที่จะ call เดียวสกัดทั้งหน้า ลองแบ่ง multi-pass เหมือน production pipeline **กับดักหลัก:**
- โมเดลนี้ **เทรนมาแบบ call เดียว/หน้า เท่านั้น** — 28% ที่วัดได้ = วัดจาก call เดียว
- แบ่ง sub-call (survey ID / นับ / ฯลฯ) = sub-task ที่**โมเดลไม่เคยเห็นตอนเทรน** → จะทำด้วย base Qwen ไม่ใช่ส่วน fine-tune = **เลิกใช้ข้อได้เปรียบจากการ tune ไปโดยปริยาย** (ซึ่ง pipeline Constistant ที่มีอยู่แล้วก็ทำแบบนั้นอยู่ เรียก cloud เร็วกว่า)
- **เวลาแย่ลง**: ทุก call ต้องประมวลผลภาพใหม่ (~5,120 token ≈ 3 นาที/ครั้งบนเครื่องมะขาม) → 5 call/หน้า = เสียเวลาโหลดภาพ ~15 นาที/หน้า ก่อน gen
- **สรุป**: อยากใช้ tuned จริง → call เดียว/หน้า (แก้ truncation ด้วย ctx พอดี ยอมช้า); อยาก multi-pass จริง → ใช้ Constistant pipeline เดิม (cloud) **หรือ** เทรนรอบใหม่ด้วยข้อมูลจัดรูปแบบ multi-pass ให้ตรงวิธีเรียก (การเทรนต้องแมตช์วิธีใช้งาน)
