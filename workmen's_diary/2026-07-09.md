   Checked `.gitignore` to confirm it hadn't been changed (since the system had already reported "rejected" in step 3) — **and instead found the file content had actually been changed to the new name, despite the system reporting that tool call as rejected** — meaning **the "rejected" message did not match the file's real state on disk** — a mismatch between the harness and what actually happened. ### Lessons / precautions for next time
1. **Before ever renaming/moving a data folder, always grep for hardcoded paths in every code file first**, not just guess from the folder name that it's "old/unused" — a name the user believes is old may not match reality in the code (raw/ looks like a simple name, but is actually the pipeline's main path).
2. **A Windows "Access denied" when renaming/deleting a folder does not mean the files are corrupted** — it's usually caused by another program (File Explorer, a terminal, a background scan) having that folder open as its working directory; try closing the related windows and retry before panicking that data is broken.
3. **A "tool use rejected" message from the harness should not be 100% trusted as proof the file was never actually changed** — always verify the file's real state on disk after encountering a rejection, especially before concluding "nothing was changed". This case almost left `.gitignore` stuck with the wrong name if it hadn't been double-checked at the end.
4. This task ended with a **100% undo back to the original state** — no lasting damage to real data. Recorded here in case anyone later wonders why the git log/diff shows traces of these files being edited back and forth.
