**Task 2 — pass3: measuring real distances from pixels (`server/purson-worker/pass3_measure.py`, new)**
- Makham's brief: take the pass1.5/2.5 results and measure further — find the center point from corner to corner of each element, then measure
  pixels against the grid master ("นับ pixel from grid A-B เทียบ grid master แล้ววัดคานสู่คาน" — "count pixels from grid A-B, compare against the grid master, then measure beam to beam")
- **Chosen approach — no need to detect grid lines in the image at all:** use "anchors" = elements that have both a `grid_ref`
  (which the pass2 model can read) and a `cv_position` (which CV sees) → (pixel, metre) pairs known on both sides →
  least-squares fit of the 2 axes separately, `px = a*m + b` → gives px per metre → invert it to measure anything
  Rejected alternative: Hough detect the grid lines, then match the order of the lines to ids — breaks easily when lines are occluded
  and would need a complete rewrite, whereas the anchor approach uses answers that already exist as its starting point
- **4-layer anti-garbage gate (returns None + a Thai reason, never returns a bogus number):** anchors < 3 (2 can be fit, but
  the residual is always 0, so quality can't be measured at all) · anchors all on a single grid line (no spread along the axis) ·
  residual > 0.5 m (some grid_ref is wrong) · px/m of the two axes differs by > 5% (image stretched/rotated, not orthographic)
- **What comes out:** every element gets `cv_measure.pos_m` (real position in metres) · elements the model
  gave no ref for get `grid_ref_cv` (snap to the nearest grid intersection within 0.5 m; anything farther isn't forced in) ·
  elements the model did give a ref for get `grid_ref_check_m` (how many metres away from that point they actually are = a check that catches
  the model misreading the ref) · points CV sees but the model never mentions at all (including pass2.5's self-harvest)
  are reported along with a computed grid ref — **but they are not added as elements automatically; a person has to decide**
- `parse_grid_ref()` ported verbatim from `raw-extraction-adapter.js` (row = letter → y_lines,
  column = number → x_lines) — both sides must read the same ref with the same meaning
- In-file self-check (`python pass3_measure.py`): a synthetic 50 px/m grid must fit exactly, measuring A1→A2
  must give 4.00 m, snap must hit the right point, and it must **reject** all 3 bad cases (too few anchors/all on one line/skewed)

  flip from "drop" to "keep", while `width_mm`/`span_length_m`/`dia_mm`/`depth_mm` are still dropped as before

- Switched to `updated_at`, which the trigger `purson_jobs_touch_updated_at` (migration lines 40-51)

## Follow-up fix — footing dowel_bar join (claude, per Makham's order "แก้เลย" ("fix it now"))

**Root cause (the real one):** `buildSpecs()` (`raw-extraction-adapter.js`) is already a generic join system
(not tied to element_type — beams/footings all join by element_id the same way); it's just that `SPEC_FIELDS` didn't have
`dowel_bar` — the pile-footing detail pages (S-11/S-12) have an `element_id` that matches the plan page exactly (F4/F6/F3)
with width_mm/height_mm/dowel_bar all present (checked the real files); only the field name doesn't match (`dowel_bar`, not
`main_bar`) because the schema has no official field set for footings (noted in the file's own schema_note)
→ **width_mm/height_mm had been getting through all along (footing concrete/formwork were already correct); only the rebar was missing**

**Fix:** `buildSpecs()` uses `dowel_bar` in place of `main_bar` when there is no `main_bar` (the dowel bars from the pedestal
down into the footing are, in engineering terms, the footing's real main bars, not secondary rebar — a direct substitute, the same shape
that `normalizeMainBar()` already reads). Checked: F4/F6/F3 now get real rebar 39.34/199.33/19.67 kg status=ok
(no longer needs_review) — added 2 tests in `tests/raw-extraction-specs.test.js`
(the fallback is used when there is no main_bar / a real main_bar always wins if both are present) `npm test` 1173/1173

**Not fixed yet (out of scope today):** spread footings (spread footing, the S-09 convention) use `element_id: null`
and are matched by size instead — there truly is no key shared with the plan page at all (the plan page has no width_mm/height_mm to match on either)
It needs a redesign, not just adding a field · plan_slab still has no training examples at all across the whole system (training data needs to be added)
