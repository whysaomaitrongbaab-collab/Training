## [afternoon] Claude — session with Makham

**Work done:**
- Makham asked whether Qwen could be made to count/output pixel positions for beams, to cross-check against the grid master. Initial answer (from memory, citing `No_touch_box/docs/FLOORPLANVLM.md` already in the repo) was "not worth it" — that paper needed 300K pixel-aligned samples plus RL on top of SFT to get precision.
- Makham asked for real web research before trusting that answer. Search turned up something the FLOORPLANVLM comparison missed: **Qwen3-VL has native 2D grounding (bounding-box output) built into the base model** — not something that needs fine-tuning at FLOORPLANVLM's scale. Output format: `[x1,y1,x2,y2]` normalized to a 0-1000 scale (resolution-independent).
- Also found: VLM counting hallucination is a well-documented, persistent problem even in SOTA models (64.0-74.7% accuracy), root-caused to imbalanced cross-modal attention (the decoder over-trusts text priors over actual visual tokens) — this matches the beam-collapse failure directly (house09 หน้า26: 48 real beams → 2 in the model's JSON). And prompt-induced hallucination gets worse past ~4 objects, which a 48-beam sheet is deep into.
- Found a real fix pattern (**GroundCount**, arXiv 2603.10978): don't let the VLM count on its own — run a classical detection pass first (their case: YOLO) and feed its count/positions into the VLM's context as a hint. The prompt-augmentation variant alone recovered 81.3% accuracy, no architecture change needed — usable with a LoRA-finetuned model as-is.
- Found two papers doing exactly t03's multi-pass shape in the engineering-drawing domain (arXiv 2510.21862, arXiv 2506.17374): detection stage first (YOLO variants) localizes/annotates, VLM only interprets meaning afterward. Their own numbers make the case: the VLM stage that received pre-detected input scored 96.3% (F1) vs. 67.2% for the stage that had to detect-and-interpret in one shot — same shape of gap as our beam-plan failure. Read as validation that t03's pass-splitting direction is right, and a nudge to add a classical line-detection pass (Hough) specifically for beam counting, not just the multi-view cropping Pass 1 already does.
- Found a second technique (MinerU2.5, LookPlanGraph): decouple "describe what you see in prose" from "now format it as JSON" into two separate generations — reduces both syntax errors and hallucinated capability, because the model isn't fighting format constraints and content recall at the same time.
- **Wrote up the corrected finding and a concrete proposal in `tune_ai/t03/research_beam_grounding_vs_gridmaster.md`.** The proposal: don't replace `grid_ref` with pixel data in the schema (original reasoning from 2026-08-20 still holds — derived value, tied to one scan, grid_ref alone already proved out on the overlay work). Instead run grounding as a **separate QA cross-check pass**: ask for bbox output alongside the normal grid_ref extraction, convert grid_ref → pixel via the existing gridmaster (the same conversion `overlay_gt_vs_ai_house09.py` already does), overlay both, and flag disagreement — including a straight count check (bbox count vs. `elements[]` count) that would have caught the หน้า26 collapse mechanically, without a human eyeballing the JSON.
- **Named honestly, not tested:** whether t02's LoRA fine-tune retained the base model's grounding capability at all is unverified — heavy fine-tuning toward one output format can degrade unrelated capabilities (catastrophic forgetting), and this hasn't been checked. Same for whether the grounding output format actually comes out clean through Unsloth's chat template — it may expect special tokens (`<|box_start|>` etc.) the current template doesn't set up.
