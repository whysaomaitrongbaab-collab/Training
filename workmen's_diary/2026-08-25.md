### 1. Thai→English dictionary for prompts (prompt is English, model output is Thai-domain)

**Current state, verified by reading the actual prompt files:** every prompt in this project (`No_touch_box/Prompt/**/prompt.md`, `tune_ai/t03/_common.md`, `pass0_classify/prompt.md`, `primary_rawjson_schema.md`) is written in English, with an explicit standing rule (`_common.md:93,106`): *"Thai stays Thai. Never translate a printed [label]... the drawing's own alphabet — Thai ก/ข/ค stays Thai."* So today there is no dictionary layer at all — Thai text from the drawing is preserved verbatim in the output, and the English prompt just describes *what field* to put it in.

**Matching published technique found:** **Dictionary Insertion Prompting (DIP)** — arXiv 2411.01141 (2024), "Dictionary Insertion Prompting for Multilingual Reasoning on Multilingual LLMs". Inserts short English gloss/definition entries for key non-English terms **directly into the prompt** (not translating the whole input), giving an English-centric LLM explicit lexical grounding before it reasons. This is the closest existing research to what the teacher described — a Thai construction-term → English glossary injected alongside the prompt, distinct from the "never translate the drawing text itself" rule already in place (glossary sits *beside* the raw Thai as a reasoning aid, doesn't replace it in the output).

**Counter-finding worth knowing before building this:** a separate study found translating the **whole prompt** into English can score **~8% lower** than a native-language prompt, because translation loses context the native phrasing carried. So the safe version of this idea is DIP's *targeted term-glossary insertion* (a handful of `เสา = column`, `คาน = beam`, `ฐานราก = footing`, `เหล็กปลอก / ป. = stirrup`, `ตอม่อ = pedestal/tie-beam`, `DB/RB` rebar-type codes, etc.), not a wholesale prompt translation pass.

**Open question for อาจารย์:** which problem is the dictionary meant to solve — (a) helping the model map a Thai term it reads on the drawing to the *correct English schema enum* (`element_type`, `discipline`, etc.) — this is what DIP targets — or (b) something else (e.g. output i18n)? Current prompts give zero worked example of a glossary today, so this needs a decision before writing one.

### 2. pattern_recognition.py + cv2 template matching

**Searched, does not exist:** grepped/globbed `Constistant`, `Training` (incl. `No_touch_box`, `tune_ai/*`), and the sibling KU project `ku_project_jop` (incl. its full `git log --all` history) for `pattern_recognition` / `template_match` / `matchTemplate` — **zero hits anywhere, including deleted files.** This is a new idea from today's meeting, not a script to resurrect.

**Read the linked tutorial** (docs.opencv.org/3.4.7, API unchanged through 4.x): `cv2.matchTemplate(image, template, method)` slides the template over the image and returns a similarity map; 6 methods — `TM_SQDIFF`/`TM_SQDIFF_NORMED` (take the **min**), `TM_CCORR`/`TM_CCORR_NORMED`, `TM_CCOEFF`/`TM_CCOEFF_NORMED` (take the **max**, `_NORMED` variants are 0–1 and comparable across images). `cv2.minMaxLoc()` finds the single best match; for **multiple** instances of the same symbol on a page, threshold the similarity map (~0.8–0.9) instead of taking the single best.

**Limitations researched (not in the old tutorial, found separately):** plain template matching is **not rotation/scale invariant** — a symbol printed slightly bigger/smaller or rotated won't match well. Workarounds (a rotated+scaled template bank) are expensive and still weaker than feature-based or deep-learning detectors for that failure mode ([Medium: rotation/scale-invariant template matching](https://medium.com/@coders.stop/template-matching-beyond-basics-rotation-and-scale-invariant-detection-2ae78d8fa190), [arXiv 1907.01150](https://arxiv.org/pdf/1907.01150) multi-scale variant).

**Directly relevant domain research found:**
- **SkeySpot** (arXiv 2508.10449, 2025) — service-key/symbol detection on electrical layout construction drawings. Uses **YOLOv8** (deep learning), explicitly because classical template matching "struggles with variations in symbol appearance, rotation, scale, and image quality" common in real drawing sets and needs a template per variant.
- General floor-plan symbol-detection literature (search summary): normalized-correlation template matching (threshold ~0.9) **does** work well when the symbol is a small, fixed, exactly-repeated graphic (a legend icon, a north arrow, a grid bubble) — much weaker on hand-drawn or stylistically-varying elements.

**How this could plausibly fit our pipeline (observation only, nothing decided):** the thing this project currently struggles with by *manual* pixel-measurement is exactly the small-fixed-repeated-symbol case template matching is good at — see the 2026-08-24 diary entries where Makham hand-measured grid-row y-pixel positions (e.g. `y=768/1085/1404/1618 px`) directly off the PNG to correct a gridline extraction. A grid crosshair/tick template match could auto-locate those pixel positions as a classical-CV cross-check next to the VLM's gridline JSON, rather than replacing the VLM on variable content like beam/column marks (which SkeySpot's finding says template matching is the wrong tool for).

**Local precedent for this kind of hybrid, already in a sibling project:** `ku_project_jop` (เสาพัง, T-BHI bridge inspection) already combines classical CV + deep learning — `crack_scale.py` uses **ArUco marker detection** (`cv2.aruco`) for pixel→mm scale calibration, alongside a YOLOv8-seg model (`vision.py`) for the actual damage detection. Same "classical CV for precise fixed measurement, DL/VLM for variable content" split — just a different classical technique (marker detection, not template matching).

**Open question for อาจารย์:** confirm whether "pattern_recognition.py" refers to a file/example from a lecture (not currently in any repo we have access to) or is meant as a from-scratch build — and whether the target use is grid/symbol localization (matches the evidence above) or something else like page-orientation/logo detection.

### 3. max_frames currently 768 — where it actually is, and whether it's the right knob

**Traced the literal number:** `tune_ai/t03/ผล_t03_run/lora/processor_config.json` → `video_processor.max_frames: 768`. Confirmed via [GitHub QwenLM/Qwen3-VL#852](https://github.com/QwenLM/Qwen3-VL/issues/852) this is the **well-known hardcoded default** in Qwen2.5-VL/Qwen3-VL's **video** frame sampler (that issue is literally about this same constant — for a 2-hour video, 768 frames ≈ 1 frame every 9.4s, and it asks for it to be configurable via a `QWEN_VL_MAX_FRAMES` env var).

**Why it doesn't apply here:** grepped the whole repo for `max_frames` — the only hit is this one auto-saved config file. Our training/inference code (`train_t03.py` and every prior round) sends every drawing page as a still **image** content item (`{"type": "image", "image": PIL.Image...}`), never as `"video"` — the video processor / `max_frames` path is never invoked. **Raising this value would have zero effect on this project as currently built.**

**The two knobs that actually govern "how much the model reads at once" here** (both in `train_t03.py`, confirmed by reading the file):
- **`MAX_PIXELS = 5120 * 1024`** — visual-token budget *per image* (~5,120 tokens/image). This is the one t01 got silently wrong (defaulted to 512px/~266 tokens, rule_of_tune #12) and tanked accuracy — proven load-bearing.
- **`MAX_LENGTH = 32768`** — total sequence length (prompt + all images + JSON answer), already raised this round from t01/t02's 24,576 because gridline examples (4 images) measured ~26,791 tokens and were getting truncated mid-JSON.

**Researched the model's real ceiling:** base model `unsloth/Qwen3.6-35B-A3B` has a **native 262,144-token context window** ([Unsloth docs](https://unsloth.ai/docs/models/qwen3.6), [HF model card](https://huggingface.co/unsloth/Qwen3.6-35B-A3B)), extensible to ~1,010,000 via YaRN. So `MAX_LENGTH=32768` is nowhere near the *model's* limit — the actual ceiling right now is **GPU VRAM on the rented single card**: t03 already had to cut LoRA rank 32→16 to fit 32,768-length sequences in a 95GB GPU, and even then the eval step OOM'd from fp32 logit upcasting at that same length (both documented in `train_t03.py`'s own comments, 2026-08-24). Raising `MAX_LENGTH` further (e.g. more gridline images per example) is legitimately possible against the *model*, but costs more VRAM per step against the *hardware* already near its limit.

**What to bring back to อาจารย์:** clarify whether "max_frames" meant loosely "how much can the model read at once" (→ real answer: `MAX_LENGTH`, already raised once this round, model has far more headroom than the rented GPU does) or genuinely video frame sampling (→ not applicable, this project never sends video, and touching `processor_config.json`'s `max_frames` would do nothing).

### 4. Increase Qwen model size (bigger B)

**What's actually in use, checked against the training scripts:** t01/t03 use `unsloth/Qwen3.6-35B-A3B` (35B total / 3B active, MoE); t02 used a different, older-generation family, `Qwen3-VL-30B-A3B`.

**Qwen3.6 family ceiling, researched:** open-weight Qwen3.6 has exactly **two** sizes — **27B dense** and **35B-A3B MoE** (already what we use). The only thing bigger in the Qwen3.6 line is **Qwen3.6-Max-Preview**, which is **closed-weight, API-only** — not downloadable, not fine-tunable. So within this exact model family, **there is no bigger open-weight option to move to** — 35B-A3B is already the ceiling.

**Checked the older Qwen3-VL family (what t02 used) for a bigger open step:** sizes are 2B/4B/8B/32B dense, 30B-A3B/**235B-A22B** MoE. The next step up from t02's 30B-A3B is **Qwen3-VL-235B-A22B** — but researched hardware cost is a different order of magnitude: **~513GB+ VRAM for inference alone (8×80GB GPUs)**, and LoRA fine-tuning ~50% more on top (**~770GB+**) per current pricing guides ([Spheron](https://www.spheron.network/tools/gpu-recommender/Qwen/Qwen3-235B-A22B/), [Novita](https://blogs.novita.ai/qwen3-vl-235b-a22b-vram-how-to-avoid-huge-hardware-costs/)). That's a jump from today's single rented GPU (~$1.1/hr, one RTX PRO 6000 96GB) to an **8-GPU multi-node rental** — multi-GPU distributed training, not "rent one bigger card."

**Bottom line to bring back:** "increase B a lot" isn't a free dial here. Inside the model family already in use there's nowhere bigger (open-weight) to go. A genuinely much-bigger open VLM (235B-A22B) means ~8x the GPUs and a correspondingly much higher $/hr plus multi-GPU training complexity neither t01/t02/t03 have needed so far — a real budget/scope decision for อาจารย์+มะขาม to make explicitly, not a config tweak.
