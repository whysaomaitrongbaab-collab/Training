**Impact/precautions:**
- **The `checkout --theirs`-on-a-conflicted-file mistake is worth remembering as a pattern to avoid**: it looks like a safe, targeted per-file resolution but it actually discards the *entire* file's working-tree state (including cleanly auto-merged, non-conflicting content), not just the conflicting hunks. Only safe to use when you're certain the file has zero valuable content on the side you're discarding — verified via `git show <base-commit> --stat -- <file>` or equivalent, not assumed.
- **A hunk-boundary regex/scripted "take theirs per conflict marker" approach is also not safe** for a file with large, structurally significant hunks (loop openings, function bodies) — a hunk that looks self-contained in the diff can still depend on non-conflicting code just outside its markers. The syntax error it produced was only caught because `node --check`/`npm test` was run immediately after — this is exactly why "verify before declaring done" matters even for a git merge, not just for application code changes.
- **Auto-merged files are not automatically correct** — `tests/bbs-summary.test.js` had zero conflict markers and still shipped a self-contradicting assertion, because two same-day fixes on different branches touched non-overlapping lines of the same test with incompatible assumptions about the fixture. A green `git merge` exit code does not mean the result makes sense; only the test suite catching an actual assertion failure surfaced this one.
- Every merge step in this session was verified against the real `npm test` run (not just `node --check`) before pushing — this is the only reason both real mistakes were caught before landing on `origin/pipeline-optimize`.
