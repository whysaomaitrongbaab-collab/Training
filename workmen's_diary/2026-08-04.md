**Findings — the big one: training and production do different jobs**
- Training teaches **one-shot single-page**: 1 image → complete JSON for that page
- Production is **5-pass cross-page**: Pass 0 route → Pass 1 spec from section sheets → Pass 2 survey IDs in plans → Pass 3 count per ID → Pass 4 merge
- The tuned model was never taught to cross-reference across pages → at best it can replace **Pass 1 only**, not the pipeline
- This also caps `element recall` — ground truth is built from several sheets, but the model only ever sees one

**Findings — 3 real contradictions found in the Pass 0-4 ↔ schema mapping**
1. **Pass 3 breaks §4 of our own schema.** §4 says span is *"calculated by code from the grid only — never let the model estimate distance"*, but `qt_buildCountPrompt` asks the model for *"grouped by span length (meters)"* = eyeballing it off the image
2. **Pass 1 cannot express top/bottom rebar.** Production has one flat `main_bar_count`; §6 requires `main_bar{top,middle,bottom}` split always. Even a perfect read gets flattened on write — prompt + output shape must change before tuning Pass 1 is worth anything
3. **Pass 2 is dead code that still costs money.** `layoutIds` is collected then never used (Pass 3 loops over Pass 1's ids), errors swallowed by an empty `catch`. Costs N API calls per run. Possibly a recall lever if wired up — it would catch marks present in plans but absent from section sheets

**Findings — model choice: no reason to switch**
- Checked SAM 3 / Grounding DINO / YOLO-World first — **wrong tool**, as Makham pointed out: our elements are connected boxes with context needing ID + length, not dogs-and-cats detection. Real length comes from the grid table, not from box size in pixels
- Compared Qwen2.5-VL-72B against Qwen3.6-35B-A3B (t01's model): **Qwen3.6 wins on paper across the board** — newer (2026-04-15 vs 2025-01), MMMU 81.7 vs ~70.2, 262K vs 32K context, Apache 2.0, and its merge/GGUF path is already proven working on this machine
- The MoE-merge bug that killed t02 is specific to Qwen3-VL-30B-A3B, not to MoE in general — Qwen3.6 merged fine

**Findings — page-type taxonomy is fragmented across Constistant (6 incompatible sets)**
- Same question ("what kind of page is this?") is answered by 6 different vocabularies: schema §1 (**14**, now 16) · `QT_PROMPT_PAGE_IDENTIFY` Pass 0 (**2**) · `QT_PROMPT_CLASSIFY_SHEET` + `DrawingUpload.sheet_type` (**5**) · `DrawingUpload.drawing_type` (**3**) · `classifyPageType()` in `pdfTextLayer.js` (**7**) · `schema-v2.js` parked (**6**)
- **Information is already being lost today**, two places: `wz-step1.js:224` squashes 5 values into 2 (`general_notes`/`schedule_table`/`unknown` all become `section_detail`), and `drawing-index.js:205-208` hardcodes `section_detail` over whatever was actually read
- **The schema's 14 was already the richest of the six** — every Constistant value maps *into* it (`DETAIL_SHEET`→`section`, `TITLE_BLOCK`→`title`, `REBAR_SCHEDULE`→`schedule`, `elevation`→`side_profile`, `combined`→ not a pattern, it is §3 multi-view). So the real problem is the reverse: Constistant **cannot store** a 16-value result. Extending `sheet_type` is a prerequisite before a new Pass 0 can output the full taxonomy
- Makham's call: fixing the 6-way fragmentation itself is **not worth it right now** — only the 2 genuinely-missing patterns were added
