### 3. ★★ The most likely cause — **the LoRA may not be in t01's GGUF at all**

This is the biggest item of the night, and it is **the same bug that broke t02 on the 28th**

**4 pieces of evidence (actually read the real code with my own eyes, not inferred):**

1. **Pages 03-06 are t01's own training data** (train.jsonl lines 3-6) — the model saw them during training
   and still **fails to match the trained schema on a single page** — format conformance is what fine-tuning
   learns fastest (normally locked in within the first few hundred steps); missing it on pages it has memorized = highly abnormal

2. **`train_qwen36.py:152`** has a comment we wrote ourselves:
   *"must be 0 — this model's **MoE ParamWrapper** does not support dropout!=0 (confirmed from a real error)"*
   → **t01 uses ParamWrapper (LoRA of the `target_parameters` kind on MoE experts)**

3. **On the 28th we already proved that peft/Unsloth's `merge_and_unload()`
   merges a ParamWrapper-style LoRA on MoE incorrectly** (only 0.67% of the real values changed, when far more should have changed
   — the structure passes, but the behavior falls back close to base) → **t01's GGUF was converted with the same function**

4. **t01's guard against a silent merge failure is too weak to catch it** — `export_gguf.py:107`:
   ```python
   _looks_tuned = _pred.lstrip().startswith("{") and any(k in _pred[:400]
                  for k in ('"png"', '"views"', '"pattern"', '"doc_page"'))
   ```
   But **the prompt itself already instructs the model to answer using the words `"views"` and `"pattern"`**
   → a model **that has never been tuned at all** sails through this guard, just by following the prompt
   → back then it showed a green ✓ and that proved nothing whatsoever

**Compared with t02:** t02 got caught because its guard compared **the real key names** (found `page_number/title/project`
instead of `png/doc_page/...` and stopped) — **t01 used a weaker guard, so it let this through**

> **⚠️ Not yet proven — but the test is cheap and finishes in ~20 minutes:**
> Take the **untuned base Qwen3.6-35B GGUF** and run page 03 with the same prompt.
> If the output looks like t01's → **the LoRA really did not make it into the GGUF**, and every conclusion ever drawn from this GGUF file
> is about the base model, not about the thing we tuned · **this must be done before spending any more money on training/renting**

### 4. Two secondary causes (real, but not the main one)

**4.1 — image resolution at training ≠ at inference (a 14.3× difference)**
`llama_server_stdout.log` reports the actual image token count fed in: `2048 + 1748 = 3,796 tokens/image`
but t01 was trained on images the collator shrank to 512px = **~266 tokens/image** (the bug found in the t02 audit)
· llama.cpp even warned about it in the log itself (nobody read it):
```
W load_hparams: Qwen-VL models require at minimum 1024 image tokens to function correctly
W load_hparams: if you encounter problems with accuracy, try adding --image-min-tokens 1024
```

**4.2 — the GGUF Q4_K_M has never had its accuracy measured at all**
- The **90% JSON valid / 28.2% element recall** figures were measured with `eval_fields.py`, which loads
  **bf16 + adapter through Unsloth without going through merge** (`eval_fields.py:29` → `load_in_4bit=False`) — **not the GGUF**
- t01's Phase 10 tested the GGUF only for "does it answer in JSON, does it hang" — it never checked whether the content was correct
- `t01_workflow.md` itself records that Unsloth warns this family *"loses quality abnormally when quantized"*
  (the reason bf16 training was mandated) — **we were careful during training, but forgot to be careful when putting it to use**

> **Important:** the 90%/28.2% figures are still **valid for the adapter** — what remains unconfirmed is the **GGUF**
