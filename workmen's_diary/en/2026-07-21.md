## Claude — continuing from the top entry: the "GPU out of memory" problem (CUDA out of memory) — explained in great detail, as Makham requested

Confirmed from the log that all the previous bugs were genuinely gone — the line `image processor: max=5242880 px (≈5120 visual tokens/image)` appeared correctly (matching the intended 5,120, no longer the 16,384 default), and there was no more error from `lora_dropout` — **it moved successfully all the way through the forward pass (having the model read the image+predict) to the backward pass (the step that calculates how to adjust the model's weights)**, but then crashed right there with this error:

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 100.00 MiB.
GPU 0 has a total capacity of 94.97 GiB of which 96.25 MiB is free.
```

### What is "CUDA out of memory" (explained without assuming prior background knowledge)

A GPU has its own memory (VRAM), separate from a computer's normal RAM — this rented machine has 95GB of VRAM. When training an AI model, the model itself must first be loaded into VRAM (35 billion bf16 parameters already consumes most of it), and then during computation (both when reading the image/predicting an answer, and when calculating weight adjustments) there must be room left over to store "intermediate values" during the calculation too (called activation memory) — the longer/larger the text/image fed in, the more intermediate values need to be stored.

It crashed here because **94.87GB of the total 94.97GB had already been used (only 96MB free), but it needed just 100MB more, and that still wasn't enough** — an extremely close call (short by only ~0.1% of the total), not a crash from a severely wrong setting, just something set with "a bit too much margin" that overflowed slightly.

### Why it was this close a call — found that `MAX_LENGTH` had been set with more margin than necessary

`MAX_LENGTH` is the maximum length (counted in "tokens", the small units text is broken into, roughly a word or syllable) allowed for 1 example. It had initially been set to 10,240, a rough estimate of "instruction ~1,020 + image 5,120 + longest answer ~2,750 + a safety margin".

But upon opening the `stats.json` file (a stats summary file created when preparing the dataset) and looking at the **actual** numbers from the 226+88 examples, found:
- Instruction = 1,022 tokens (matching the estimate).
- The actual longest answer found (across both train and val) = 2,748 tokens (not just "approximately 2,750" — this is the value measured from every real example).
- Combined with the image's 5,120 tokens = 1,022 + 5,120 + 2,748 = 8,890 tokens, the maximum length that could "actually occur".

So the originally set 10,240 had a full 1,350 tokens of margin that could never actually be used (no example is that long) — this "reserved for nothing" margin forced the GPU to prepare activation memory for the set maximum length (not the actual length used), wasting space unnecessarily.

### The 3 fixes used (all of which "don't affect model quality" — just smarter memory management, not reducing what the model sees/learns)

**(1) Reduced `MAX_LENGTH` from 10,240 → 9,216**
Used the real number from stats.json (8,890) plus an added ~330-token buffer (for a few small special tokens the template might add), instead of the previous excessive margin — cutting out "space that would never be used", not cutting any real content from any example (since no example is longer than 8,890 anyway).

**(2) Added `PYTORCH_ALLOC_CONF=expandable_segments:True`**
This is a setting for PyTorch's own memory manager (the program used to run AI calculations) — normally, as a program repeatedly requests and releases GPU memory, "memory fragmentation" occurs (like a parking lot with small scattered empty spots — even if they add up to enough total space to fit a big car, there's no single spot long enough). `expandable_segments:True` tells it to make the reserved memory chunks more flexible in size, reducing this problem (PyTorch itself directly suggested this flag in the error message encountered).

**(3) Changed the optimizer from `adamw_8bit` → `paged_adamw_8bit`**
The "optimizer" is the part that calculates which direction/how much to adjust the model's weights at each step. It has to keep "statistics" for every parameter too (consuming extra VRAM) — the "paged" version borrows the concept of "virtual memory" from ordinary computers (when RAM isn't enough, the computer temporarily moves some of it to the hard disk) and applies it to VRAM/RAM instead, preventing a sudden spike in memory demand from the optimizer's work from overflowing (switching from the same-calculation optimizer, just a different memory-management method, doesn't affect training results).

### Why not fix it by "reducing image resolution" (`MAX_PIXELS`) instead
This is another possible route (a smaller image = fewer tokens = less VRAM), but it **was not chosen**, because the 5,120-token value isn't a random number — it's a value already tested previously to be the lowest point that can still distinguish top/bottom rebar dots in the drawing. Going lower than this risks the model misreading rebar numbers (a problem often encountered, as recorded in the project's CLAUDE.md) — so a different fix was chosen instead, one that doesn't affect quality, per the rule set in `rule_of_tune.md` rule 2 (any value that affects what the model sees/learns must always be warned about/permission asked before changing — the 3 methods chosen above don't fall under this, since they're purely memory management).
