# Part 3 — The day the AI never finished its sentence (August 21-22, 2026)

Continued from `2026-07-29(teach mk).md`
Basic vocabulary (token, LoRA, VRAM, GGUF, visual token) was already explained in Parts 1-2; this part just refers to it and doesn't explain it again

> **Shortest summary before the long read:** model t02 read a beam plan page and **never finished its JSON answer** — it kept typing round and round in a loop
> until it ran out of its word quota and stopped mid-sentence. The result: the whole page was unusable, even the parts it had read correctly at the start
> Tonight it got solved for good with a technique called **grammar-constrained decoding** → pages that pass went up from **57.9% to 96.8%**
> But this fix exposed a bigger problem: **a grammatically valid answer doesn't mean the content is right**

---

## 1. The symptom — what "never finishing the sentence" looks like

We told t02 to read house 08's beam plan page. What came back was:

```json
{ "png": "20", "sheet_code": "S-03",
  "elements": [
    { "element_id": "B2", "grid_ref_start": "D1", "grid_ref_end": "D2" },
    { "element_id": "B2", "grid_ref_start": "D2", "grid_ref_end": "D3" },
    { "element_id": "B2", "grid_ref_start": "D3", "grid_ref_end": "D4" },
    { "element_id": "B2", "grid_ref_start": "D4", "grid_ref_end": "D5" },
    ... (looping like this for hundreds more lines) ...
```

And then it **just stopped there** — no `]`, no `}` to close it off

### Why just an unclosed bracket is such a big deal

JSON is a very strict language. If the brackets are incomplete, the computer fails to read **the whole file** — it doesn't get to read even part of it

Analogy: it's like writing a 3-page letter but forgetting to close a quotation mark you opened on the very first line
A person can still more or less follow it, but a **machine** will say "this file is broken" and throw away the whole thing

The actual measured result: that beam plan page has 31 real beams, and the model had already read several of them correctly at the start
but because it didn't close the brackets in time, **we got 0 of them** — the work it had already gotten right was lost along with it

---

## 2. Why the AI keeps looping and never finishes

### The AI doesn't "write an answer" — it guesses the next word, one word at a time

This is the key thing to understand first. The AI doesn't think up the whole answer as one chunk and then type it out
It works like this: look at everything typed so far → **guess what the next word is likely to be** → type it → loop back to step 1

So when it types `{ "element_id": "B2", "grid_ref_start": "D3"...`
it doesn't know "I'm writing beam number 40" — it only sees that this kind of pattern keeps repeating above
and the word that's "likely to come next" is the same pattern one more time

### The trap: the more it loops, the more sure it is that it should keep looping

Once it has typed the same pattern 5 times, the evidence it sees is "this page has a whole lot of this pattern"
so the 6th time it's even more confident than before, and the 20th time more confident still — **it keeps digging itself a deeper and deeper hole**

This symptom is called a **repetition loop (repeating itself in a loop)**, and it's a chronic condition that every AI has
not just ours, and not because we tuned it wrong

### Then why doesn't it stop on its own

It only stops when it guesses that "the next word is the end signal", but once it's stuck in the hole
the end signal always scores lower than the repeated pattern, so in the end it hits the `max_new_tokens` ceiling
(the maximum word quota we set = 3,000) and gets cut off midway

**It's this ceiling that cuts it off, not the AI** — that's why it ends without closing the brackets

---

## 3. Attempt 1 — tweaking parameters (helps, but not enough)

On the 21st we added these 2 into the answer-generation call:

| Parameter | Value | What it does |
|---|---|---|
| `repetition_penalty` | 1.15 | Words already typed get **points deducted**, so they're less likely to be picked again |
| `no_repeat_ngram_size` | 8 | Forbids repeating any run of 8 consecutive words that **has already been typed word-for-word** before |

It helped somewhat — from "breaks every time" to "breaks sometimes"
But it still wasn't a fix at the root cause, because both of these only **make looping harder** — they don't prevent it from ending without closing the brackets

---

## 4. Attempt 2 — Grammar-constrained decoding (the one that solved it)

### The idea: post a "gate guard" every time it's about to type

Normally the AI picks the next word freely from its entire vocabulary (~151,000 words)

grammar-constrained decoding means taking **JSON's grammar rules** and making them the guard —
every time the AI is about to type the next word, the guard first checks *"if this word gets typed, will the JSON still be grammatically valid?"*
If not, it **cuts that word out immediately** — it isn't allowed to be picked at all

A simple analogy: it's like writing on paper with lines that force the pen to stay on them —
the pen can't go outside the lines at all — it's not "you can go outside them, but you lose points"

### What follows automatically

- **Brackets are always fully closed** — because if a `[` is open, the guard won't let it end until there's a `]`
- No strings with a forgotten closing quotation mark
- No numbers left half-typed, like `3.` and then it ends

**Important: this is the difference between "asking nicely" and "forcing"**
`repetition_penalty` is asking nicely (it deducts points, but the model can still do it)
grammar is forcing (it can't do it at all — it's physically impossible)

### We tried 2 of them and picked the second one

| Tool | Result |
|---|---|
| `lm-format-enforcer` | Works, but has a weak spot — see section 5 |
| **`xgrammar`** | **Better on every point → chosen as the default** |

## 5. Tonight's most expensive lesson — I misdiagnosed it, and had already written it into the docs

This part matters more than all the technical stuff above — read it slowly, Makham

### What happened

Added the grammar, first run → **still broken**, the JSON still wouldn't parse
I immediately concluded *"Unsloth (the model loader) must be swallowing the grammar instruction and not passing it on"*
and **had already written that conclusion into SUMMARY.md**

**Wrong. Dead wrong.**

### What was actually going on

Once I traced through the real code layer by layer (not guessing), I found:

1. Unsloth passes the instruction on in full — it doesn't swallow anything at all
2. The grammar was working the whole time
3. **The real root cause:** `lm-format-enforcer` treats `{"a":1,}` (an extra comma before the close) as **acceptable**
   but Python treats it as **wrong** — the two sides don't define "valid" the same way

Provable in 1 line: take a "broken" file and delete the extra comma → **it's readable immediately**
Meaning the grammar had been working correctly all along — I accused an innocent party

### 2 things to remember

**Point 1 — Don't blame the tool before reading the real code**
A "probably because of X" that sounds reasonable ≠ "because of X"
When hunting for a cause, trace the real thing layer by layer — don't pick the suspect that makes the prettiest story

**Point 2 — A wrong guess written into the docs is worse than writing nothing**
If the evidence isn't enough to point to the cause yet, write *"Cause not known yet; the suspects are A or B"*
Don't write a wrong, definitive verdict, because whoever reads it later (including ourselves 3 months from now) will believe it and keep going the wrong way

## 6. Real results — measured in numbers

Real run on an RTX PRO 6000 GPU (96GB): all 25 pages of house 08 + another 6 pages of house 09:

| | Before (no grammar) | After (xgrammar) |
|---|---|---|
| Pages with readable JSON | 57.9% (11 of 19) | **96.8% (30 of 31)** |
| House 08 beam plan page | ❌ Broken in both runs | ✅ Passed |

## 7. The bug grammar can't fix (there's 1, and we really hit it)

Page 07 of house 08 is still broken — the model printed this:

```
"description": "ct_igh_igh_igh_ide_igh_igh_igh_ida_igh_igh_igh_ife_igh_igh..."
```

It loops **inside the quotation marks** and then hits the word ceiling

**Why the guard can't catch it:** inside a string, any character at all is grammatically valid
The word `igh` is valid, `บ้าน` is valid, anything is valid — the guard's job is to check grammar, not meaning

**Why `no_repeat_ngram_size=8` can't catch it either:** it keeps swapping in different separators (`_ide`, `_ida`, `_ife`)
so no run of 8 words ever repeats exactly — it slips past the rule just right

**The fix we used:** check whether the file fails to parse → regenerate just that one page
(1 page out of 31 isn't worth sitting down to build a more complicated fix than this)

## 8. Bigger than the bug — a grammatically correct answer ≠ a correct answer in content

Once the JSON was readable, we got to see the real output for the first time — and the real output is **still not good**

On house 09's beam plan page, which should have 48 beams, the model answered with **2 beams** and then wrote a jumble like
`"F-F x 1'-2', F-F x 2'-3', ..."` — stuffing the whole page into a single field

We drew the answer on top of the real drawing (the file `_overlay_gt_vs_ai_หน้า26.png` I sent you to look at):
- **Left (green) = human-checked ground truth** → the lines sit exactly on the real beam lines for 45 of 48 beams
- **Right (orange) = AI** → floating boxes that don't follow the beam lines at all

**This is the image that explains everything in one picture** — even with the naked eye you can tell they're two completely different things

### Why is it like this — the answer lies in the number of examples

I went and actually counted the data used to tune t02, and got this:

| Page type | Seen by t02 during training | Result |
|---|---|---|
| Door-window schedule | ~24 pages | Reads **86%** ✅ |
| Material list | ~158 pages | Usable |
| **Beam plan** | **~13 pages** | **Reads 11%** ❌ |

**See the relationship?** — the pages it saw a lot of, it does well; the pages it saw few of, it can't do
It's not because beam plans are too hard, but because **we only taught it 13 sheets**

On top of that, the beam plan is also the hardest page type (25 beams per page on average, and each one needs its start-end points right)
Hardest + fewest examples = most broken

## 9. So how many houses of data are enough?

This kind of work needs roughly **100+ examples per page type** before it starts to stabilize

| Level | Number of houses | Beam plans obtained |
|---|---|---|
| Now | 11 houses (4 actually used for tuning) | 35 sheets (13 actually seen) |
| **Target** | **25-30 houses** | **80-96 sheets** |
| Full-scale | 40-50 houses | 128-160 sheets |

### But don't add more the old way — this is where a huge amount of effort can be saved

I counted and found that **the "material list" pages ate up 435 files = 37% of all the work done so far
but contribute elements = 0** (they're tables, with no member positions)

If new houses do **only the pages the system actually uses**, it comes down to ~38 pages per house instead of ~107 pages

> **Adding 20 houses = doing ~750 pages (not 2,140 pages) — 65% less effort for the same result**

Full details are in `tune_ai/t03/dataset_sizing.md`

## 10. Summary of tonight's lessons

1. **AI not finishing its answer ≠ AI being stupid** — it falls into a repetition hole because it guesses the next word one at a time; it doesn't plan the whole answer
2. **"Asking" and "forcing" are different** — `repetition_penalty` is asking, grammar is forcing; a structural problem needs forcing
3. **Don't declare the cause before reading the real code**, and if you're not sure yet, write that you're not sure yet — a wrong guess written into the docs is more dangerous than not writing anything
4. **Fixing the format doesn't fix the content** — grammar made the files 96.8% readable, but the accuracy is still the same as before
5. **The number of examples is what determines accuracy** — 13 sheets got 11%, 24 sheets got 86%; the numbers say it plainly
6. **When making more data, be selective about it** — doing every page equally wastes 65% of the effort on pages nobody uses

## New vocabulary from this episode

**Grammar-constrained decoding (forcing the grammar while the answer is being generated)**
A technique that forbids the AI from typing any word that would make the output ungrammatical — it removes that option before the AI gets a chance to pick it

**xgrammar**
The program that plays the guard role described above — the one we chose; its strength is that it can't produce an extra comma at all, right from the source

**Repetition loop (going round in circles)**
The symptom where the AI keeps typing the same pattern without stopping, because the more it repeats, the more the evidence tells it to keep repeating

**max_new_tokens (word-count ceiling)**
The maximum word quota per answer — ours is set to 3,000; if it hits the ceiling, it gets cut off mid-sentence immediately

**parse (reading a file into data)**
The step where the machine turns text into data it can keep working with; if the grammar is wrong in even one spot, the whole file fails

**recall (completeness)**
Measures: if there are really 100 items, how many the AI finds — a different thing from "are the ones it found correct?"

**Ground truth (answer key)**
Data a person has checked and confirmed correct, used as the ruler to measure how right the AI's answers are
