## Project

"Constistant" (Steel Calc) — a static, no-build, vanilla JS web app for Thai construction teams: rebar cut-list optimization (CSP), AI-driven drawing/quantity-takeoff scanning, and project save/load via Supabase. Built for STECON Group Innovation Challenge SS4.

There is no build step — plain HTML/CSS/JS files served directly (e.g. via a static file server / Live Server). Tests do exist: `npm test` runs every `tests/*.test.*` file via Node's built-in test runner (no framework; currently the BBS regression + shape-allowance suites). Fixtures live in `tests/fixtures/`.

See [README.md](README.md) for the full project layout and data flow diagram.

## Architecture

### Shell (`contistant.html` + `js/shell/`, `css/`)
`contistant.html` is a thin shell: topbar (project switcher, "Calculate Project" button), sidebar, tab bar, and one `<div class="app-panel" id="*-app">` per feature tab. `js/shell/shell-index.js` wires tab switching, project switcher, wizard overlay, and `constistant_runPipeline()`.

### Data contract: `js/shared/schema.js`
Single source of truth for all object shapes. **Never construct entity objects ad-hoc — always use `create*` factory functions.**

Entity dependency chain:
```
projects
  └── project_config
  └── drawing_uploads
        ├── beam_library
        └── drawing_elements
              ├── boq_items → bbs_items → schedule_tasks → resource_items
              └── readiness_checks
```

`schema.js` also exports lookup tables: waste/lap/bend factors, cost factors, `CREW_TYPES`, `EQUIPMENT_TYPES`, `PROVINCIAL_WEATHER`, `WORK_TYPE_HIERARCHY`, etc.

### Shared modules (`js/shared/`)
- `schema.js` — entity factories and reference tables
- `demo-seed.js` — demo project seed data via `getDemoDataByEngine(engine)`
- `pipeline.js` — `runPipeline()`: BOQ → BBS → schedule → resources → readiness; fires `PIPELINE_EVENT`
- `project-store.js` — multi-project localStorage via `projectStorageKey()`; fires `PROJECT_EVENT`
- `storage-keys.js` — single registry of every localStorage key (`STORAGE_KEYS` project-scoped + `GLOBAL_STORAGE_KEYS`); `PROJECT_SCOPED_KEYS` (used by `deleteProject()`) is derived automatically from the registry instead of hand-maintained, so a new project-scoped key can't be forgotten there again. `pipeline.js` re-exports `STORAGE_KEYS` for backward compat; feature modules should import keys from here rather than declaring key strings locally.
- `timeline-engine.js` — duration estimation, budget impact, task grouping, weather buffer, `computeEVM()` (Earned Value Management: SPI/CPI/EAC/VAC + S-curve series from `schedule_tasks.percent_complete`/`task_cost_actual`)
- `price-config.js` — **single source of truth for material pricing** (concrete, rebar, formwork, labor costs from CGD 2569); supports user overrides via `getEffectivePrice()` + localStorage, tracks `unit_price_source` ('cgd_2026' | 'manual' | 'upload')
- `standards-config.js` — **single source of truth for engineering constants** (rebar lap, concrete cover, hook, bend deduction, stock bar lengths), same provenance pattern as `price-config.js`: every value carries its standard + clause, resolves override > extracted > default, and returns a provenance object rather than a bare number. Exports `resolveStandard()`, `lapLengthMm()` (WSD fixed multiples vs. SDM `LD_TABLE`), `coverMm()` (keyed by exposure via `EXPOSURE_BY_ELEMENT`, not by element type), `hookMm()` (scales with bar diameter), `isUnusualOverride()`. Pure — no DOM, no storage; `buildStandardsContext()` in project-store.js assembles its `ctx`
- `work-packages.js` — Work Package grouping + progress derivation, **pure** (zero storage/DOM imports; `schema.js` imports *from* it, so it must stay leaf-ward). Owns `parseTaskId`/`progressKey`/`stageOfTask` — the pipeline emits two task-id shapes (`task-<element>-<floor>-<stage>` per element, `task-excavation-<floor>` per floor) and every consumer must parse through these rather than string-matching, which has caused silent-data-loss bugs twice. Also `buildWorkPackages()`, `applyProgressToTasks()`, `tickStage()` (the sole authority on the pre-pour hold point — returns a Thai reason the UI prints verbatim), `activeThisWeek()`, `orphanedProgress()`
- `inspection-checklists.js` — pre-pour inspection items per element type (data only, same pattern as `building-law-reference.js`)
- `structure-model.js` — **pure** geometry/status/rebar model for the 3D viewer (no THREE, no DOM, no storage; imports only `standards-config.js`). `buildStructureModel()` → floors + one box per physical piece (z-vertical, `box.z` = bottom, metres); `applyStatusToPieces()`/`pieceStatus()`/`actionableCategoryId()` (exactly one WP is "ต้องทำตอนนี้"); `rebarLayout()` distributes bars corner-first and returns an `unknowns` list rather than a guess; `structuralWorkPackages()` filters the category rail to real structural types on real floors; `elementGetsLap()` (slab excluded, matching the pipeline). The Planner 3D view (`js/planner/planner-3d-scene.js` + `planner-3d-view.js`) renders it
- `project-status-strip.js` — shared "5-second answer" project status, rendered into a popover (`#project-status-strip`) anchored to a small button in the topbar next to "Calculate Project"; hovering the button reveals it (rows fade in sequentially via CSS). Shows phase, RAG dot, overall % (EVM), key dates/days remaining, rainy-season alert. Public API: `ph_renderStatusStrip()`

### AI Vision pipeline (`js/ai/`, `js/drawing/drawing-qwen.js`, `supabase/functions/qwen-vision/`)
**Qwen-VL-Max (Alibaba DashScope) is the active vision model**, called server-side only — no API key ever reaches the browser.

- `js/ai/qwenVision.js` — client wrapper; calls `supabase.functions.invoke('qwen-vision', { body })` via the Supabase JS SDK. Exposes `analyzeDrawingWithQwen()` / `analyzeDrawingWithQwenMulti()`.
- `supabase/functions/qwen-vision/index.ts` — Deno Edge Function holding `QWEN_API_KEY`/`QWEN_API_HOST` as env secrets; validates image size (max ~5MB/image, 20MB total payload), proxies to Qwen's OpenAI-compatible `/chat/completions` with `response_format: json_object`.
- `api/qwen-vision.js` — **legacy Vercel serverless fallback** of the same proxy (used before the Supabase Edge Function existed); includes its own request-size checks and rate limiting via `database/rate_limit.sql` (`check_rate_limit()` Postgres function, fixed-window, `RATE_LIMIT_PER_MINUTE = 10`). Prefer the Supabase Edge Function path for new work.
- `js/drawing/drawing-qwen.js` — `qt_callQwenParts(prompt, parts, maxRetry)` mirrors the old Gemini "parts" interface (mixed `{text}`/`{inline_data}` array) so callers (`drawing-index.js`, `wz-step1.js`) needed minimal changes when swapping providers; handles 429/5xx backoff+retry. Also exports `qt_classifySheetQwen(imageDataUrl)` for wizard Step 1 sheet-type classification.
- `js/drawing/drawing-gemini.js` — **legacy/fallback**, Gemini 2.5 Flash integration. No longer imported by `drawing-index.js`/`wz-step1.js`; kept in case Qwen needs to be swapped back. `qt_getMime()` is re-exported from `drawing-qwen.js` since it's provider-agnostic.
- `js/ai/prompts.js` — all extraction/classification prompt builders (`QT_PROMPT_CLASSIFY_SHEET`, `QT_PROMPT_PAGE_IDENTIFY`, `QT_PROMPT_LAYOUT_SURVEY`, `qt_buildExtractionPrompt()`, `qt_buildCountPrompt()`).

**Multi-pass extraction flow** (`drawing-index.js` → `qt_runRead()`): Pass 0 (AI identifies section/layout pages in a multi-page PDF) → Pass 1 (extract element details from section pages) → Pass 2 (survey element IDs present in layout/floor-plan pages) → Pass 3 (per-element-ID rebar length/qty counting from layout pages) → Pass 4 (merge into `qt_elementsData`).

**Soil Investigation's boring-log AI upload uses Gemini instead of Qwen** (`js/site/site-gemini.js`): `si_callGeminiParts(prompt, parts, maxRetry)` calls `js/drawing/drawing-gemini.js`'s existing `qt_callGeminiParts()` directly with a key imported from the local gitignored `gemini.js` (repo root — see Setup). This is a deliberate exception to the "no API key in the browser" rule used elsewhere: it's a client-side key, intentionally simple for this private team demo phase, not routed through a Supabase Edge Function. `js/site/site-index.js`'s `si_uploadSoilFile()` is the only caller. Do not reuse this pattern for a public-facing deployment without revisiting the key-exposure tradeoff.

### Material Pricing System (`js/shared/price-config.js`, `js/boq/boq-export.js`)
**Single source of truth for construction material costs** — replaces hardcoded rates across pipeline/BOQ/catalog.

**Data hierarchy:**
1. `MATERIAL_PRICES` in price-config.js — base prices from CGD 2569 (concrete: 180-350 ksc; rebar: SR24/SD30/SD40 all diameters; formwork; labor)
2. User overrides — localStorage `constistant_price_override` (per material_key: `concrete.ready_mix_240`, `rebar.sd40_16`, etc.)
3. Supabase `material_prices` table (future per-project pricing)

**Functions (actual exports — verified 2026-07-11):**
- `getPriceByCategory(category, subtype)` — retrieve base price (material_key = `category.subtype`)
- `getEffectivePrice(material_key)` — base price + user overrides (reads override store internally)
- `getConcretePrice(ksc)` / `getRebarPrice(grade, dia_mm)` / `getFormworkPrice(element_type)` — typed lookups used by the pipeline
- `getPriceSourceInfo(source_code)` — badge metadata for a `unit_price_source` value
- Note: there is currently **no exported override writer** (`saveLocalStorageOverride` never existed); Material Catalog manipulates the override store via its own UI handlers

**BOQ Export (`js/boq/boq-export.js`, `js/boq/boq-export-variants.js` + `boq-print.css`):**
- `exportBOQToHTML(projectId)` — generic export handler; pulls data from localStorage `STORAGE_KEYS.boq` (populated by pipeline)
- **4 export variants** in `boq-export-variants.js`, each a pure `{key, label, description, render(project, items)}` function (self-contained, no shared state) selectable from a dropdown on the BOQ Summary page — see [docs/BOQ_EXPORT_VARIANTS.md](docs/BOQ_EXPORT_VARIANTS.md):
  - `government` (default) — Thai procurement standard (mirrors "Boq Excel Template for public job.xlsm"): hierarchical WBS grouping by `category_code`, category subtotals, grand total + 7% VAT, signature blocks
  - `contractor` — Contractor Proposal / quotation format for bidding
  - `breakdown` — Cost Breakdown by work type (concrete, rebar, formwork)
  - `schedule` — Payment Schedule, milestone-based by project phase
- PDF generation goes through a **local Puppeteer server** (`server/pdf-server.js`, `node server/pdf-server.js`, listens on :3002): `exportBOQToHTML()` builds the HTML then `generateBOQPDF()` POSTs it to `/api/pdf/generate` and downloads the returned PDF (solves Thai-font/text-layer corruption from Microsoft Print to PDF). The express/cors/dotenv/puppeteer deps in package.json exist for this server — it is live, not legacy.
- Print CSS: A4 landscape, Sarabun + IBM Plex Mono, color-coded rows (category header #d4d4d4, subtotal #e8e8e8, grand total #1a4080)

**Integration:** Pipeline reads prices via `getConcretePrice(ksc)`, `getRebarPrice(grade, dia_mm)`, `getFormworkPrice(element_type)` → tracks `unit_price_source` in BOQ items for traceability.

### Planner (`js/planner/`) — site-engineer overview
Page is overview-first: header status strip (activity/critical counts, total days, project end date, SPI/CPI pills via `computeEVM()`, overall % -complete bar) → HTML-grid Gantt → editable task table → add-activity form. See [docs/PLANNER_ENHANCED.md](docs/PLANNER_ENHANCED.md) and [docs/PLANNER_QUICK_START.md](docs/PLANNER_QUICK_START.md).
- Gantt is an HTML grid (`.gantt2*` classes in `css/feature-panels.css`), not SVG — left label column + month axis row + per-task lane, with percent-complete fill, critical-path outline, weather-risk hatch, rainy-season band overlays, and a today-line.
- Click any Gantt bar → `pl_showDetail(id)` opens a `.modal-overlay`/`.pl-detail` modal with the full task record (`renderDetailModal`), including a transparent duration-formula breakdown (ระยะเวลา = ปริมาณงาน ÷ (ทีม × productivity) × (1 + เผื่ออากาศ)) when quantity/crew/productivity are present; `pl_closeDetail()` closes it. State held in module-level `openDetailId`.
- **Drag-to-reschedule** (`js/planner/planner-drag-handler.js`, `pl_initDragHandlers()`): click-drag a Gantt bar left/right to move its dates, snapping to 1-day increments (`SNAP_DAYS`); on drop, applies via `pl_updateTaskDate()`, cascades dependents (`shiftDependents()`), and shows the budget delta.
- **Critical path analysis** (`js/planner/planner-critical-path.js`): `identifyCriticalPath(tasks)` runs forward/backward-pass CPM to compute float per task (critical = float ≤ 0.1 days); `analyzeDependencies()` and `renderDependencyGraph()` support the dependency view; `renderCriticalPathSummary()` renders the highlighted summary card. Runs on save / "Calculate Project".
- Editing `% เสร็จ` / `ใช้จริง (฿)` in the task table calls `pl_updateProgress`/`pl_updateActualCost`, which persist and dispatch `PIPELINE_EVENT` (`reason: 'progress-changed'`) so Overview's EVM card re-renders live.
- `loadProjectConfig()` falls back to `getDemoProject().project_config` when the current project is `DEMO_PROJECT_ID` and localStorage has no saved config (keeps rainy-season overlay working out of the box).

### Module conventions
- ES modules, but functions also attached to `window`/`globalThis` for inline `onclick` handlers.
- Cross-module mutable state on `globalThis` (e.g. `qt_elementsData`).
- Comments mix Thai and English — follow existing usage per file.

### Three-layer model
1. Frontend (HTML/CSS/JS) — UI only
2. Supabase JS SDK (`supabase.js` at repo root) — DB read/write, plus Edge Function invocation for AI vision (`supabase.functions.invoke('qwen-vision', ...)`)
3. Supabase (Postgres + Auth + Edge Functions) — schema in `database/`; Edge Functions in `supabase/functions/` (deployed via Supabase CLI, config in `supabase/config.toml`; secrets `QWEN_API_KEY`/`QWEN_API_HOST` set via `supabase secrets set`, never committed)

### BBS (Bar Bending Schedule) — rebar cut-list viewer (`js/bbs/bbs-index.js`)
**Recent enhancements (June 2026):** Improved data cell formatting to correctly handle zero values (0 is valid data, not hidden) across qty, cut-length, unit-weight, and total-weight columns. Added extensive debug logging for CSV import pipeline (`bbs_parseManualInput` → `bbs_normalizeRawRow`) to trace data transformation from raw CSV through shape dimension parsing and weight calculations. Manual import now supports rebar specifications (mark, diameter, spacing, pin, shape type, shape dims A/B/C/hook, qty, cut length, unit weight).

**Key functions:**
- `bbs_importManualData()` — parse CSV, validate headers, create section
- `bbs_parseManualInput(text)` — split CSV lines, map headers, normalize rows
- `bbs_normalizeRawRow(raw, index)` — coerce types, calculate derived fields (lengths by diameter, totalWeight)
- `buildSectionTable(section)` — render table with shape SVG per row
- `renderShapeSvg(shapeType, shapeDims, dia)` — draw rebar shape code (from `bbs-shapes.js`)
